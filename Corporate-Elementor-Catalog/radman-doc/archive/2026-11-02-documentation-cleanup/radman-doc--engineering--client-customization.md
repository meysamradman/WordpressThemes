# سفارشی‌سازی هر مشتری

## ساختار محصول سفارشی در Child — CONFIRMED، ۲۰۲۶-۱۱-۰۲

طبق درخواست مالک، مسیر محصول مانند وبلاگ به ورودی‌های پایدار و قطعه‌های قابل طراحی تقسیم شد؛ این مرحله تغییر طراحی یا کپی امکانات اختصاصی وبلاگ به محصول نیست. آرشیو واقعی WordPress، دسته/زیردسته، برند/ویژگی و جزئیات همان رکوردهای موجود را مصرف می‌کنند.

- `template-parts/catalog/archive.php`: پوستهٔ آرشیو؛ `archive/header.php` عنوان و توضیح دسته، و `archive/section.php` ناحیهٔ نتایج قابل جایگزینی AJAX است. query، فیلتر و pagination در موتور مشترک والد می‌مانند.
- `template-parts/catalog/single.php`: Loop، حفاظت رمز، لینک بازگشت و ترتیب اجزا؛ `single/overview.php` رسانه و خلاصه، و `single/content.php` توضیح و صفحه‌بندی محتوا را نگه می‌دارند. گالری، دسته/برند/ویژگی، نمایش قیمت/تماس و مشخصات از rendererهای مشترک می‌آیند.
- `template-parts/catalog/card.php` ورودی سازگار قبلی و `shared/product-card.php` مالک markup کارت محصول است؛ کارت در پاسخ معمولی و AJAX یکسان مصرف می‌شود.
- `inc/catalog/sidebar.php` جای‌گذاری سایدبار آرشیو، ثبت ابزارک و enqueue شرطی را به Grid مشترک متصل می‌کند. `template-parts/content/sidebar.php` برای scopeهای محصول به `template-parts/catalog/sidebar.php` واگذار می‌کند. آرشیو و جزئیات ناحیهٔ ابزارک و تنظیم مستقل بومی دارند؛ سایدبار بیرون ناحیهٔ نتایج AJAX است و در حالت خاموش/خالی wrapper ندارد.

**اصلاح صریح مالک همان روز:** منظور از «مثل وبلاگ» فقط تفکیک فایل نبود؛ سایدبار باید در آرشیو محصولات واقعاً نمایش داده شود. در نصب مشترک، سایدبار آرشیو محصول با جایگاه end و عرض ۳۲۰px مانند آرشیو وبلاگ فعال شد. سه نمونهٔ مستقل از ابزارک بومی `rdct-catalog-section` برای جستجوی محصول، دسته‌های تودرتو با شمار محتوا، و تازه‌ترین محصولات تصویری تخصیص یافتند؛ ابزارک‌های وبلاگ کپی یا جابه‌جا نشدند و سایدبار جزئیات خودکار فعال نشد. این آماده‌سازی دادهٔ محلی بنا به درخواست مالک است، نه پیش‌فرض خودکار سایت‌های تازه.

ابزارک در `inc/catalog/widgets/archive.php` و markup بخش‌ها در `template-parts/catalog/sidebar/{search,categories,tags,recent}.php` است. با اصلاح بعدی مالک، فرم جستجو/برند/ویژگی/مرتب‌سازی به سایدبار منتقل و نمونهٔ بالای فهرست حذف شد؛ دستهٔ درختی، تگ و رفتار sticky بدون اسکرول داخلی در [مالک سایدبار](../../engineering/sidebars.md) نگهداری می‌شوند. `inc/catalog/archive.php` مقادیر فیلترِ زمینهٔ taxonomy را برای فرم و نتیجه یکسان می‌کند؛ `template-parts/content/catalog-results.php` و `catalog/archive/results-status.php` نتیجه/شمار/حذف فیلتر را از همان query مشترک می‌گیرند. CSS/JS اختصاصی فقط در نمای دارای سایدبار فعال و پُر enqueue می‌شوند؛ پایهٔ مشترک وبلاگ/محصول در `src/css/content/sidebar.css` و `src/js/content/sidebar.js` باقی است. مسیر استایل بعدی صفحه `src/css/pages/catalog/` و کارت/سایدبار `src/css/catalog/` است؛ پوشهٔ خالی لازم نیست.

بررسی محدود: lint دوازده فایل PHP، رندر وردپرس برای سایدبار start/end و خاموش/خالی، شش کارت، مرز AJAX و عنوان/معرفی/مشخصات جزئیات پاس شدند. خروجی main آرشیو/جزئیات و HTML fragment پس از حذف تفاوت فاصله‌ها با قبل یکسان بود؛ HTTP دسته و فیلتر ترکیبی نیز بررسی شدند. CSS/JS تغییر نکرد؛ build یا ZIP تازه لازم نبود. پذیرش بصری مرورگر و ویرایشگر Elementor انجام نشد؛ طراحی نهایی محصول همچنان منتظر دستور بعدی مالک است.

شواهد پس از اصلاح نمایش: build، lint شش PHP و شش بررسی کوتاه درخواست آرشیو/sticky پاس شدند؛ GET آرشیو شامل یک سایدبار، جستجو، زیردسته‌ها، تازه‌ترین محصولات، فایل سبک منتخب و شش کارت بود. دستهٔ والد دو محصول و fragment ترکیبی برند/ویژگی یک محصول و بدون سایدبار برگرداند. ابزارک‌های سایر نواحی و تنظیمات نامرتبط حفظ شدند. بررسی بصری مرورگر انجام نشد؛ شواهد برابری خروجی بند قبل فقط مربوط به مرحلهٔ تفکیک فایل پیش از فعال‌کردن سایدبار است.

## قطعه‌های کدنویسی‌شدهٔ قابل استفاده مجدد — CONFIRMED، ۲۰۲۶-۱۱-۰۱

با تأیید مالک، طراحی اختصاصی پنل/آیتم‌ها در Child کدنویسی می‌شود؛ مسیر Elementor Template برای طراحی المنتوری باقی می‌ماند. سیستم بلوک‌ساز یا CPT جدید لازم نیست. بلوک‌های استاندارد وردپرس مسیر قدیمیِ محتوای ساده‌اند، نه الزام طراحی اختصاصی. مقایسهٔ WoodMart نشان داد HTML Block ممکن است خودش محتوای Elementor داشته باشد؛ نام HTML Block تضمین حذف موتور Elementor یا سرعت بیشتر نیست.

رجیستری کوچک `radmanct/inc/custom-content.php` فقط تعریف‌های کد مورد اعتماد را نگه می‌دارد. هر تعریف عنوان، callback رندر و callback اختیاری assets دارد؛ ثبت روی `after_setup_theme` بعد از راه‌اندازی Child انجام شود. شناسهٔ پایدار شامل حروف کوچک لاتین، عدد و خط تیره، با شروع حرف و حداکثر ۸۰ کاراکتر است. شناسهٔ تکراری تعریف اول را بازنویسی نمی‌کند. هیچ مسیر فایل، PHP/JS یا callback از تنظیمات/درخواست HTTP اجرا نمی‌شود. تنظیمات فقط شناسه را ذخیره می‌کنند؛ شناسهٔ مفقود خروجی خالی دارد و از دادهٔ ذخیره‌شده حذف نمی‌شود. هر رندر `instance_id` مستقل برای ID/ARIA دریافت می‌کند؛ حلقه و عمق بیش از ۸ مهار می‌شود و buffer/حالت فعال در خطا نیز آزاد می‌شوند. خروجی PHP مورد اعتماد escape خود را در template انجام می‌دهد؛ KSES نباید SVG یا markup معتبر کامپوننت را بعداً خراب کند.

نمونهٔ واقعی `site-navigation` در `radmanct-child/inc/content/navigation.php` ثبت شده و partial آن در `template-parts/content/navigation.php` است؛ CSS مستقل در `src/css/content/navigation.css` قرار دارد و JS بی‌مصرف ساخته نشده است. این طرح منوی primary موجود را مصرف می‌کند و خودکار جایگزین پنل فعلی سایت نمی‌شود. قالب، registry و Components موتور یا وابستگی Elementor را برای این مسیر فراخوانی نمی‌کنند.

```php
add_action( 'after_setup_theme', static function () {
    rdct_register_content( 'client-contact', array(
        'title' => __( 'Contact panel', 'radmanct-child' ),
        'render' => static function ( array $context ) {
            get_template_part( 'template-parts/content/contact', null, $context );
        },
        'assets' => static function () {
            // Enqueue only this design's built assets and selected shared components.
        },
    ) );
}, 15 );
```

قرارداد مصرف:

- در هدر/فوترساز، عنصر پنل: منبع `custom` و `panelCustomContent` شناسهٔ طرح؛ گزینهٔ طرح چایلد از metadata ثبت‌شده ساخته می‌شود. کنترل‌های Elementor منبع اختصاصی جدید را اضافه نمی‌کنند و Template فعلی خود را حفظ می‌کنند. callbackهای قبلی `rdct_panel($content, $options)` نیز باقی‌اند.
- مصرف مستقیم PHP: `echo rdct_render_content('client-contact', ['slot'=>'custom-page']);`؛ خروجی wrapper اجباری اضافه ندارد.
- کاروسل، آکاردئون، Curtain هر دو layout و آیتم Sticky Sections: کلید `custom_content` در آرایهٔ همان آیتم. عنوان‌ها و قاب‌های کامپوننت موجود حفظ می‌شوند؛ renderer جدید موازی ساخته نشده است.
- ستون ثابت Sticky Sections: `aside_custom_content` در options؛ Flip Box: `front_custom_content` و `back_custom_content` در options. این کلیدها مخصوص PHP هستند و field جدید در Classic/Atomic نمی‌سازند. callableهای موجود کاروسل/استیکی اولویت قبلی را حفظ می‌کنند؛ ارجاع صریح سفارشی بر متن/Template همان slot تقدم دارد.
- callback دارایی هر شناسه فقط یک‌بار در درخواست و هنگام مصرف اجرا می‌شود. پنل سازنده در مرحلهٔ enqueue آن را آماده می‌کند. برای قطعه‌های مستقیم صفحه، `rdct_prepare_content('client-contact')` را در enqueue همان صفحه فراخوانی کنید تا CSS پیش از head و بدون flash آماده باشد؛ رندر نیز fallback آماده‌سازی دارد. enqueue کامپوننت‌ها از requirements مشترک و URL موتورهای محلی استفاده کند؛ فایل‌های GSAP/Swiper/فونت کپی نشوند. late CSS مطابق امکانات loader موجود مسئولیت callback است؛ نمونهٔ Child آن را برای stylesheet خودش پوشش می‌دهد.

Template المنتور و wp_blockهای ذخیره‌شده مهاجرت/حذف نشدند. تأیید بصری و چرخهٔ واقعی ویرایش/Undo Elementor با قرارداد PHP یا build یکی نیست؛ WPML همچنان نیازمند بررسی جداگانه است. کد طرح می‌تواند محتوای زبان جاری را از APIهای وردپرس بگیرد؛ registry، سیستم ترجمه یا fallback خودکار جدید ایجاد نمی‌کند.

## قرارداد صفحهٔ سفارشی، دارایی و SEO — CONFIRMED، ۲۰۲۶-۱۰-۳۰

- تنظیمات قالب پیش‌فرض مشترک خانواده/رنگ/وزن/اندازه/ارتفاع خط و فاصله‌ها هستند. CSS/JS یا مقادیر یکسان برای هر صفحه دوباره تولید نشوند. در صورت درخواست مالک، استایل مستقل یک صفحه/سکشن/عنصر فقط در همان scope و از طریق token یا گزینهٔ موجود کامپوننت override شود؛ مقدار جهانی عوض نشود و !important/کنترل یا موتور موازی ساخته نشود. این استثنا باید عمدی و قابل حذف باشد؛ طراحی سفارشی نباید تنظیمات را بی‌دلیل قطع کند.
- هر صفحهٔ متفاوت template/partial و entry CSS/JS متعلق به خودش را دارد؛ بخش بزرگ می‌تواند زیرپوشهٔ همان صفحه داشته باشد. CSS/JS صفحهٔ دیگر روی آن enqueue نشود. فایل JS خالی برای تقارن پوشه لازم نیست؛ base فقط قراردادهای واقعاً مشترک را نگه دارد. [مالک پوشه و بارگذاری](../../engineering/assets.md).
- مصرف کامپوننت از PHP همچنان renderer و requirements مشترک را استفاده کند؛ CSS/JS کامپوننت، preset و قابلیت انتخابی فقط هنگام مصرف همان مورد و یک بار بارگذاری شود. موتور GSAP/Swiper/فونت در Child کپی یا دوباره bundle نشود؛ entry واحد و lazy موجود مصرف شود. فایل‌های Elementor صرفاً به دلیل نصب افزونه وارد صفحهٔ PHP نشوند؛ محتوای Elementor در بلوک/هدر/فوترِ واقعاً مصرف‌شده استثنای معتبر است، پس dequeue سراسری یا تطبیق کور نام فایل ممنوع است.
- registry فونت، گروه خط مصرفی و خانواده‌های مؤثر منبع واحدند. انتخاب فونت مکمل به‌تنهایی مجوز اعلان/دریافت آن در صفحه نیست؛ گروه دوم فقط با زبان واقعی یا انتخاب صریحِ محتوای ترکیبی مصرف شود. دارایی مدیریت/آیکون با فونت محتوای سایت یکی نیست. [مالک تایپوگرافی](../../engineering/typography.md).
- صفحهٔ سفارشی همچنان صفحه/آرشیو/نوشتهٔ واقعی WordPress است: Loop، get_header/get_footer، wp_head/wp_footer، title-tag، عنوان/وضعیت/رمز/صفحه‌بندی و hookهای افزونهٔ SEO حفظ شوند. Title سند، Robots، Canonical و متادیتای افزونه در templateها دستی و تکراری چاپ نشوند؛ عنوان نمایشی H1 مستقل از Title سند است. این قاعده برای خانه، وبلاگ، نمونه‌کار، کاتالوگ و جزئیات آن‌ها یکسان است. تعیین index/noindex به تنظیم واقعی سایت/محتوا و افزونهٔ SEO تعلق دارد؛ محیط لوکال برای حل ظاهر به index تغییر نکند. Canonical آرشیو، description، Open Graph و schema پیشرفته به مالک SEO تعلق دارند و نبود افزونه مجوز ادعای تکمیل آن‌ها نیست. [قرارداد صفحه](../../scenarios/pages.md).
- DOM کمینه با حفظ hookهای کامپوننت/دسترس‌پذیری؛ wrapper لازم برای Grid، viewport تصویر/لایهٔ مدار یا pin-spacer ساخته‌شدهٔ GSAP با div تزئینی بی‌کار یکسان نیست. بررسی محدود باید هم خروجی واقعی و هم import graph را ببیند؛ build یا نبود لینک در HTML، اثبات Network/سرعت همهٔ تعامل‌ها نیست. [مالک markup](../../engineering/markup-css.md).

بازبینی فعلی خانه: خروجی عمومی فقط دو @font-face مؤثر Peyda و Hafez محلی، بدون اعلان تکراری و بدون فونت لاتین/شبکه‌ای داشت؛ لینک stylesheet/script المنتور در HTML نبود. entry تصویر متحرک فقط برای خانهٔ دارای بستهٔ رسانه enqueue می‌شود و GSAP همان URL مشترک والد است. Title و H1 و Canonical هرکدام یک بار و Robots برابر noindex,nofollow با blog_public=0 بود. CSS خدمات از selector چهارخانواده‌ای هم‌معنی و اندازه/ارتفاع خط/فاصلهٔ پوشانده‌شده پاک شد؛ تصویر/مدار/سرعت/DOM تغییر نکردند. بررسی HTTP جزئیات نوشته و آرشیو محصول/نمونه‌کار هم Title و H1 و Robots تکی و بدون لینک دارایی Elementor داشت. Canonical دو آرشیو در حالت native بدون افزونه موجود نبود؛ جزئیات نمونه‌کار/محصول به دلیل نبود مورد منتشرشده، و آرشیو وبلاگ به دلیل نبود برگهٔ نوشته‌های تخصیص‌یافته بررسی زنده نشدند. مرورگر/Network و افزونهٔ SEO واقعی در این مرحله بررسی نشده‌اند.

## ارث‌بری تنظیمات در طراحی سفارشی — CONFIRMED، ۲۰۲۶-۱۰-۳۰

بازبینی ۲۰۲۶-۱۱-۰۲: خانه و قالب custom-page خانواده/اندازه/وزن/ارتفاع خط را از tokenهای مشترک می‌گیرند؛ fallback طراحی، موتور یا تنظیمات جداگانهٔ فونت نیست. HTTP خانه دو font-face محلی و بدون inline profile اختصاصی داشت؛ مشاهدهٔ بصری انجام نشد. نمونهٔ منتشرشدهٔ custom-page در سایت فعلی وجود نداشت و مسیر آن از سورس بررسی شد. **OPEN:** رنگ هیروی فعلی از پالت روشنِ طراحی تیره می‌آید و بعضی قواعد آن انتخاب رنگ عمومی را می‌پوشانند؛ متن عمومیِ تیره روی پس‌زمینهٔ تیره خوانایی ندارد. یکسان‌سازی این رنگ‌ها با تنظیمات عمومی بدون تعیین سیاست بخش تیره انجام نشد؛ این مورد به معنی تکمیل سراسری قرارداد رنگ زیر نیست.

تمام طراحی‌های سفارشی فعلی و آیندهٔ مشتری، خانواده، رنگ، وزن، اندازهٔ واکنش‌گرا و ارتفاع خط متن/تیتر/لینک و فاصلهٔ کناری صفحه را از تنظیمات مشترک قالب مصرف می‌کنند. رنگ اصلیِ تأکیدها، آیکون‌ها، خطوط و دکمه‌های طرح نیز از brand_color می‌آید؛ HEX موازی برای هر قسمت ساخته نشود. مقدار طراحی در CSS فقط fallbackِ تنظیم خالی است. تغییر مستقل یک قسمت به درخواست صریح مالک انجام می‌شود؛ افزودن صفحهٔ سفارشی مجوز قطع ارث‌بری نیست. رنگ داخل فایل تصویر ثابت است و این قرارداد به معنی رنگ‌آمیزی خودکار عکس نیست. مرز محتوای Elementor و رابط مدیریت حفظ می‌شود. [نقش‌ها و کنترل‌ها](../../engineering/typography.md).

آرشیوهای وبلاگ/محصول marker و resolver پاسخ AJAX والد را نگه می‌دارند؛ کارت Child در ورود اولیه و fragment مصرف می‌شود. آرشیو نمونه‌کار query/pagination بومی خودش را دارد. جزئیات محصول تصویر/گالری، خلاصه، کد/taxonomy، قیمت یا تماس، محتوای کامل و مشخصات را از داده و helperهای موجود می‌گیرد؛ جزئیات نمونه‌کار تصویر/گالری، خلاصه، کد/دسته و محتوا را می‌گیرد. محافظ رمز، صفحه‌بندی محتوای چندصفحه‌ای و لینک بازگشت حفظ‌اند. لایهٔ مشتری ثبت داده، زبان، query یا منطق متادیتا را تکثیر نمی‌کند. هدر/فوتر هم از پوسته و سازندهٔ والد می‌آیند.

PHP lint نه فایل و قراردادهای محدود renderer، فیلتر کاتالوگ، متادیتا، آرشیو و WPML محتوا بررسی شدند؛ نصب/نمایش واقعی و دیزاین نهایی هنوز پذیرش نشده‌اند. امکانات پیشرفتهٔ دادهٔ مشتری مانند PDF/فیلتر بازه‌ای طبق [سناریوی محتوا](../../scenarios/content.md) نهایی نشده‌اند؛ آماده‌بودن طرح پایه ادعای ساخته‌شدن آن‌ها نیست.

## برگهٔ مستقل هر زبان با WPML

**تکمیل تنظیمات برگه — ۲۰۲۶-۱۰-۲۵:** `_rdct_page_layout` و `_radman_page_effects` در XML قالب مانند انتخاب هدر/فوتر و رنگ محتوا `copy-once` دارند. ترجمهٔ تازه تنظیمات آغازین را می‌گیرد و سپس عرض/فاصله و افکت هر زبان از ویرایش همان برگه مستقل قابل تغییر است؛ ذخیرهٔ زبان مبدأ نباید آن‌ها را به‌صورت دائمی overwrite کند. انتخاب template و دادهٔ خود Elementor همچنان به قراردادهای بومی WPML واگذار می‌شوند. این تغییر schema یا endpoint، اسکن زبان‌ها و JS/runtime تازه ندارد؛ تنظیمات صریح مدیر در WPML و چرخهٔ واقعی ترجمه هنوز باید در نصب مقصد بررسی شوند. رفتار Copy once بر اساس [مستند رسمی WPML](https://wpml.org/documentation/getting-started-guide/translating-custom-fields/) با Context7 و الگوی محدود `copy-once` در XML WoodMart بررسی شد؛ این موضوع تکمیل ATE دادهٔ تو‌در‌توی مشتری نیست.

برای سایت سفارشی نیز زبان دوم از بخش Languages همان برگه در WPML افزوده یا به برگهٔ ترجمهٔ موجود متصل می‌شود؛ هر نسخه رکورد واقعی خودش با عنوان، محتوا و تصویر مستقل دارد. template مشتری دادهٔ برگهٔ جاری را می‌خواند؛ قالب مشترک قابل استفاده است و نیازی به کپی PHP برای هر زبان نیست. برای طراحی مستقل از ویرایشگر WordPress/حالت ویرایش مستقل ترجمه استفاده شود؛ Duplicate متصل با sync فعال، استقلال محتوا را تضمین نمی‌کند.

اگر فایل template دو زبان متفاوت است، گزینهٔ بومی WPML برای همگام‌سازی page template باید توسط مدیر غیرفعال شود؛ Theme این تنظیم سراسری را خودکار تغییر نمی‌دهد و `_wp_page_template` را override نمی‌کند. انتخاب هدر/فوتر در بار اول copy-once است و resolver سازنده نسخهٔ متصل زبان جاری را پیدا می‌کند؛ [قرارداد سازنده](../../engineering/builder.md). محتوا و منابع همهٔ زبان‌ها هم‌زمان بارگذاری نمی‌شوند. فرم ویرایش سکشن‌های اختصاصی جدید فقط پس از تعریف همان طراحی ساخته می‌شود؛ ترجمهٔ تو‌در‌توی تمام فیلدهای `_radman_content_data` در ATE هنوز آماده ادعا نمی‌شود. افزودن ACF یا سیستم زبان اختصاصی لازم نیست.

پایه پیاده‌سازی شده در `radmanct-child/`: یک Child Theme استاندارد و اختیاری. والد به‌تنهایی کار می‌کند؛ این نمونه را برای هر پروژه کپی/نام‌گذاری کنید و همه طرح‌های مشتریان را به والد اضافه نکنید.

| تغییر | محل نمونه |
|---|---|
| پیش‌فرض رنگ برند و عرض مشتری | فیلتر `radmanct/settings/defaults` در `radmanct-child/functions.php`؛ انتخاب ذخیره‌شدهٔ مدیر اولویت دارد |
| radius و استایل مشترک مشتری | `radmanct-child/src/css/client.css` |
| استایل فقط یک صفحه | `radmanct-child/src/css/pages/custom-page.css` |
| Template قابل انتخاب برگه | `radmanct-child/templates/custom-page.php` |
| HTML/PHP همان صفحه | `radmanct-child/template-parts/client/page.php` |
| شرط بارگذاری فایل مشتری | `radmanct-child/functions.php` |
| ورودی فایل جدید در Build | target مربوط مشتری در `tools/build.mjs` |
| بازنویسی هدر/فوتر یا بخش موجود | همان مسیر `template-parts/` والد داخل Child |

## روند تغییر

### ورودی‌های طرح محتوا — Theme 0.1.25

طرح اولیهٔ مالک هنوز دریافت نشده است؛ فایل‌های زیر فعلاً ظاهر پایهٔ موجود را نگه می‌دارند. طبق درخواست جدید، شش view و سه card در Child آماده‌اند؛ سایر بخش‌های والد تنها در صورت نیاز همان دیزاین override شوند و کل قالب کپی نشود.

پوستهٔ صفحه همیشه آماده است: `header.php` سند HTML، `wp_head`، بدنه و main با چیدمان سراسری را باز می‌کند؛ `template-parts/site/header.php` هدر انتخاب‌شدهٔ سازنده را نمایش می‌دهد. `footer.php` main را می‌بندد و فوتر انتخاب‌شده، `wp_footer` و پایان سند را می‌نویسد. فایل طراحی محتوا فقط داخل این پوسته قرار می‌گیرد. تغییر طرح وبلاگ/محصول/نمونه‌کار به تغییر هدر/فوتر، ایجاد صفحهٔ دستی برای هر رکورد یا بازنویسی ثبت داده نیاز ندارد. جزئیات از رکورد جاری و آرشیو از query صفحه‌بندی‌شدهٔ WordPress می‌آیند.

برگهٔ سفارشی پیش‌فرض تنظیم مجدد عرض/فاصله ندارد؛ همان تنظیمات قالب را می‌خواند. متاباکس اختیاری چیدمان برگه فقط برای استثنای آگاهانه است و پیش‌فرض ارث‌بری دارد؛ نباید wrapper یا padding دوم داخل فایل طراحی بسازد. [اولویت و حدود چیدمان](../../engineering/layout.md).

| صفحه | مسیر در والد و مسیر متناظر override در Child |
|---|---|
| آرشیو وبلاگ | `template-parts/blog/archive.php` |
| جزئیات نوشته | `template-parts/blog/single.php` |
| آرشیو محصولات | `template-parts/catalog/archive.php` |
| جزئیات محصول | `template-parts/catalog/single.php` |
| آرشیو نمونه‌کار | `template-parts/portfolio/archive.php` |

کارت هر بخش در `template-parts/{blog,catalog,portfolio}/card.php` مستقل قابل override است. والد برای کارت‌ها و بدنهٔ مشترک محصول/نمونه‌کار از partialهای `content/` استفاده می‌کند. قالب‌های بالادستی header/footer و gate اختصاصی/Pro را مالک‌اند؛ داخل این شش partial دوباره `get_header()`/`get_footer()` یا تشخیص renderer اضافه نشود. آرشیو taxonomy نیز همان طرح بخش خودش را مصرف می‌کند. برای AJAX وبلاگ/محصول، ناحیهٔ `data-rdct-archive-view` و قرارداد [آرشیو AJAX](../../engineering/archive-ajax.md) حفظ شود؛ تغییر ساختار نتایج از `content/blog-results.php` یا `content/catalog-results.php` انجام شود تا ورود اولیه و پاسخ fragment یکسان باشند. کارت‌های جدید در هر دو مسیر مصرف می‌شوند.

CSS پایه از ورودی‌های موجود `listing.css`/`blog.css`، `catalog.css`/`catalog-single.css` و `portfolio.css`/`portfolio-single.css` می‌آید. برای طراحی مشتری، ورودی CSS فقط در Child و فقط روی scope/view مرتبط اضافه و با manifest مینیفای‌شده بارگذاری شود؛ `RadmanCT\Renderers\uses_elementor()` مانع تحمیل طراحی اختصاصی روی طرح Pro منطبق باشد. فایل خالی، stylesheet عمومی برای همهٔ بخش‌ها یا asset شش طرحِ استفاده‌نشده از پیش ساخته نشود. query، متادیتا، قیمت/تماس و گالری در موتور فعلی Theme/Content باقی بمانند؛ guard رمز محتوا هنگام بازنویسی جزئیات حفظ شود.

1. هر دو قالب در `wp-content/themes/` نصب و Child فعال شود.
2. در ویرایش برگه Template «صفحهٔ اختصاصی مشتری / Custom client page» انتخاب شود؛ عنوان، تصویر شاخص و محتوای Gutenberg از همان برگه می‌آیند.
3. رنگ/عرض از پنل رادمان قابل انتخاب‌اند؛ پیش‌فرض هر مشتری با `radmanct/settings/defaults` تنظیم شود. برای استایل عمومی `client.css` و برای همین صفحه `custom-page.css` ویرایش شود. فایل صفحه فقط روی Template خودش enqueue می‌شود، نه وبلاگ یا برگه عادی.
4. پس از تغییر CSS/JS در ریشه `npm run build` اجرا شود؛ `dist/` مستقیم ویرایش نشود. PHP نیاز به build ندارد.
5. برگه‌های دارای ساختار یکسان همان template و اجزای مشترک را با دادهٔ متفاوت مصرف کنند. فقط برای چیدمان واقعاً متفاوت template/part تازه و فقط برای asset واقعاً اختصاصی entry و شرط enqueue اضافه شود؛ ساخت template و CSS مستقل برای تک‌تک برگه‌ها الزامی نیست.

## مرز Child و استفادهٔ مجدد — روشن‌سازی ۲۰۲۶-۱۰-۲۰

Child Theme شرط استفادهٔ بدون Elementor نیست؛ قالب والد به‌تنهایی صفحات PHP، Gutenberg، هدر/فوتر و اجزای عمومی را نمایش می‌دهد. Child جای طراحی و override مخصوص مشتری است تا به‌روزرسانی والد آن را بازنویسی نکند. قابلیت عمومی Radman CT باید در ماژول مربوط والد توسعه یابد، نه اینکه هر بار به Child منتقل یا در هر پروژه کپی شود. ثبت داده و منطق مستقل محتوا همچنان متعلق به Core است؛ فایل‌های طراحی مشتری جای آن نیستند.

Template صفحه ترکیب‌کنندهٔ چیدمان است: هدر/فوتر از `get_header()` و `get_footer()`، بخش تکراری از `get_template_part(..., ..., $args)` و اجزای عمومی از API مشترک والد فراخوانی شوند. نمونهٔ فعلی `templates/custom-page.php` فقط Loop و partial مشترک را متصل می‌کند و برای چندین برگه قابل انتخاب است؛ عنوان، تصویر و محتوا از همان برگه می‌آیند. اجزای موجود مثل `rdct_icon()`، `rdct_text_reveal()` و `rdct_motion_attributes()` از PHP سفارشی در دسترس‌اند؛ renderer و lifecycle آن‌ها با اتصال اختیاری Elementor مشترک است. این به معنی ساخته‌شدن همهٔ کامپوننت‌های آینده نیست. [مالک اجزای نمایشی و دارایی‌ها](../../engineering/components.md).

متن و تصویر عمومی در WordPress و دادهٔ ساختاریافته در فیلد ثبت‌شدهٔ متناسب نگهداری شوند؛ برای تغییر محتوا PHP کپی نشود. نمونهٔ Child فعلی عنوان/تصویر شاخص/محتوای اصلی را دارد؛ فرم جامع ویرایش همهٔ سکشن‌های طراحی اختصاصی پیاده نشده است. کپی کل template والد برای تغییر کوچک، تکرار CSS/JS کامپوننت و اسکن همهٔ صفحات برای کشف استفاده الگوی مطلوب نیستند. CSS/JS اختصاصی فقط در محل مصرف بارگذاری شوند و overrideهای لازم هنگام تغییر قرارداد والد بازبینی شوند.

این تفکیک با [راهنمای رسمی Child Theme](https://developer.wordpress.org/themes/advanced-topics/child-themes/) و [اجزای قابل استفادهٔ مجدد](https://developer.wordpress.org/reference/functions/get_template_part/) و Context7 تطبیق داده شد. وردپرس Child را ابزار جداسازی تغییرات می‌داند، نه الزام معماری همهٔ سایت‌ها؛ برای تغییرات بسیار گسترده، ارزیابی یک قالب مستقل هم مطرح است. در پروژهٔ فعلی، والد خود Radman CT است و توسعهٔ امکانات مشترک در همان والد ادامه می‌یابد.

`get_template_part` فایل Child را پیش از والد پیدا می‌کند؛ برای تغییر markup، مسیر متناظر در Child ساخته شود. سلسله‌مراتب استاندارد WordPress و Template اختصاصی قابل استفاده‌اند؛ انتخاب‌گر چندین طرح آماده در والد نداریم.

نام پوشه Child قابل تغییر است، ولی `Template: radmanct` در header آن باید نام والد باشد؛ کلید target در Build نیز با پوشه Child هماهنگ شود. به‌روزرسانی والد Child را بازنویسی نمی‌کند؛ overrideها هنگام تغییر قرارداد والد نیاز به بازبینی دارند.

## فونت و محدودیت فعلی

نمونهٔ Child اکنون `templates/custom-page.php` را در فیلتر `radmanct/layout/custom_templates` ثبت می‌کند: خروجی PHP مستقل و main مدیریت‌شده با عرض/gutter/فاصلهٔ تنظیمات محتوا می‌گیرد. padding قبلی داخل article حذف شد تا فاصله دوبار اعمال نشود؛ CSS چیدمان اختصاصی صفحه همچنان شرطی است. همهٔ برگه‌های استفاده‌کنندهٔ این template همین رفتار را با دادهٔ خودشان می‌گیرند. ثبت template جدید در این فهرست به معنی انتخاب صریح مسیر PHP و پذیرش چیدمان محتواست؛ صرف افزودن نام، فایل template ایجاد نمی‌کند.

Templateهای ثبت‌نشده به‌صورت پیش‌فرض از مدیریت خودکار main خارج‌اند؛ برای طراحی آزاد می‌توان wrapper اختصاصی با `rdct_content_layout_attributes('content')` و فرزند مستقیم `.rdct-ctr` ساخت یا از opt-in قبلی استفاده کرد. scopeهای آرشیو/جزئیات نیز موجودند. opt-in والد و wrapper دستی را روی یک ناحیه با هم مصرف نکنید؛ [قرارداد چیدمان](../../engineering/layout.md).

برای تغییر فقط محصول یا نمونه‌کار، ورودی‌های مستقل `single-radman_product.php`، `archive-radman_product.php`، `single-radman_portfolio.php` و `archive-radman_portfolio.php` در Child قابل override هستند؛ CSS مستقل هر بخش نیز می‌تواند شرطی از Child بیاید. انتخاب روش نمایش در «طراحی محتوا» است؛ طراحی اختصاصی مشتری باید پیش از markup خودش قرارداد `RadmanCT\Renderers\render()` را حفظ کند تا انتخاب Pro همچنان عمل کند. [قرارداد انتخاب](../../engineering/renderers.md).

انتخاب فونت در پنل رادمان انجام می‌شود؛ فیلتر `radmanct/typography/fonts` هم برای override صریح کلیدهای `persian` و `latin` با گروه معتبر موجود است. پیش‌فرض IRANSansX و GT Walsheim حفظ شده؛ فهرست کامل و روش افزودن خانواده در [قرارداد فونت](../../engineering/typography.md) است. برای تغییر صرفِ پیش‌فرض بدون حذف اختیار مدیر، `radmanct/settings/defaults` مناسب است.

Template تمام‌عرض والد مسیر مستقیم `the_content()` دارد؛ برای صفحهٔ Elementor، Template اختصاصی «رادمان — المنتور با هدر و فوتر» هم موجود است. اتصال اولیه و بررسی محدود PHP/DB انجام شده؛ ماتریس Pro و فونت مرورگر هنوز کامل نیست. [قرارداد Elementor](../../engineering/elementor.md). نمونه Child طرح نهایی مشتری یا محدودیت طراحی نیست.
