# Radman CT theme work

## Start with the affected contract

Read root AGENTS and `radman-doc/product/essentials.md` once; use AGENTS to find only the affected scenario and engineering owner. Read confirmed behavior and remaining gaps before editing. User corrections override older drafts; proposals and archived references are not approval. Follow [architecture](../../engineering/architecture.md), [naming](../../engineering/naming.md) and [asset ownership](../../engineering/assets.md); preserve persisted identifiers.

Continued theme, builder and independent content-module work is authorized within confirmed scenarios. Do not add commerce, deferred forms/submissions, licensing, deployment or publishing. Keep PHP rendering independent of Elementor and development tooling; React belongs to administration. Keep Theme, Content, Components and MCP ownership distinct.

## Before implementation

- Inspect nearby source and current manifests. Search affected headings/files before reading; do not preload every document, theme or archive.
- Find the matching supplied reference through [reference-map](../../research/reference-map.md). Inspect that subsystem only; adapt behavior without importing a third-party framework or changing reference files. Hub Classic behavior does not prove Atomic support.
- For library/API/version questions, resolve then query Context7 and compare with the actual supplied version. Do not invent APIs, private hooks or build commands.
- Record important new decisions in their canonical owner during the same task. Link remaining work from the roadmap; avoid parallel reports.
- For component changes, apply the folder and asset-isolation contract in `radman-doc/engineering/assets.md`: reuse a small shared base, keep independent presets/behaviors separate, and inspect changed requirements/static imports for unrelated eager assets. Preserve stored IDs and public PHP helpers during internal file moves; no empty modules or duplicate engines for symmetry.

## Elementor control gate

Keep V3/Classic reliable and available while developing Atomic in parallel against supported capabilities. A stable Atomic release does not imply complete feature coverage. Apply the editor-native appearance rule to popups, inputs, buttons, switches, colors and typography; WordPress Admin or Radman panel styling is not a substitute for an available Elementor control or shell. Record a missing native capability before using a custom exception; see the canonical scenario below.

Follow [native-control requirements](../../scenarios/components.md#elementor-native-controls) and the [control inventory](../../engineering/components.md) for every existing or future widget. Before adding a field, identify its native Classic/Atomic control, supported target API, stored value and shared renderer mapping. Check real reference field types, groups, conditions, states and responsive behavior.

Use native controls or a suitable composition first. Distinguish plain text from editable HTML and attachment IDs from native image values. Do not rebuild an available editor, uploader, input, checkbox, dropdown or color picker. A legacy storage shape justifies a value adapter only when needed, not another UI. Assess backward-compatible reads before changing storage; preserve control/widget IDs, history metadata and existing responsive/Global/Dynamic behavior. Do not add dependencies on private or unstable editor APIs.

For a necessary exception, record the missing native capability and reason in the inventory. Reassess existing icon/table/responsive/motion exceptions instead of copying them. Use native theme/spacing/focus/disabled/error behavior; scope essential CSS and load control assets only in the editor. Registration, a native component import or a successful build is not visual acceptance.

## Verify and finish

During continued development, keep package versions unchanged and do not create/rebuild ZIPs until the user explicitly asks to prepare packages. Build source only when needed for the changed code; do not repeat packaging as routine progress.

Use focused checks appropriate to changed behavior: build, asset contracts and relevant PHP lint by default. Do not repeatedly run long suites, runtime environments or performance scans; ask before a lengthy check. Do not open Chrome or perform browser visual checks unless requested. Keep changes local; no automatic stage/commit/push, CI, release or deployment.

Compare the result with affected requirements. Update actual evidence in [foundation](../../implementation/foundation.md) and unmet items in the existing owner/roadmap. Report what changed, the checks that actually ran and remaining acceptance briefly. Distinguish source review, stub/native-schema checks, real WordPress/editor operation and measured performance. For documentation-only work, use the documentation workflow without app builds or runtime edits.
