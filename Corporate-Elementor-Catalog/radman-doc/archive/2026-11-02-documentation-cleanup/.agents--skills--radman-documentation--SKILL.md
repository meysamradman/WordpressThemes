# Radman CT documentation

## Choose one owner

Follow root AGENTS; read essentials once and open only the affected owner. Behavior belongs in `radman-doc/scenarios/`, technical contracts in `engineering/`, current state/roadmap in `product/`, actual checks in `implementation/`, reference evidence in `research/`, and superseded material in `archive/`. Repeatable agent procedures belong in `.agents/skills/`.

Use [naming](../../engineering/naming.md) and [asset ownership](../../engineering/assets.md) when relevant. Do not create duplicate root reports, a second rule catalog or extra documents for facts that already have an owner.

## Update decisions and rules

1. Record explicit user decisions and corrections proactively during the same task. Preserve CONFIRMED, PROPOSED, OPEN and DEFERRED; discussion does not authorize implementation.
2. Search the existing requirement and correct contradictory current wording in place. Preserve useful requirements and historical evidence; archives never override current decisions.
3. Keep product detail in its canonical document and link from related owners. Skills contain short decision gates and workflow, not copied product specifications or implementation history. Update AGENTS/index routing only if discovery would otherwise fail.
4. When the user supplies a document or screenshot, extract applicable requirements into the owner, retain unresolved questions and distinguish requested appearance from observed behavior. Do not copy the whole input into a redundant document or treat every example as new scope.
5. For Elementor UI rules, maintain the [native-control scenario](../../scenarios/components.md#elementor-native-controls) and [technical control inventory](../../engineering/components.md). Preserve Classic/Atomic distinctions and PHP independence; record justified exceptions, compatibility gaps and manual acceptance separately.
6. Distinguish recorded, implemented, checked and still pending. Keep detailed execution evidence out of scenario rules; update existing roadmap links rather than duplicating reports.

## Validate only the documentation change

Check local links, routing, skill frontmatter and UTF-8 in changed files. Use UTF-8-safe edits for Persian; check replacement characters and accidental repeated question marks. Validate changed skills with the available skill validator when applicable.

Do not run app builds/tests/servers, browse framework docs or inspect reference themes for a documentation-only change unless an unresolved technical question requires it. Report the canonical files updated and any actual unresolved decision briefly.
