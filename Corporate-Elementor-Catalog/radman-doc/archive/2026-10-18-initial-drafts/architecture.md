# معماری پیشنهادی رادمان

> **آرشیو تاریخی؛ جایگزین‌شده:** این متن مرجع تصمیم جاری نیست. تصمیم قطعی ۲۰۲۶-۱۰-۱۸ در [معماری نهایی](../../engineering/architecture.md) بر تمام وضعیت‌ها و پیشنهادهای این فایل مقدم است. متن قدیمی فقط برای سابقه حفظ شده است.

> **نیازمند بازطراحی:** پیشنهاد Core Plugin و محدودکردن React به مدیریت، با توضیح جدید مالک محصول کنار گذاشته شد. این متن سابقه پیشنهاد قبلی است؛ جهت فعلی در [اصلاح معماری](frontend-direction.md) ثبت شده و هنوز معماری جایگزین نهایی نشده است.

نسخه: `0.2.0-draft` — تصمیم‌های فنی این سند `PROPOSED` هستند.

## انتخاب نوع قالب

| گزینه | مزیت برای رادمان | هزینه و محدودیت |
|---|---|---|
| Classic/Hybrid + `theme.json` | قالب‌های PHP و کنترل مستقیم خروجی سازنده اختصاصی؛ ویرایش محتوای برگه با بلوک | ساخت و نگهداری پنل سازنده بر عهده ماست؛ Site Editor کامل ارائه نمی‌شود |
| Block Theme + Site Editor | استفاده از ویرایشگر، قالب‌ها و اجزای استاندارد وردپرس؛ کد مدیریت اختصاصی کمتر | تجربه اختصاصی ردیف/جزء و قواعد تخصیص مدنظر باید در نمونه واقعی ارزیابی شود؛ افزودن سازنده دوم پیچیدگی دارد |

با توجه به انتخاب صریح سازنده اختصاصی، پیشنهاد فعلی **Classic/Hybrid همراه `theme.json`** است. این پیشنهاد به معنی سریع‌تر بودن ذاتی قالب کلاسیک نیست؛ هر دو مسیر می‌توانند HTML سمت سرور تولید کنند. معیار انتخاب، تجربه ویرایش و هزینه نگهداری است.

قبل از توسعه کامل سازنده، یک نمونه کوچک باید قرارداد ذخیره، رندر و بارگذاری فایل‌ها را اثبات کند. `theme.json` به‌تنهایی قالب کلاسیک را به Block Theme تبدیل نمی‌کند.

## مرز مسئولیت‌ها

| مالک | مسئولیت | خارج از مسئولیت |
|---|---|---|
| `radman`، قالب | PHP templates، طراحی، tokens، ظاهر بلوک‌ها، هدر/فوترساز و رندر آن | مالکیت محصول کاتالوگی، درخواست مشتری و منطق فروش |
| `radman-core`، افزونه پیشنهادی | نوع محتوا، دسته‌ها، مشخصات، گالری و بروشور کاتالوگ؛ بلوک‌های دارای منطق داده مستقل | قالب عمومی سایت و پنل سازنده ظاهری |
| ادغام‌های اختیاری | اتصال محدود به افزونه منتخب فرم، SEO، Elementor یا WooCommerce | بازسازی API داخلی آن افزونه‌ها |

قالب باید بدون Core برای برگه و وبلاگ کار کند. فعال‌بودن کاتالوگ به Core نیاز دارد. با تعویض قالب و فعال‌ماندن Core، داده‌ها و مدیریت باقی می‌مانند؛ ظاهر اختصاصی رادمان منتقل نمی‌شود. غیرفعال‌کردن Core رکوردها را حذف نمی‌کند، اما ثبت نوع محتوا و مدیریت آن دیگر فعال نیست.

سازنده هدر/فوتر فعلاً در قالب پیشنهاد می‌شود چون مسئول ظاهر است. اگر بعداً انتقال سازنده به قالب‌های دیگر لازم شد، خروج آن به افزونه مستقل تصمیم معماری جدا می‌خواهد. از روز اول یک framework عمومی چندمحصولی نسازیم.

## جریان رندر و فایل‌ها

1. در راه‌اندازی، فقط قابلیت‌های فعال ثبت شوند؛ داده‌های صفحه جاری با API استاندارد وردپرس خوانده شوند.
2. قبل از چاپ head، هدر/فوتر مؤثر صفحه انتخاب و وابستگی‌های فایل آن مشخص شوند.
3. Rendererهای PHP فقط داده معتبر را به HTML معنایی تبدیل کنند.
4. فایل‌های عمومی با API enqueue وردپرس و handle مشخص ثبت شوند؛ فایل‌های مدیریت فقط روی صفحه مدیریت مربوط بارگذاری شوند.
5. استایل سازنده هنگام ذخیره موفق تولید/کش شود؛ کلید شامل نسخه renderer، نسخه schema و hash داده و tokens باشد. تغییر هر وابستگی کش را باطل کند.
6. اگر نوشتن فایل CSS ممکن نبود، آخرین استایل معتبر یا CSS محدود و اعتبارسنجی‌شده inline ارائه شود؛ خروجی نباید خالی شود.
7. JS عمومی فقط برای تعامل لازم باشد. پنل React در مدیریت از وابستگی‌های رسمی وردپرس استفاده کند؛ React دوم bundle نشود.

برای بلوک‌های اختصاصی از `block.json` و تفکیک فایل ویرایشگر/نمایش استفاده شود. بارگذاری شرطی روی نسخه هدف وردپرس و در قالب کلاسیک عملاً آزمایش شود؛ وجود metadata به‌تنهایی اثبات رفتار همه صفحات نیست.

## قرارداد اولیه سازنده؛ هنوز schema نهایی نیست

| داده | پیشنهاد قرارداد |
|---|---|
| هویت | `schemaVersion`، شناسه layout، `kind: header/footer`، عنوان و revision |
| ساختار | `rows -> columns -> items` با شناسه پایدار؛ عمق و تعداد محدود |
| عنصر | `type` از registry مجاز + `props` با schema اختصاصی؛ بدون PHP/JS یا CSS دلخواه |
| واکنش‌گرایی | پایه mobile با override صریح tablet/desktop؛ یک سند برای هر layout، بدون کپی بی‌ارتباط داده‌ها |
| تخصیص | صفحه مشخص > نوع محتوا > پیش‌فرض سایت؛ در یک سطح تنها یک تخصیص معتبر، تعارض هنگام ذخیره رد شود |
| رفتار | Sticky/Overlay فقط برای هدر؛ اجزای سازگار هر ناحیه از registry مشخص شوند |
| ارجاع | شناسه رسانه و منو؛ export شامل شناسه محلی قابل‌اتکا بین سایت‌ها نیست و به remap نیاز دارد |
| خطا | نسخه ناشناخته بدون بازنویسی رد شود؛ عنصر ناشناخته هشدار مدیریتی و fallback امن داشته باشد |

پیشنهاد ذخیره: نوع محتوای خصوصی مخصوص layout در قالب، با schema در post meta ثبت‌شده و پیکربندی کوچک پیش‌فرض/تخصیص در گزینه non-autoload. Revision باید خود داده meta را هم پوشش دهد؛ صرف ساخت CPT کافی نیست. جزئیات پس از تعیین حداقل نسخه وردپرس آزمایش شوند.

ذخیره با revision موردانتظار انجام شود تا دو تب تغییر یکدیگر را بی‌خبر بازنویسی نکنند. پیش‌نمایش پیش‌نویس فقط با مجوز کاربر قابل‌دسترسی باشد و به کش عمومی نشت نکند. تغییر schema نیازمند export/backup، migration نسخه‌دار و حفظ داده قبلی هنگام شکست است.

## کاتالوگ

- شناسه پیشنهادی `radman_product` و دسته `radman_product_cat`؛ slug عمومی URL پس از توافق ثبت شود.
- اطلاعات عمومی در ستون‌های استاندارد پست؛ شناسه گالری/PDF و مشخصات محدود در meta معتبر. فیلترهای پرتکرار مانند دسته/برند در taxonomy مناسب قرار گیرند.
- قرارداد مشخصات پیشنهادی: `schemaVersion`، گروه، کلید پایدار، عنوان، نوع، واحد، مقدار و وضعیت قابل‌فیلتر. تغییر عنوان نباید کلید داده را عوض کند.
- شروع با مشخصات کنترل‌شده؛ فیلدساز عمومی تا روشن‌شدن نیاز ساخته نشود. برای مقادیر قابل‌فیلتر نوع و قواعد مقایسه از ابتدا روشن باشد.
- فعلاً جدول اختصاصی پیشنهاد نمی‌شود. نیاز به آن فقط با اندازه‌گیری Query و نیاز واقعی فیلتر بررسی شود.
- کاتالوگ به فروشگاه به‌طور خودکار تبدیل نمی‌شود. استعلام مشتری نیز دامنه داده و حریم خصوصی جدا دارد.

## طراحی و ابزار

- namespace پیشنهادی `Radman`، text domain قالب `radman`، prefix توابع `radman_`، CSS با `radman-` و مسیر REST احتمالی `radman/v1`.
- tokens از یک مرجع سازگار با `theme.json`؛ CSS با logical properties برای RTL/LTR. نام‌های Webtalik در سند اولیه نام فنی نهایی نیستند.
- PHP template hierarchy و hookهای استاندارد حفظ شوند؛ سفارشی‌سازی مشتری در child theme یا افزونه همان سایت قرار گیرد.
- در شروع ابزار ساخت واحد ترجیح دارد؛ اگر پنل React/بلوک لازم شد `@wordpress/scripts` کاندید است. Vite هم‌زمان بدون نیاز اثبات‌شده اضافه نشود.
- نسخه WordPress/PHP/Node، ابزار Drag & Drop و روش محیط محلی هنوز `OPEN` هستند؛ هیچ وابستگی یا lockfile ایجاد نشده است.

## منابع مستندات

در تاریخ این سند، Context7 برای Theme Handbook، Plugin Handbook و Gutenberg بررسی شد. گزاره‌های API از منابع وردپرس‌اند؛ انتخاب معماری بالا پیشنهاد مختص رادمان است.

- [انواع قالب در Handbook وردپرس](https://developer.wordpress.org/themes/core-concepts/theme-types/): تفاوت Classic و Block و نقش Site Editor؛ از نسخه Handbook در Context7 بررسی شد.
- [ثبت Custom Post Type](https://developer.wordpress.org/plugins/post-types/registering-custom-post-types/): توصیه قرارگیری نوع محتوا در افزونه برای انتقال‌پذیری داده.
- [Metadata بلوک‌ها](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-metadata/): تفکیک `editorScript`، `viewScript`، `style` و `viewStyle`؛ قابلیت‌ها تابع نسخه هدف‌اند.
