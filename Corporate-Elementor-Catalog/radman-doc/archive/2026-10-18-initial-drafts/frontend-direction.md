# جهت اصلاح‌شده رادمان و تحقیق React / Elementor

> **آرشیو تاریخی؛ جایگزین‌شده:** این متن مرجع تصمیم جاری نیست. تصمیم قطعی ۲۰۲۶-۱۰-۱۸ در [معماری نهایی](../../engineering/architecture.md) بر تمام وضعیت‌ها و پیشنهادهای این فایل مقدم است. متن قدیمی فقط برای سابقه حفظ شده است.

تاریخ: ۲۰۲۶-۱۰-۱۸ — وضعیت: نیازهای محصول تأییدشده، روش رندر هنوز باز است.

## خواسته صریح مالک محصول

- یک قالب رادمان بدون افزونه همراه اختصاصی؛ کاتالوگ و قابلیت‌های اختصاصی داخل قالب باشند.
- React در فرانت‌اند استفاده شود؛ محدودکردن آن به مدیریت پاسخ این خواسته نیست.
- پشتیبانی از Elementor وجود داشته باشد.
- سازنده اختصاصی هدر/فوتر جدا از Elementor باشد.
- سرعت و حذف کد غیرضروری هدف اصلی‌اند.

با توجه به درخواست پشتیبانی Elementor، «بدون افزونه» در اینجا به معنی نداشتن افزونه همراه رادمان تفسیر می‌شود؛ استفاده اختیاری از خود Elementor به نصب افزونه Elementor نیاز دارد.

## تطبیق با سند ورودی

سند اولیه خوانده شده، اما با توضیح جدید مالک محصول تفاوت دارد:

- بخش ۳.۲ و بخش ۶، Core Plugin را پیشنهاد می‌کنند.
- بخش ۳.۳، صفحات عمومی را PHP/HTML و React را عمدتاً برای مدیریت و بخش‌های تعاملی می‌داند.
- بخش ۱۰، React فرانت را محدود به موارد پیچیده می‌کند؛ بخش ۱۸ نیز React مدیریت و PHP عمومی را خلاصه می‌کند.

پس سند اولیه نباید به‌عنوان تأیید خواسته جدید معرفی شود. توضیح جدید مالک محصول بر این پیشنهادهای قدیمی مقدم است. اسناد قبلی هم پیش از این توضیح نوشته شده‌اند و بخش‌های ناسازگارشان علامت‌گذاری شد.

## نتیجه تحقیق مستندات

۱. React را می‌توان در قسمت‌های مشخص یک صفحه موجود اجرا کرد؛ لازم نیست کل صفحه به React بازنویسی شود. React کنترل DOM داخل root خودش را می‌گیرد. این مبنای فنی همزیستی است، نه تضمین آماده‌بودن ادغام رادمان. [راهنمای رسمی ادغام React](https://react.dev/learn/add-react-to-an-existing-project)، [createRoot](https://react.dev/reference/react-dom/client/createRoot).

۲. پشتیبانی استاندارد محتوای Elementor به مسیر رندر وردپرس و `the_content()` وابسته است. فایل‌ها و رفتار frontend عناصر Elementor هم باید حفظ شوند. نمایش HTML خام داخل React به‌تنهایی اثبات سازگاری ویرایشگر، فرم‌ها و ویجت‌ها نیست. [راهنمای رسمی ناحیه محتوا](https://elementor.com/help/the-content-area-was-not-found-error/)، [اسکریپت‌ها و استایل‌ها](https://developers.elementor.com/docs/scripts-styles/).

۳. React رندر سمت سرور دارد و HTML حاصل می‌تواند با hydration تعاملی شود. SSR رسمی React با JavaScript اجرا می‌شود؛ صرف داشتن هاست PHP وردپرس، زیرساخت اجرای آن را فراهم نمی‌کند. محل اجرا، پیش‌تولید یا سرویس رندر باید جدا انتخاب شود. [Server React DOM APIs](https://react.dev/reference/react-dom/server).

۴. React به‌تنهایی تضمین سرعت نیست. برای رادمان باید هزینه دریافت/اجرای JS، محتوای نمایش اولیه، داده‌گیری و فایل‌های Elementor روی صفحات واقعی اندازه‌گیری شوند. این نتیجه مهندسی از مدل اجراست؛ هنوز benchmark رادمان وجود ندارد.

## گزینه‌های قابل بررسی؛ هیچ‌کدام هنوز انتخاب نشده‌اند

| مسیر | معنی عملی | هزینه یا محدودیت |
|---|---|---|
| قالب وردپرس + React در بخش‌های فرانت | ناحیه Elementor با رندر استاندارد خودش؛ بخش‌های React با مرز DOM مستقل؛ سازنده هدر/فوتر مستقل | React در فرانت وجود دارد، اما همه HTML از React تولید نمی‌شود؛ نباید با خواسته «کل فرانت React» یکی فرض شود |
| صفحات اختصاصی تمام React + صفحات Elementor استاندارد | مسیر رندر هر صفحه مشخص؛ قالب و سازنده مشترک | رندر اولیه صفحات React و جلوگیری از تداخل فایل‌ها باید حل شوند؛ هنوز نمونه لازم است |
| کل فرانت React با SSR/پیش‌تولید و ادغام سفارشی Elementor | کنترل گسترده React بر نمایش عمومی | زیرساخت و کش/بازسازی محتوا، پیش‌نمایش و چرخه ویجت‌های Elementor پیچیده‌تر می‌شوند؛ سازگاری خودکار فرض نشود |

جداسازی هدر/فوتر از Elementor امکان کنترل فایل‌ها و حذف وابستگی هدر/فوتر به آن را می‌دهد؛ اگر محتوای صفحه Elementor باشد، هزینه فایل‌های موردنیاز آن محتوا همچنان وجود دارد. سازنده جدا به‌تنهایی تضمین سرعت نیست.

## اثر نبود افزونه همراه

ماژول‌بندی داخل قالب همچنان ممکن است؛ یک ZIP به معنی یک فایل بزرگ یا بارگذاری همه امکانات نیست. ثبت کاتالوگ و API اختصاصی در ماژول‌های خود قالب انجام خواهد شد. با تعویض قالب رکوردهای کاتالوگ در دیتابیس باقی می‌مانند، ولی مدیریت و نمایش وابسته به ثبت نوع محتوای رادمان دیگر فعال نیست. این پیامد انتخاب بسته‌بندی است؛ دلیل بازگرداندن خودکار افزونه ردشده نیست.

## تصمیم تأییدشده: طراحی پایه به‌جای مجموعه طرح‌های قابل‌انتخاب

برای وبلاگ، محصول کاتالوگی و نمونه‌کار، مجموعه چندین طرح آماده با انتخاب‌گر در تنظیمات قالب ساخته نشود. هر بخش طراحی پایه خودش را با React داشته باشد. اگر مشتری ظاهر دیگری خواست، برای همان پروژه سفارشی‌سازی شود؛ طرح اختصاصی مشتری به‌طور خودکار به هسته عمومی رادمان اضافه نشود.

این تصمیم درباره تنوع ظاهری است؛ صفحه فهرست/آرشیو و صفحه جزئیات، در صورت نیاز، همچنان نقش‌های متفاوت دارند. به معنی یکسان‌بودن ظاهر همه انواع محتوا، حذف تنظیم فونت/رنگ سراسری یا حذف سازنده اختصاصی هدر/فوتر نیست. امکان صفحه مستقل Elementor نیز مطابق تصمیم قبلی برقرار است. ثبت این سیاست برای نمونه‌کار به‌تنهایی جزئیات مدل داده و قابلیت‌های نمونه‌کار را نهایی نمی‌کند.

پیشنهاد نگهداری: اجزای مشترک و قرارداد داده ثابت بمانند و سفارشی‌سازی مشتری در لایه ظاهر جدا و قابل‌ارتقا انجام شود؛ روش بسته‌بندی این لایه هنوز انتخاب نشده است. تغییر مستقیم و پراکنده هسته برای هر مشتری هدف نیست.

نتیجه مورد انتظار، کاهش کد، گزینه‌ها و دامنه تست و نگهداری است. کاهش حجم بسته با حذف طرح‌های استفاده‌نشده ممکن است؛ سرعت صفحه به فایل‌های واقعی بارگذاری‌شده بستگی دارد. اگر طرح‌های اضافه از ابتدا بارگذاری نشوند، حذف آن‌ها الزاماً سرعت همان صفحه را بیشتر نمی‌کند. React نیز به‌تنهایی تضمین سرعت نیست. فعلاً اندازه‌گیری اجرایی انجام نشده است.

## موضوع تصمیم بعدی

### تصمیم تأییدشده: انتخاب روش در سطح هر صفحه

مالک محصول تصریح کرد که ممکن است تمام صفحات یک پروژه با React ساخته شوند و بعداً فقط یک صفحه، مثلاً تماس با ما، با Elementor ساخته شود. بنابراین React محدود به چند صفحه ویژه یا اجزای تعاملی نیست. تعداد یا نسبت صفحات هر روش محدودیتی ندارد و انتخاب روش برای هر صفحه مستقل است.

- پروژه می‌تواند فرانت کاملاً React داشته باشد؛ نصب Elementor برای این حالت اجباری نیست.
- اگر Elementor نصب و برای یک صفحه انتخاب شد، محتوای همان صفحه از مسیر استاندارد Elementor نمایش داده شود؛ سایر صفحات React باقی بمانند.
- هدر/فوترساز اختصاصی رادمان مستقل از روش محتوای صفحه است و در هر دو حالت قابل استفاده خواهد بود.
- وابستگی‌های مخصوص هر روش فقط در صفحات نیازمند آن بارگذاری شوند؛ وابستگی مشترک هدر/فوتر جدا محاسبه شود.
- انتخاب روش صفحه با تبدیل خودکار محتوای React به Elementor یا برعکس یکی نیست؛ تبدیل محتوا فعلاً تعهد پروژه نیست.

پرسش قبلی درباره «تمام React یا صرفاً بخش‌های تعاملی» با این توضیح پاسخ داده شد و دیگر پرسش باز محصول نیست. روش رندر اولیه صفحات React، زیرساخت هاست و قرارداد محتوا/ویرایش صفحات React همچنان تصمیم فنی باز هستند.

تحقیق قبلی با Context7 برای React و Elementor و منابع رسمی بالا انجام شد؛ تست اجرایی یا اندازه‌گیری سرعت انجام نشده است.
