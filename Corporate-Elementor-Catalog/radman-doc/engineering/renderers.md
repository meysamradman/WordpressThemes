# انتخاب روش نمایش محتوا

وضعیت ۲۰۲۶-۱۰-۱۹: پیاده شده با fallback بومی؛ نیاز تأییدشده در [صفحات](../scenarios/pages.md) است. این کنترل با انتخاب Template یک برگه یا روشن/خاموشی ماژول‌های Core متفاوت است.

## تنظیمات و اولویت

### مرز AJAX اختصاصی و المنتوری — ۲۰۲۶-۱۰-۲۰

نیاز تأییدشدهٔ AJAX فیلتر/جستجو/صفحه‌بندی برای آرشیوهای محصول و وبلاگ در [سناریوی محتوا](../scenarios/content.md) است. وضعیت: **کد پایهٔ اختصاصی پیاده شد؛ پذیرش نصب واقعی باقی است**. کنترلر مستقل فقط روی markup اختصاصی و fallback واقعی فعال است؛ Pro منطبق marker یا پاسخ fragment رادمان نمی‌گیرد. query اصلی و partial مشترک نتایج، HTML اولیه و GET را حفظ می‌کنند؛ نمایش سایت SPA نمی‌شود. مسیر fragment، JS lazy، History، خطا و شواهد در [قرارداد AJAX](archive-ajax.md) مالک مستقل دارند.

مستند رسمی Elementor در این تاریخ بررسی شد: [Loop pagination](https://elementor.com/help/paginate-loop/) گزینهٔ `Load Type = AJAX` دارد که فقط Loop Grid را تازه می‌کند؛ [Taxonomy Filter](https://elementor.com/help/taxonomy-filter-widget/) باید به Loop Grid مشخص متصل شود و طبق محدودیت مستند، با `Current Query` کار نمی‌کند؛ برای این ترکیب query باید داخل widget تنظیم شود. [Search widget](https://elementor.com/help/search-widget/) تنظیم Live Results و قالب نتایج خودش را دارد؛ وجود آن را نباید معادل فیلتر خودکار هر Loop Grid دانست. در آرشیو بدون Taxonomy Filter، Current Query بسته به طرح قابل استفاده است؛ در طرح دارای آن، حفظ زمینهٔ آرشیو/زبان و نوع محتوای مستقل نیاز به تنظیم و تأیید همان نسخه دارد. هیچ مسیر WooCommerce برای CPT کاتالوگ فرض نشود.

این بررسی تأیید امکانات مستند است؛ اجرای ترکیب widgetها با CPT، Atomic، نسخه‌های ارسالی و WPML هنوز پذیرش runtime جدا می‌خواهد. صرف نصب Pro یا انتخاب `elementor`، صفحه را خودکار AJAX نمی‌کند.

مسیر مدیریت: رادمان ← طراحی محتوا. وبلاگ، محصولات و نمونه‌کار هر کدام دو انتخاب مستقل «صفحهٔ جزئیات» و «آرشیو» دارند. پیش‌فرض همه `custom` است؛ تنها مقدار دیگر `elementor` است و مسیر فایل یا ID دلخواه PHP نمی‌پذیرد.

کلیدها در تنظیمات ظاهری قالب: `blog_single_renderer`، `blog_archive_renderer`، `catalog_single_renderer`، `catalog_archive_renderer`، `portfolio_single_renderer` و `portfolio_archive_renderer`. طبق اصلاح مالک در ۲۰۲۶-۱۰-۲۰، هر دو گزینه حتی در نبود Core/Pro قابل انتخاب و ذخیره‌اند؛ وضعیت ماژول خاموش و fallback روشن است و انتخاب renderer آن را روشن نمی‌کند. نبود Pro در پنل روشن است و تغییر انتخاب، محتوای WordPress/Core را بازنویسی نمی‌کند. تنظیمات چیدمان اختصاصی هم برای fallback قابل دسترسی‌اند.

رابط در `src/js/admin/renderer-fields.js` از صفحهٔ اصلی تنظیمات جدا شد. بخش برگه‌ها روش انتخاب native Template، ورودی مدیریت برگه‌ها و وضعیت Elementor/Atomic را دارد؛ selector سراسری یا metadata موازی برای برگه‌ها ساخته نشد. قالب صریح اختصاصی و مسیر Atomic در [قرارداد Elementor](elementor.md) مالک مستقل دارند. برگهٔ معمولی Elementor به Pro نیاز ندارد؛ انتخاب `elementor` برای آرشیو/single همچنان به Pro Theme Builder و طرح منتشرشدهٔ منطبق نیاز دارد.

`inc/renderers.php` زمینهٔ query جاری را تشخیص می‌دهد. وبلاگ شامل نوشتهٔ منفرد، صفحهٔ نوشته‌ها و آرشیو دسته/برچسب/نویسنده/تاریخ است؛ نتایج جستجوی مختلط، برگه‌ها و ۴۰۴ خودکار به این انتخاب‌ها ملحق نمی‌شوند. برای محصول و نمونه‌کار، single، آرشیو CPT و taxonomyهای خودشان هدف هستند.

## PHP اختصاصی و Elementor Pro

در حالت اختصاصی، template hierarchy استاندارد WordPress و Child Theme مالک markup و CSS هستند. فایل‌های `single-radman_product.php`، `archive-radman_product.php`، `single-radman_portfolio.php` و `archive-radman_portfolio.php` ورودی‌های مستقل سفارشی‌سازی‌اند؛ وبلاگ از single/index استفاده می‌کند. بازنویسی یک ورودی در Child نباید فایل‌های مشتری دیگر را به قالب پایه اضافه کند. قالب سفارشی مشتری برای حفظ کلید انتخاب، همان بررسی `RadmanCT\Renderers\render()` پیش از خروجی اختصاصی را نگه دارد.

در حالت المنتوری، API بومی `elementor_location_exits(location, true)` وجود طرح منطبق و `elementor_theme_do_location` نمایش آن را مدیریت می‌کنند. طراحی و شرایط نمایش از Theme Builder خود Pro تعیین می‌شوند؛ IDهای طرح در گزینه‌های موازی رادمان ذخیره نمی‌شوند. نبود API یا طرح منتشرشدهٔ منطبق، حالت اختصاصی را باقی می‌گذارد. محتوای رمزدار از این مسیر به نمایش اطلاعات تکمیلی نمی‌رود.

ثبت locationهای single/archive با overwrite خاموش است. header/footer مانند الگوی محدود WoodMart به‌صورت غیرعمومی ثبت می‌شوند تا مالکیت سازندهٔ PHP رادمان حفظ شود. hook `elementor/theme/get_location_templates/template_id`، طرح location انتخاب‌نشده را در خروجی عمومی کنار می‌گذارد؛ مدیریت و preview مجاز المنتور این محدودسازی عمومی را ندارند. این مسیر با نسخهٔ ارسالی Pro بررسی شده، نه تضمین API همه نسخه‌های آینده.

CSS طراحی اختصاصی وقتی طرح Pro منطبق مصرف می‌شود کنار گذاشته می‌شود. CSS پایه، فونت محلی و هدر/فوتر رادمان باقی می‌مانند. اگر طرحی نباشد، CSS اختصاصی fallback بارگذاری می‌شود. Elementor همچنان مالک JS/CSS widgetهای خودش است؛ تنظیمات تأخیر/کش و همه widgetها بررسی نشده‌اند.

## طراحی پایهٔ اختصاصی — ۲۰۲۶-۱۰-۲۰

**آماده‌سازی طرح — Theme 0.1.25:** آرشیو و جزئیات هر سه بخش اکنون partial مستقل در `template-parts/blog/`، `catalog/` و `portfolio/` دارند؛ [نقشهٔ شش صفحه و کارت‌ها](client-customization.md). gate موجود Pro و header/footer بیرون partial طراحی باقی مانده‌اند؛ تغییر ظاهر به انتخاب renderer، query یا داده دست نمی‌زند. نام و رفتار partialهای ورودی `content/archive.php` و `content/detail.php` حفظ شد؛ بدنهٔ مشترک به `content/item-archive.php` و `content/item-detail.php` منتقل شد. طرح بصری تازه اجرا نشده و منتظر نمونهٔ مالک است. قرارداد کوتاه شش مسیر، عدم query به Pro در حالت custom و fallback طرح ناموجود پاس شد؛ این بررسی اثبات ظاهر یا نصب واقعی نیست.

آرشیو محصول کارت تصویر، عنوان، برند/کد، خلاصه و پیوند جزئیات دارد؛ فیلترهای دسته/برند/ویژگی، جستجو و صفحه‌بندی موجود حفظ شده‌اند. جزئیات محصول از partial مستقل `template-parts/content/product-overview.php` استفاده می‌کند: تصویر و گالری کنار عنوان، خلاصه، کد، دسته/برند/ویژگی و نمایش قیمت یا تماس؛ سپس محتوای کامل و جدول مشخصات می‌آیند. در عرض کوچک، نمای دو ستون به یک ستون تبدیل می‌شود. قیمت فقط در جزئیات است؛ بخش توضیحات خالی تیتر ندارد.

وبلاگ کارت تصویر، دسته، تاریخ، عنوان و خلاصه دارد؛ جزئیات با پیوند بازگشت، عنوان، دسته/تاریخ/نویسنده، خلاصه، تصویر و محتوای استاندارد نمایش داده می‌شود. `inc/blog.php` مستقل از Core است. partialهای `content/card`، `content/post-meta`، `content/item-card` و `content/product-overview` از مسیر بومی `get_template_part` در Child Theme قابل override هستند. تصویر ناموجود جای‌نگهدار CSS دارد؛ دارایی یا فونت خارجی ندارد. CSS مشترک کارت/متادیتا در source ماژولار است و همراه ورودی مربوط build می‌شود؛ stylesheet اختصاصی هنگام مصرف Pro منطبق کنار می‌رود.

این خروجی، طراحی پایهٔ قابل سفارشی‌سازی است؛ کتابخانهٔ چند طرح آماده یا تأیید طراحی نهایی مشتری نیست. gate انتخاب renderer پیش از markup اختصاصی حفظ شده است. کنترل رمز نوشته/محصول پیش از تصویر و اطلاعات تکمیلی اجرا می‌شود. مرجع محدود Hub برای markup بومی نوشته و WoodMart برای متادیتای محصول استفاده شد؛ موتور یا کد کامل قالب مرجع وارد نشد. API رسمی [get_template_part](https://developer.wordpress.org/reference/functions/get_template_part/) برای انتقال args و override قالب فرزند بررسی شد.

## دادهٔ کاتالوگ در طرح المنتوری

### متادیتای کارت جاری — ۲۰۲۶-۱۰-۲۰

برای کارت محصول در Loop Item از `[radman_content_meta context="loop" compact="yes"]` استفاده شود. این حالت صریح، `get_the_ID()` همان قلم جاری را مصرف می‌کند؛ حالت پیش‌فرض بدون context همچنان به منبع single اصلی متکی است تا جابه‌جایی global post توسط سند المنتور، اطلاعات جزئیات را اشتباه نکند. compact فقط کد و برند محصول را نشان می‌دهد؛ حذف compact دسته/برند/ویژگی کامل را برمی‌گرداند. نمونه‌کار taxonomy خودش را دارد. این ابزار query محصول یا تعویض global post ایجاد نمی‌کند؛ query جاری و Loop Grid همچنان متعلق به Pro هستند.

نوع محتوا، ماژول فعال، انتشار و رمز همان قلم بررسی می‌شوند؛ قلم نامرتبط/خصوصی/بدون منبع خروجی ندارد و به محصول بیرونی fallback نمی‌کند. ابزارهای قیمت، مشخصات و گالری در این تغییر به آرشیو تعمیم داده نشده‌اند؛ قیمت همچنان در جزئیات مصرف می‌شود. CSS متادیتا با handle مشترک در همان مصرف بارگذاری می‌شود.

منبع دقیق نسخهٔ ارسالی Pro در `modules/posts/skins/skin-base.php::render` و `modules/loop-builder/skins/skin-loop-base.php::render_post_content` بررسی شد: query بومی قلم را با `the_post` فعال و `get_the_ID` را پیش از رندر سند Loop می‌خواند. مستند عمومی hook/query در Context7 خوانده شد، اما جزئیات این قرارداد از سورس Pro ارسالی است. قرارداد PHP کوتاه قلم متفاوت از single بیرونی، compact، قلم نامرتبط/رمزدار و ماژول خاموش را بررسی می‌کند؛ اجرای واقعی Loop Grid/Atomic در مرورگر هنوز پذیرش نشده است.

در widget استاندارد Shortcode می‌توان از `[radman_product_specs]`، `[radman_content_gallery]`، `[radman_content_meta]` و `[radman_product_inquiry]` و در آرشیو محصول از `[radman_catalog_filters]` استفاده کرد. متادیتای مشترک، کد مرجع و دسته/برند/ویژگی همان محصول یا دستهٔ نمونه‌کار را نشان می‌دهد؛ CSS آن در طرح Pro فقط هنگام خروجی واقعی مصرف می‌شود. در آرشیو المنتوری، نمایش CPT با ابزار Posts/Archive/Loop و query بومی مناسب همان طرح انجام شود؛ شرط Current Query و محدودیت Taxonomy Filter در بخش «مرز AJAX» همین سند مشخص است. ویجت‌های فروشگاهی WooCommerce در دامنهٔ رادمان نیستند. shortcode فیلتر رادمان فعلاً فرم GET است و خودبه‌خود widget المنتوری را AJAX نمی‌کند؛ برای تعامل بومی Pro از widgetهای خودش استفاده شود. این‌ها ابزار نمایش PHP هستند؛ widget اختصاصی یا کتابخانهٔ اضافه ندارند. فقط در زمینهٔ معتبر همان محتوا خروجی می‌دهند و در ماژول خاموش ثبت نمی‌شوند. منبع پیش‌فرض از query اصلی و حالت صریح loop از قلم جاری می‌آید، نه از سند قالب Elementor.

فایل CSS هر ابزار هنگام مصرف بارگذاری و با handle استاندارد deduplicate می‌شود؛ اگر shortcode پس از head رندر شود، همان فایل minified در محل مصرف چاپ می‌شود. گالری JS مستقل و محلی دارد؛ بدون JS نیز تصاویر و پیوندهایشان قابل استفاده‌اند. درج پویای widget پس از بارگذاری اولیهٔ صفحه جدا بررسی نشده است.

## شواهد و محدودیت

پیش‌نمایش بومی همان محصول/نمونه‌کار برای ویرایشگر مجاز، استثنای محدود شرط انتشار عمومی ابزارهای بالاست؛ ID اصلی، مجوز همان محتوا، رمز و وضعیت ماژول با محافظ مشترک بررسی می‌شوند. این استثنا به قلم خصوصی دیگری در Loop سرایت نمی‌کند. جزئیات و بررسی واقعی در [پیش‌نمایش مجاز](content-modules.md) است؛ ادعای پذیرش preview واقعی Pro/WPML نیست.

### قیمت یا تماس محصول — ۲۰۲۶-۱۰-۲۰

ابزار `[rdct_product_display]` انتخاب همان محصول را بین قیمت متنی و پیوند «تماس با ما» نمایش می‌دهد. `[radman_product_inquiry]` برای سازگاری با محتوای ذخیره‌شده alias همین خروجی است؛ دیگر فرم یا دکمهٔ «درخواست قیمت» ندارد. renderer مشترک `inc/integrations/product-display.php` در جزئیات PHP و shortcode المنتور مصرف می‌شود؛ `template-parts/content/product-display.php` نقطهٔ override قالب فرزند است. نوع محتوا/ماژول، انتشار و رمز محافظ بررسی می‌شوند؛ خروجی خالی CSS نمی‌گیرد. استایل سبک مستقل فقط در جزئیات کاتالوگ یا مصرف ابزار بارگذاری می‌شود. [قرارداد داده و تصمیم مالک](content-modules.md).

`tests/renderers-contract.php` جدایی بخش‌ها و archive/single، fallback، محتوای رمزدار، whitelist تنظیمات و مالکیت locationها را با stub بررسی می‌کند. بررسی محدود `tools/qa-elementor.ps1 -RendererOnly` روی WordPress 7.1.3/PHP 8.4.26/Elementor 4.3.5/Pro 4.3.2 پاس شد: ساخت واقعی Single Theme Builder، شرط انتشار منطبق، رندر طرح از API بومی، ادامهٔ نمایش سازندهٔ PHP و بازگشت انتخاب به custom. fixture شرایط نمایش در تلاش اول قالب ورودی نادرست داشت؛ به آرایهٔ ساختاریافتهٔ API همان نسخه اصلاح شد و بررسی هدفمند پاس شد. سورس افزونه تغییر نکرده است.

مرجع رسمی: [نمایش location همراه fallback](https://developers.elementor.com/docs/themes/displaying-locations/). مرورگر، ماتریس کامل آرشیو/محصول/نمونه‌کار با Pro و WPML واقعی هنوز تأیید نشده‌اند. deprecationهای خود افزونه‌های ارسالی در [قرارداد Elementor](elementor.md) ثبت‌اند و پنهان نشده‌اند.
