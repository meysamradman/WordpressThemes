# رابط مشترک مدیریت رادمان

## منوی مستقل نماهای محتوا و انتخابگر مشترک — ۲۰۲۶-۱۰-۳۰

تراز ردیف منو در خود کنترل مشترک با Grid سه‌ستونی آیکون/عنوان/فلش حل می‌شود؛ align-items:center، جایگاه ثابت آیکون‌ها و line-height یکسان مانع بالارفتن glyph فلش در کادر بزرگ‌تر می‌شوند. flex و margin:auto قبلی برای عنوان/فلش حذف شدند؛ node جدید اضافه نشد و RTL/LTR از جهت سند می‌آید.

بررسی محدود مرورگر: مرکز عمودی متن، آیکون و فلش هر هفت ردیف حداکثر ۰٫۰۱px اختلاف داشت. با بازکردن «ظاهر» فقط همان گروه باز ماند و شش گروه دیگر inert بودند. تصویر نتیجه در artifacts/settings-menu-aligned.png ثبت شد؛ تنظیمات سایت ذخیره یا بازنویسی نشدند.

گروه‌های منو تک‌باز هستند: بازکردن یک والد، والد قبلی را می‌بندد؛ کلیک دوباره همان والد همه را می‌بندد و انتخاب صفحه عوض نمی‌شود. بازشدن/بسته‌شدن و فلش با CSS کوتاه ۱۸۰ms انجام می‌شود؛ wrapper موجودِ فرزندان یک لایهٔ Grid برای انیمیشن ارتفاع طبیعی دارد. فرزندان بسته inert و aria-hidden هستند؛ مسیر کیبورد و اتصال aria-controls حفظ شده‌اند. کاهش حرکت transition را حذف می‌کند؛ تایمر، GSAP، اندازه‌گیری DOM یا وابستگی جدید لازم نیست.

هویت بالای منوی تنظیمات طبق اصلاح مالک فقط یک تصویر لوگو و نسخهٔ کوچک دارد؛ عنوان متنی تکراری رادمان، wrapper آن و فاصلهٔ بلند قبلی حذف شدند. نسخه همچنان از metadata واقعی config می‌آید؛ مقدار یا نسخهٔ بسته تغییر نکرد.

خط سربرگ برند و toolbar تنظیمات با حداقل ارتفاع مشترک ۶٫۵rem هم‌تراز است؛ محتوا در هر دو عمودی وسط است و padding افقی toolbar با پنل فرم یکسان می‌ماند. حداقل ارتفاع به‌جای ارتفاع ثابت اجازهٔ شکستن کنترل‌های toolbar در عرض کم را می‌دهد.

تصحیح مالک: انتخاب نوع محتوا/آرشیو/جزئیات با تب‌های افقی درون فرم حذف شد. منوی تنظیمات سه والد وبلاگ، نمونه‌کار و محصولات دارد؛ هرکدام دو فرزند آرشیو و جزئیات. هر نما یک صفحهٔ تنظیمات مستقل با فرم مشترک و lazy import واحد `content-view-fields.js` است: روش نمایش، چیدمان، رنگ پس‌زمینه و سایدبار همان نما. کلیدهای ذخیره‌شده حفظ شدند؛ بازنشانی فقط scope همان صفحه را برمی‌گرداند. صفحهٔ کم‌محتوای برگه‌ها/طراحی محتوا، callout، فعال‌ساز تکراری Atomic و ماژول انتخاب scope حذف شدند؛ ویرایش صفحات و فعال‌سازی Elementor از رابط بومی خودشان انجام می‌شود.

ChoiceControl باقی‌ماندهٔ سایر فرم‌ها، با مطالعهٔ کنترل buttons و base.css وودمارت و راهنمای فاصلهٔ UX، دکمه‌های با عرض طبیعی، gap هشت پیکسل، گوشهٔ مستقل، وضعیت انتخاب پررنگ و focus بومی دارد؛ flex-grow و margin منفی اتصال حذف شدند. کنترل‌های آیکونی سازنده اندازهٔ اختصاصی موجود را حفظ می‌کنند. فونت منوی تنظیمات به ۱۴px و زیرمنو به ۱۳px کاهش یافت؛ فرم‌ها و صفحات دیگر وردپرس هدف نیستند. مرورگر منوهای مستقل و حذف پیام موفقیت Rocket در صفحات رادمان را نشان داد؛ تنظیمات کاربر ذخیره نشدند.

## دسته‌بندی رنگ و محتوا — ۲۰۲۶-۱۰-۳۰

طبق [تنظیمات](../scenarios/settings.md)، شناسهٔ پایدار design اکنون عنوان «رنگ‌ها» دارد؛ URL قدیمی و دادهٔ ذخیره‌شده حفظ می‌شوند. ColorSettingsFields تنبل، کنترل رنگ مشترک و ContentScopeFields مشترک با طراحی محتوا را مصرف می‌کند. انتخاب محتوا/نما با ChoiceControl موجود است؛ تنها کنترل‌های نمای منتخب mount می‌شوند، درحالی‌که state کامل SettingsApp مالک تمام مقادیر و ذخیرهٔ JSON است. reset بخش رنگ، پس‌زمینه‌ها و برند را پوشش می‌دهد؛ reset طراحی محتوا رنگ‌ها را تغییر نمی‌دهد. هیچ endpoint، گزینهٔ DB، وابستگی یا stylesheet تازه اضافه نشده است. الگوی دسته‌بندی و section مستقل رنگ از فایل مرجع WoodMart inc/admin/settings/colors.php بررسی شد؛ framework آن منتقل نشد.

## سخت‌گیری ورودی ذخیرهٔ تنظیمات — ۲۰۲۶-۱۰-۲۹

save فقط POST با nonce رشته‌ای غیرخالی حداکثر ۱۲۸ بایت را، علاوه بر capability و بررسی nonce بومی قبلی، می‌پذیرد. nonce آرایه‌ای یا روش نادرست پیش از sanitizer/storage با 403 رد می‌شود. قرارداد settings-ajax برای این ورودی‌ها و حفظ مرز کد سفارشی، دادهٔ canonical و شکست write پاس شد؛ دادهٔ نصب مشترک نوشته نشد.

## بازنشانی کامل و چرخهٔ پنجرهٔ رنگ — ۲۰۲۶-۱۰-۲۹

با اولویت تازهٔ مالک، WPML در این ادامه تغییر نکرد. جاافتادگی بازنشانی اندازه‌های تایپوگرافی بسته شد: `settings-reset.js` بدون React، DOM یا import موتور کنترل‌ها، فیلدهای مجاز هر بخش را از defaults برمی‌گزیند؛ desktop/tablet/mobile هر دو زبان را پوشش می‌دهد و اندازهٔ cursor را با فونت اشتباه نمی‌گیرد. SettingsApp تأیید و state فرم را مالک است و این فایل فقط بازنشانی مقادیر را. بازنشانی کامل مجوز کد سفارشی را حفظ می‌کند؛ defaults یا مقادیر ورودی mutate نمی‌شوند.

ایراد واقعی ColorField این بود که با وجود instance قبلی مستقیماً return می‌کرد؛ trigger اکنون همان instance را دوباره show می‌کند و popup/vendor دیگری ساخته نمی‌شود. wrapper مشترک color-picker هنگام setColor بیرونی، timer و draft معلق را لغو می‌کند تا رنگ قبلی بعد از reset/تغییر بیرونی دوباره ثبت نشود. cleanup پیشین حفظ شد. الگوی فیلد/مقدار پیش‌فرض و enqueue مرجع WoodMart `controls/color/class-color.php` دوباره بررسی شد؛ تغییر موتور یا انتقال framework انجام نشد. Context7 برای Pickr نتیجهٔ مرتبط نداشت؛ APIهای show/setColor/destroy با README نسخهٔ نصب‌شدهٔ محلی 1.10.2 تطبیق داده شدند.

تست قدیمی NativeDropdown/ColorPicker با رفتار فعلی مشترک جایگزین شد؛ بازشدن مکرر، reset و destroy را می‌سنجد. تست wrapper با double کتابخانه، لغو debounce قدیمی و callback پس از destroy را پوشش می‌دهد؛ این شاهد عملکرد خود UI کتابخانه در مرورگر نیست. همراه قرارداد بازنشانی و ذخیرهٔ موجود، ۱۳ تست زیر یک ثانیه پاس شدند؛ Build و بررسی graph تأیید کردند Pickr در importهای فوری settings/builder نیست و فهرست سازنده preview/inspector را وارد نمی‌کند. کد PHP، WPML، دادهٔ سایت، نسخه‌ها و ZIP تغییر نکردند؛ مرورگر و تست طولانی اجرا نشدند.

## وضعیت بارگذاری مشترک — CONFIRMED، ۲۰۲۶-۱۰-۲۸

درخواست مالک: انتظار کوتاه آماده‌شدن رابط/پیش‌نمایش روشن و یکدست باشد؛ لودینگ تزئینی جای رفع تأخیر اضافه را نگیرد. shared/admin/loading.css تنها شکل نشانگر است و LoadingStatus در controls.js markup React مشترک با role=status و aria-live=polite می‌دهد. پوستهٔ PHP آغازین و کتابخانهٔ Vanilla همان class را مصرف می‌کنند؛ موتور یا وابستگی تازه، overlay مسدودکننده و spinner تصویری نداریم. رنگ/فونت ارث می‌برند و reduced motion چرخش را متوقف می‌کند.

اصلاح مالک، ۲۰۲۶-۱۱-۰۱: در هر نمای فعال فقط یک نشانگر انتظار نمایش داده شود. پوستهٔ PHP تنظیمات و سازنده ابتدا همان نشانگر مشترک را دارد و با mount شدن React جایگزین می‌شود؛ هم‌زمان باقی نمی‌ماند. داخل هدر/فوترساز، نوار وضعیت بالایی مالک واحد انتظار عملیات، پنل و پیش‌نمایش است؛ اولویت با عملیات، سپس پنل و سپس پیش‌نمایش است. Preview و Inspector فقط وضعیت آماده‌بودن/خطا را به والد گزارش می‌کنند و spinner جدا ندارند. خطای پنل جای انتظار را با پیام و تلاش دوباره می‌گیرد. تنظیمات هدر/فوتر دو درخواست مستقل خود را حفظ می‌کند، اما فقط یک نشانگر مشترک تا پایان هر دو دارد. هنگام ذخیره، وضعیت اصلی ذخیره جای نشانگرهای دریافت پنل را می‌گیرد؛ عنوان دکمه ثابت و کنترل حین عملیات غیرفعال است. این اصلاح جای قاعدهٔ قدیمی نشانگر فقط داخل Preview را می‌گیرد. هیچ حداقل زمان نمایشی، تایمر تزئینی، overlay یا وابستگی تازه اضافه نشده و debounce واقعی پیش‌نمایش حفظ است. CSS فقط در entryهای مدیریت مربوط است؛ صفحات عمومی یا مدیریت سایر بخش‌های WordPress هدف نیستند و کتابخانهٔ Elementor نشانگر مستقل بومی خود را حفظ می‌کند.

الگوی CSS انتخابی و فعال‌بودن فقط حین انتظار در مرجع mod-sticky-loader.css و backend هدر وودمارت بررسی شد؛ overlay، source یا framework آن کپی نشد. build، ۱۶ بررسی کوتاه preview/Inspector/library/save و lint PHP موفق بودند. در تب‌های مستقل مرورگر، بارگذاری اولیه و سپس aria-busy=false، حذف نشانگر و نمایش پیش‌نمایش هدر و فوتر دیده شد؛ چیدمان ذخیره نشد. همهٔ خطاهای شبکه یا ظاهر تمام مصرف‌کنندگان در مرورگر بازتولید نشدند. نسخه 1.1.1 و ZIP ثابت‌اند.

اصلاح فنی ۲۰۲۶-۱۱-۰۱: استایل نقطهٔ وضعیت با `:not(.rdct-loading)` از حلقهٔ انتظار جدا شد تا اندازه/پس‌زمینهٔ نقطه روی spinner نیفتد. وضعیت انتظار در موبایل مخفی نمی‌شود و به سطر خوانا می‌رود؛ محوشدن کل fieldset هنگام ذخیره حذف شد و کنترل‌ها همچنان disabled هستند. رنگ نشانگر از accent مشترک و حرکت از reduced-motion پیروی می‌کند. دریافت lazy ویرایشگر کد نیز دیگر فضای خالی بدون وضعیت ندارد.

مرجع محدود تازه: WoodMart `inc/admin/assets/js/builder.js` برای `ui.isLoading` و START_LOADING/STOP_LOADING و Hub `liquid/assets/src/liquid-admin.js` برای اتصال is-active به beforeSend/done بررسی شدند. این‌ها الگوی اتصال نشانگر به عملیات‌اند؛ نه تضمین مدیریت همهٔ خطاهای آن قالب‌ها و نه مجوز کپی Redux/jQuery، loader تصویری یا overlay آن‌ها. Build، lint دو PHP، ۲۲ آزمون کوتاه وضعیت/preview/Inspector/ذخیره و ۴ بررسی گراف دارایی پاس شدند. مرورگر، کندی شبکهٔ واقعی و ظاهر تمام دستگاه‌ها این نوبت بررسی نشدند؛ شواهد مرورگر بند قبلی مربوط به بررسی تاریخی ۲۰۲۶-۱۰-۲۸ است.

## ذخیرهٔ بدون رفرش تنظیمات — ۲۰۲۶-۱۰-۲۷

`settings/save.php` فقط action احراز‌شدهٔ `wp_ajax_rdct_save_settings` را ثبت می‌کند؛ capability برابر edit_theme_options و nonce مستقل لازم‌اند. payload JSON حداکثر ۴MiB، دارای کلید تنظیمات شناخته‌شده و محدود به عمق ۱۶ است. sanitizer موجود، حقوق unfiltered_html و hookهای update_option/ترجمه حفظ‌اند؛ endpoint عمومی، REST یا option خامِ بدون validation ساخته نشد. دادهٔ نامعتبر ذخیره نمی‌شود؛ پاسخ موفق مقدار canonical ذخیره‌شده را برمی‌گرداند و شکست واقعی نوشتن خطاست.

همهٔ submitها در SettingsApp به همین AJAX و عملیات ثبت‌شدهٔ سازنده وصل‌اند؛ native submit و رفرش حذف شدند. وضعیت در همان نوار بالا با role=status باقی می‌ماند. شکست header/footer موفقیت کلی نمی‌سازد؛ ذخیرهٔ دو رکورد و تنظیمات تراکنش واحد دیتابیس نیست. baseline پس از موفقیت به‌روز می‌شود و mergeSaved تغییرات تازهٔ حین درخواست را نگه می‌دارد. تا پایان درخواست ذخیرهٔ دوم/تعویض بخش مسدود است؛ هشدار خروج برای دادهٔ ذخیره‌نشده حفظ می‌شود. [سناریوی تنظیمات](../scenarios/settings.md).

قرارداد PHP مجوز، nonce، دادهٔ نامعتبر، حفاظت کد سفارشی، پاسخ canonical و شکست نوشتن را پوشش داد؛ JS پاسخ خراب/ناموفق و حفظ ویرایش حین درخواست را بررسی کرد. Build و ۳۷ بررسی مدیریت/دارایی موفق بودند؛ دو بررسی انتخاب زبان نیز پاس شدند. آزمون قدیمی NativeDropdown/ColorPicker در settings-ui با Pickr فعلی ناسازگار بود و در ادامهٔ ۲۰۲۶-۱۰-۲۹ با قرارداد رفتار فعلی جایگزین و پاس شد. ذخیرهٔ واقعی مرورگر روی میزبان/ظاهر نهایی و WPML در این کار تأیید نشده‌اند.

## اصلاح انتخاب رنگ و ردیف‌های تنظیمات — ۲۰۲۶-۱۰-۲۷

اصلاح صریح مالک، جایگزین کنترل قبلی: ColorField مشترک از Pickr محلی 1.10.2 با پوستهٔ monolith مشابه انتخابگر Classic Elementor استفاده می‌کند؛ بستهٔ رسمی MIT و مجوز داخل Theme است. موتور و CSS فقط پس از اولین کلیک import می‌شوند؛ مدیریت به نصب Elementor یا wp-components وابسته نیست. یک ورودی HEX داخل پنجره، swatchهای مشترک و بازنشانی دارد؛ فیلد HEX بیرونی تکراری حذف شده است. opacity با مدل فعلی خاموش است. پنجره در body و خارج از overflow بخش مدیریت قرار می‌گیرد، جهت HEX برابر LTR است و cleanup مانع پنجرهٔ دیررس پس از unmount می‌شود. بررسی fixture مرورگر، نصب واقعی میزبان را اثبات نمی‌کند؛ drag فیزیکی هنوز تأیید نشده است. توضیحات کنترل بومی WordPress در بخش‌های تاریخ‌دار پایین، وضعیت پیش از این اصلاح هستند.

ذخیرهٔ تب هدر/فوتر به toolbar مشترک تنظیمات وصل است. coordinator رکوردهای تغییرکرده را با revision موجود و به‌ترتیب ذخیره می‌کند؛ شکست، ادامهٔ ذخیره و پیام موفقیت کلی را متوقف می‌کند. ذخیرهٔ تنظیمات Core در صورت نیاز پس از موفقیت رکوردها انجام می‌شود؛ تراکنش اتمیک میان این storageهای مستقل ادعا نمی‌شود. [قاعدهٔ رابط](../scenarios/settings.md).

صفحات/مدیریت ماژول در تنظیمات از دکمه و توضیح پراکنده به Field و callout/actions هم‌تراز منتقل شدند؛ وضعیت Atomic متن فشردهٔ inline دارد. border/margin پیش‌فرض fieldsetهای نوع محتوا حذف شد و برچسب/ورودی با grid مشترک می‌مانند. همان ColorField در هدر/فوتر استفاده می‌شود؛ پوسته یا React جدید ساخته نشد. لینک دکمهٔ واقعیِ سازنده در فرانت cursor:pointer دارد؛ عنصر بدون مقصد aria-disabled باقی است و preview همچنان ابزار انتخاب/drag است.

اصلاح تأییدشدهٔ مالک در ۲۰۲۶-۱۰-۲۷: «اندازه و جایگاه» عنصر در سازنده نباید disclosure/dropdown تازه داشته باشد. کنترل‌های اصلی مستقیم و کم‌ارتفاع باشند؛ تراز و عرض با گروه آیکونی یک‌ردیفه، نام قابل‌دسترسی و tooltip؛ ورودی درصدی فقط برای حالت عرض دلخواه ظاهر شود. نام بلند گزینه‌ها نباید دکمهٔ چهارم را به ردیف مستقل بفرستد. انتخاب دستگاه همان کنترل مشترک بالای inspector است. پیاده‌سازی محدود در [مالک سازنده](builder.md) است؛ این اصلاح، جمع‌شونده‌کردن قبلی این قسمت را جایگزین می‌کند.

اصلاح گزارش رنگ هدرساز، ۲۰۲۶-۱۰-۲۶: کنترل بومی WordPress ColorPicker حفظ است؛ بدنهٔ رنگ/HEX جهت LTR دارد تا علامت # و مقدار عددی در RTL جابه‌جا نشوند. پهنای popover از ۱۹ به ۱۷rem محدود و picker در عرض همان بدنه کشیده می‌شود تا فضای خالی کنار آن نماند؛ پنل بومی با کنترل دست‌ساز جایگزین نشده است. بررسی DOM نصب واقعی جهت RTL و فضای خالی را تأیید کرد؛ ظاهر اصلاح‌شده پس از نصب نسخهٔ بعدی باید تأیید شود.

### قرارداد React مدیریت — ۲۰۲۶-۱۰-۲۱

**CONFIRMED:** Header Builder، Footer Builder و پنل تنظیمات از React و API رسمی `@wordpress/element` استفاده کنند. در build فعلی، API از `window.wp.element` گرفته می‌شود و PHP وابستگی `wp-element` را فقط روی صفحهٔ مربوط enqueue می‌کند؛ نصب یا bundle کردن React/ReactDOM دوم لازم نیست. این همان API ارائه‌شدهٔ وردپرس است؛ تغییر سبک import در آینده باید externalization صحیح به همان runtime را حفظ کند. نسخهٔ React مدیریت تابع نسخهٔ هدف WordPress است؛ برای تحمیل نسخهٔ اختصاصی، runtime هسته جایگزین نشود. [مرجع رسمی element](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-element/).

خروجی صفحات عمومی PHP/HTML و Vanilla JS می‌ماند و بدون React کار می‌کند. تمام فایل‌های رادمان self-hosted و runtime بدون CDN است. قرارداد نسخهٔ JS، minify و بارگذاری شرطی در [منابع محلی](../scenarios/local-assets.md) قرار دارد.

**CONDITIONAL:** اگر کامپوننت مستقلی واقعاً به React جدا نیاز داشت، مبنای درخواستی مالک `19.3.1` است، مشروط به بررسی peer dependencyها، سازگاری `react-dom`، نبود runtime تکراری/اشتراک hook بین نسخه‌ها و بررسی نصب هدف. این شرط، مجوز عمومی افزودن React به فرانت نیست؛ مرز «فرانت بدون وابستگی اجباری React» و الزام React وردپرس در مدیریت حفظ شود. در ۲۰۲۶-۱۰-۲۱، رجیستری npm انتشار `react@19.3.1` را تأیید کرد؛ صفحهٔ [نسخه‌های رسمی React](https://react.dev/versions) خانوادهٔ 19.3 را معرفی می‌کند. در کد فعلی چنین نیاز مستقلی احراز نشده و dependency جدید اضافه نشده است.

### تکمیل پنل جمع‌وجور — ۲۰۲۶-۱۰-۲۰

**تأکید ۲۰۲۶-۱۰-۲۳؛ مرجع جاری تصویر مالک در بخش بالا است:** الگوی بوم/inspector و تب‌های داخلی محتوا/استایل/پیشرفته حفظ است؛ runtime و CSS خود Elementor به سازنده وابسته نمی‌شوند. قاب‌های تو‌در‌توی هر فیلد با جداکنندهٔ ساده، گروه‌های تراز متصل و ورودی دقیق کنار slider جایگزین شدند. این الگو مجوز واردکردن کنترل یا CSS اختصاصی مدیریت رادمان به پنل Elementor نیست؛ مالک آن [کامپوننت‌ها](components.md) است. تطبیق بصری/لمس بدون بررسی مرورگر ادعا نمی‌شود.

`FieldGroup` گروه مستقیم با عنوان اختیاری است؛ بخش‌های disclosure تایپوگرافی، طراحی محتوا و کتابخانهٔ چیدمان با آن جایگزین شدند. H1 تا H6 مستقیم و جفت فونت فارسی/لاتین در شبکهٔ responsive هستند؛ نمونهٔ فونت فقط برای بدنه نمایش داده می‌شود. توضیحات طولانی سازنده کوتاه و راهنمای تکراری ارث‌بری هر ورودی حذف شد؛ hint ضروری و ارتباط label/aria حفظ است.

`RangeControl` اسلایدر و ورودی دقیق عدد با min/max/step مشترک دارد؛ فقط ورودی عدد name و id فرم می‌گیرد تا مقدار دوبار ارسال نشود. مقدار خالی تنظیمات خالی می‌ماند؛ تبدیل عدد در adapter سازنده صریح است. `ChoiceControl` گزینه‌های کوتاه تراز/چیدمان را با دکمهٔ type=button و aria-pressed نمایش می‌دهد. این دو کنترل ترکیبی wrapper هدفمند دارند؛ پایه‌های native زیر همچنان ساده‌اند. استایل هر سه در `shared/admin/fields.css` با palette مشترک و فونت خوانا قرار دارد. عدد schema، کلید ذخیره‌سازی و مرز Elementor تغییر نکردند.

`shared/admin/controls.js` پایهٔ مشترک `SelectControl`، `InputControl`، `CheckboxControl` و `TextareaControl` را مالک است. خروجی آن‌ها همان select/input/textarea بومی است؛ wrapper، کلاس تزئینی، کتابخانهٔ select یا کنترل کیبورد موازی اضافه نمی‌کنند. کنترل‌ها مقدار و callback را می‌گیرند و ID/name/disabled/dir، محدودیت‌های ورودی و ویژگی‌های aria را عبور می‌دهند. گزینهٔ select شامل value/label/disabled است. enum، validation سرور و منطق فعال/غیرفعال هر قابلیت بیرون از کنترل پایه می‌مانند.

تبدیل رشته به عدد فقط با `numeric=true` صریح در محل مصرف رخ می‌دهد؛ تنظیمات متنی/ورودی خالی به‌طور ناخواسته صفر نمی‌شوند. checkbox callback بولی دارد؛ مقدار hidden/نام فرم و قرارداد ذخیرهٔ WordPress در adapter همان فرم حفظ می‌شوند. hidden/file inputهای دارای ref یا رویداد native خاص، صرفاً برای حذف چند خط به کنترل عمومی تحمیل نشده‌اند.

در تنظیمات Theme، `Field` مالک layout و اتصال label/hint است؛ `InputField`/`SelectField` نام `radman_settings[...]` و aria-describedby را یک‌جا می‌سازند. `FontField` همین select را با نمونهٔ فونت و `ToggleField` همان checkbox را با مقدار خاموش فرم ترکیب می‌کنند. کنترل‌های appearance، منو، آیکون، بلوک، کتابخانه، تخصیص و toolbar سازنده‌ها هم همان primitive را مصرف می‌کنند؛ Dropdown دوم با HTML/رفتار مستقل نداریم. ویرایش کد/مشخصات در Core نیز از ورودی مشترک استفاده می‌کند.

فرم PHP سادهٔ تنظیمات Core از Settings API و select بومی خودش استفاده می‌کند؛ برای مشترک‌سازی با فرم React، JS و لایهٔ runtime تازه به آن تحمیل نمی‌شود. تفاوت rendering PHP/React نباید باعث کپی palette و قواعد ظاهری هر فیلد شود. کنترل پیچیدهٔ واقعاً متفاوت باید مالک جدا داشته باشد؛ کنترل سادهٔ جدید ابتدا با همین اجزا ساخته شود.

## رنگ و CSS مشترک

تکمیل رابط سازنده در ۲۰۲۶-۱۰-۱۹: `shared/admin/color-field.js` یک کنترل مشترک برای swatch بومی مرورگر، ورودی HEX و بازنشانی/ارث‌بری است؛ مقدار ناقص یا CSS دلخواه commit نمی‌شود و جهت HEX مستقل LTR است. `shared/admin/panel-tabs.js` تب‌های مشترک با ارتباط tab/tabpanel، Home/End و کلیدهای جهت متناسب با RTL/LTR را می‌سازد. قواعد این دو در `shared/admin/fields.css` فقط هنگام import صفحهٔ مصرف‌کننده وارد می‌شوند؛ palette از tokens موجود است. کنترل رنگ هدر/فوتر و دکمه دوباره نوشته نشده است. این اجزا font/icon library تازه ندارند؛ آیکون رابط از Dashicons موجود مدیریت WordPress می‌آید.

`shared/admin/tokens.css` تنها مالک palette رابط اختصاصی است: accent، کاغذ/سطح/سطح ملایم، متن/متن کم‌رنگ، border/خط، sidebar، وضعیت موفق، radius و shadow. accent از `--wp-admin-theme-color` با fallback مشخص می‌آید. رنگ ثابت تازه برای هر بخش، فیلد یا صفحه اضافه نشود. رنگ طراحی محتوای مشتری، مثل رنگ هدر/دکمه/افکت در مقدار تنظیمات، palette مدیریت نیست و از آن جدا می‌ماند.

tokenها روی rootهای موجود `.rdct-stg`، `.rdct-bld-editor`، `.rdct-plugins`، `.rdct-cor-settings` و `.rdct-cnt-editor` scope دارند؛ کلاس عمومی یا utility رنگ به تک‌تک کنترل‌ها اضافه نشده است. قواعد فرم و focus مشترک‌اند؛ layout خاص sidebar، card، بوم و جدول مشخصات در ماژول مربوط باقی می‌ماند. کلاس لازم برای ساختار، وضعیت و دسترس‌پذیری حذف نمی‌شود؛ هدف حداقل markup معنادار و نبود کلاس/selector تکراری برای همان نیاز است.

جهت از مدیریت WordPress ارث می‌رسد؛ فاصله، border، اندازه و موقعیت با CSS logical (`inline`/`block` و start/end) هستند. ورودی URL یا کد و اعداد در صورت نیاز جهت دادهٔ خودش را دارد و جهت کل پنل را عوض نمی‌کند. select بومی، رفتار RTL/LTR و کیبورد مرورگر/WordPress را حفظ می‌کند؛ فلش یا popup سفارشی اضافه نشده است.

## Build و جدایی runtime

پوشهٔ `shared/` فقط منبع توسعهٔ مشترک است. Build آن را در CSS/JS مدیریت هر بسته قرار می‌دهد؛ نصب Core یا Theme به وجود این پوشه در سرور یا فعال‌بودن بستهٔ دیگر وابسته نیست. tokenها در stylesheet اصلی هر صفحه وارد می‌شوند؛ CSS مشخصات اختیاری از tokenهای والد ویرایشگر ارث می‌برد و foundation را دوباره import نمی‌کند.

Theme یک chunk کوچک `controls` را بین تنظیمات و سازنده‌ها مشترک می‌کند؛ React همان `wp-element` است. Core خروجی مستقل خودش را دارد. صفحه‌های frontend این ماژول مدیریت را import نمی‌کنند و CSS عمومی سایت palette مدیریت را ندارد. enqueue هر صفحه همچنان با screen/capability همان صفحه است؛ CSS پایهٔ مشترک مجوز enqueue سراسری پنل در همهٔ مدیریت نیست.

## مرجع و بررسی

الگوی field پایه و select تخصصی در `themes/woodmart/inc/admin/modules/options/class-field.php` و `controls/select/class-select.php` محدود بررسی شد. framework، Select2، autocomplete، style engine و wrapperهای مرجع وارد رادمان نشدند؛ selectهای سادهٔ فعلی به آن‌ها نیاز ندارند.

Build و ۳۴ بررسی کوتاه Node پاس شدند. `tests/admin-ui.test.mjs` value/نوع، صفر، ورودی خالی، گزینهٔ disabled، checkbox، نام فرم، label/hint، dir، استفاده از palette مشترک و نبود palette مدیریت در CSS عمومی را بررسی می‌کند. قرارداد asset، chunk مشترک کوچک، نبود React دوم و CSS/JS مدیریت در ورودی frontend را کنترل می‌کند. این شواهد mock/static هستند؛ رابط React واقعی، dropdown مرورگر، کنتراست بصری و RTL/LTR روی سرور تازه بررسی نشده‌اند. PHP این بازآرایی تغییر نکرد؛ lint یا دیتابیس/مرورگر بی‌دلیل تکرار نشدند.
## اصلاح پوشش فونت فارسی — ۲۰۲۶-۱۰-۱۹

stylesheet مشترک `src/css/admin/typography.css` اکنون در scope صفحهٔ مدیریت رادمان، علاوه بر ورودی‌ها، headingها، label/legend و متن‌های پنل را صریحاً از متغیر Peyda محلی تغذیه می‌کند. نمونهٔ نمایشی فونت انتخابی مستثناست؛ آیکون‌ها، خروجی monospace و سایر صفحات وردپرس بازنویسی نمی‌شوند. بدون `!important` یا تکرار font-face برای هر بخش است. قرارداد کوتاه پوشش selectorها و استثنای نمونهٔ فونت پاس شد؛ computed style و پاسخ فایل فونت روی سرور هنوز بررسی نشده‌اند.
