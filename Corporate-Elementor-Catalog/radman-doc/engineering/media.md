# هویت سایت، تصاویر سازنده و SVG

اصلاح ۲۰۲۶-۱۰-۲۷ تراز تصویر/لوگو: wrapper مربوط به presentation در item چیدمان ادغام شده، picture بدون source چاپ نمی‌شود و img به‌صورت block و با نسبت طبیعی نمایش می‌یابد؛ سقف ارتفاع فقط با مقدار انتخاب‌شده اعمال می‌شود. ابعاد ذاتی، انتخاب مستقل دستگاه و API تصویر WordPress محفوظ‌اند. [ساختار و شواهد محدود](builder.md)، [قواعد CSS/DOM](markup-css.md).

## اصلاح انتخاب رسانه — ۲۰۲۶-۱۰-۲۷

WordPress Toolbar Select ابتدا `controller.close()` و سپس رویداد `select` را اجرا می‌کند؛ cleanup هم‌زمانِ close در image-picker مشترک، callback انتخاب لوگو/تصویر را از بین می‌برد. آزادسازی پنجره اکنون با microtask و پس از select بومی انجام می‌شود؛ انتخاب یک‌بار مصرف و لغو صریح همچنان فوری است. قراردادهای close سپس select برای انتخاب تکی/چندتایی و لغو پاس شدند. اثبات ابعاد SVG قبلی، اثبات کارکرد انتخابگر نبود. [سورس هسته](https://github.com/WordPress/wordpress-develop/blob/trunk/src/js/media/views/toolbar/select.js).

## نمایش لوگوی SVG قدیمی در سازنده — ۲۰۲۶-۱۰-۲۷

مسیر تصویر سازنده برای SVG محلی با metadata اندازهٔ غایب/صفر، viewBox/width/height را با parser محدود موجود MediaSvg و داخل uploads معتبر می‌خواند؛ دادهٔ رسانه بازنویسی نمی‌شود. SVG به‌صورت img و با اندازهٔ واقعی و escaping چاپ می‌شود، نه inline؛ srcset مصنوعی یا crop تازه ساخته نمی‌شود. لوگوی سراسریِ انتخاب‌شده نیز در سازنده همین مسیر را می‌گیرد و overrideهای هر دستگاه حفظ‌اند. PNG/JPEG و fallback نام سایت همان رفتار قبلی دارند.

لوگوی SVG بدون metadata در WordPress واقعی اندازهٔ ۲۵۰×۱۸۱ گرفت و در پیش‌نمایش/عمومی سازنده با باکس تنظیم‌شدهٔ ۱۵۰×۶۴ و object-fit:contain دیده شد. قراردادهای تصاویر responsive و fallback قدیمی پاس شدند. این مورد بازتولید محدود SVG است؛ همهٔ فایل‌های لوگوی نصب مالک یا تمام مشکلات احتمالی آن‌ها تأیید نشده‌اند.

مالک رفتار: [هدر/فوتر](../scenarios/header-footer.md)، [تنظیمات](../scenarios/settings.md) و [امنیت](../scenarios/security-access.md). پیاده‌سازی محلی ۲۰۲۶-۱۰-۲۳؛ پذیرش مرورگر/رسانهٔ واقعی مستقل است.

## لوگو و تصویر

**تصاویر محتوایی سفارشی — ۲۰۲۶-۱۰-۲۸:** مطابق [سناریوی صفحات](../scenarios/pages.md)، انتخاب رسانه و attachment ID منبع تصاویر قابل ویرایش مشتری است. رندر از helper مشترک و API بومی تصویر WordPress باشد تا ابعاد ذاتی، metadata، اندازه‌های تولیدشده و `srcset/sizes` حفظ شوند؛ Hero اولویت بالا و تصاویر پایین‌تر سیاست lazy متناسب داشته باشند. وجود فایل در uploads به‌تنهایی تضمین بهبود سرعت یا فشرده‌سازی نیست؛ حجم، ابعاد و انتخاب اندازه همچنان مؤثرند. runtime نباید عکس را خودکار import یا نام/تاریخ ثابتی را جست‌وجو کند. انتقال فایل‌های قدیمی باید صریح، بدون حذف اصل، بدون overwrite انتخاب مشتری و بدون واردکردن تکراری انجام شود. مصرف فعلی تصویر خانه و شواهد در [سفارشی‌سازی مشتری](client-customization.md) است.

لوگوی اصلی `custom_logo` و نمادک `site_icon` تنظیم native وردپرس‌اند. Theme در head همان `wp_head()` را حفظ می‌کند؛ فاوآیکون موازی، آپلودر دوم یا تغییر تنظیم Elementor ندارد. صفحات سفارشی و صفحات دارای محتوای Elementor می‌توانند همان هدر/فوترساز PHP را مصرف کنند؛ داخل طرح مستقل Elementor از کنترل Image/Site Logo خود آن استفاده می‌شود.

**اصلاح مالک، ۲۰۲۶-۱۰-۲۶:** یک لوگوی سراسری در هویت سایت مرجع باقی می‌ماند؛ انتقال انحصاری به هدرساز صحیح نیست، چون Site Logo المنتور و PHP بدون سازنده نیز باید آن را بخوانند. انتخاب دستگاه در سازنده با عنوان «لوگوی جایگزین این دستگاه» فقط override همان عنصر است و مقدار سراسری را نمی‌نویسد. لینک تنظیمات با عنوان واضح «لوگوی اصلی و نمادک سایت» به همان هویت native می‌رود؛ ذخیره/آپلودر دوم ساخته نمی‌شود. کنترل `custom_logo` در Customizer اکنون Media Control بومی تصویر است و crop ندارد؛ setting و مسیر ذخیره/پیش‌نمایش native حفظ‌اند. نمادک مرورگر همچنان کنترل مربعی بومی خودش را دارد؛ تصویر افقی لوگو نباید به‌اجبار نمادک شود. برش‌های قبلاً ذخیره‌شده بازسازی نمی‌شوند؛ برای برگشت شکل کامل، تصویر اصلی رسانه باید دوباره انتخاب شود. پذیرش دیداری انتخاب/ذخیره روی میزبان پس از نصب اصلاح باز است.

`inc/builder/logo.php` موتور مشترک لوگو و تصویر سادهٔ سازنده است. هر عنصر logo کلیدهای `logoImageId`، `laptopLogoImageId`، `tabletLogoImageId` و `mobileLogoImageId` دارد؛ صفر تصویر پایهٔ عنصر و پایهٔ خالی لوگوی سایت را می‌گیرد. عناصر مستقل‌اند؛ تنظیم جهانی جدا به نام «لوگوی فوتر» نداریم. اگر هیچ تصویر معتبری وجود نداشت، لوگو به نام سایت برمی‌گردد. اگر فقط تصویر دستگاه موجود باشد و لوگوی سایت نباشد، اولین تصویر معتبر دستگاه fallback پایه می‌شود.

عنصر image همان موتور را با کلیدهای `imageId`، `laptopImageId`، `tabletImageId`، `mobileImageId` و ابعاد متناظر `imageWidth/Height` مصرف می‌کند؛ تصویر مستقل لینک خانه و fallback به برند ندارد و alt از رسانه می‌آید. این عنصر برای تصاویر سادهٔ هدر/فوتر است؛ قابلیت‌های کامل افکت/گالری کامپوننت Image دوباره در سازنده ساخته نشده‌اند. هر دو از media frame مشترک `shared/admin/image-picker.js` استفاده می‌کنند؛ شناسهٔ attachment ذخیره می‌شود، نه HTML یا URL دلخواه. حذف انتخاب، ارث‌بری را برمی‌گرداند.

خروجی یک picture با sourceهای ۰–۷۶۷، ۷۶۸–۱۰۲۳ و ۱۰۲۴–۱۴۳۹ px و تصویر پایه برای دسکتاپ است؛ بدون JS تشخیص دستگاه یا چند img مخفی. srcset/sizes و ابعاد ذاتی از API رسانه، لینک خانه از home_url و شناسهٔ ترجمه از wpml_object_id می‌آیند. رسانهٔ گم‌شده به پایه برمی‌گردد؛ جهت RTL تصویر را معکوس نمی‌کند. اندازه‌ها همان حدود قبلی سازنده و چهار دستگاه‌اند؛ تصویر هدر eager و فوتر lazy است. لوگوی مخصوص وضعیت sticky/transparent هنوز کنترل مجزا ندارد؛ نباید برابری همهٔ گزینه‌های WoodMart/Hub ادعا شود.

## بارگذاری SVG

گزینهٔ `svg_uploads` در هویت سایت، پیش‌فرض false؛ `inc/media-svg.php` تنها مالک hookهای آن است. فعال‌سازی نیازمند DOM/libxml، edit_theme_options و upload_files است. SVG خام حداکثر ۱ MiB از مسیر native upload/sideload پذیرفته می‌شود؛ SVGZ پذیرفته نیست. خاموش‌کردن، تصاویر قبلی را حذف نمی‌کند و مجوزهای مستقل افزونه‌های دیگر، از جمله Elementor، را بازنویسی نمی‌کند.

کتابخانهٔ محلی `enshrined/svg-sanitize` دقیقاً **1.1.1** با commit `1976ff93c8d8a234cdd3ff99626bd43ecf11bf49` در `radmanct/vendor/svg-sanitize/` نگهداری می‌شود؛ namespace اختصاصی از تصادم با نسخهٔ افزونه‌های دیگر جلوگیری می‌کند. فقط src و LICENSE، manifest نسخه/hash و بدون Composer runtime یا اتصال شبکه در نصب مشتری. بازسازی توسعه با `tools/vendor-svg-sanitize.py` از commit مشخص انجام می‌شود؛ SHA هر فایل و archive در manifest است. ارتقا باید با بررسی upstream، تغییر pin و قرارداد کوتاه همراه باشد.

پاک‌سازی پیش از جابه‌جایی فایل به uploads، با removeRemoteReferences و minify خود کتابخانه انجام می‌شود؛ DTD/entity/PHP و XML نامعتبر رد می‌شوند. اجازهٔ MIME فقط برای مسیر فایل پاک‌شده با hash همان بایت‌ها صادر می‌شود؛ پسوند یا اعلام MIME مرورگر کافی نیست. خطا/نبود parser/مجوز به رد بارگذاری می‌انجامد. XML و CSS پاک‌سازی upstream جای آزمون تمام SVGهای ممکن نیست؛ فایل‌ها به‌صورت img/picture مصرف می‌شوند و متن آزاد SVG وارد HTML نمی‌شود. renderer محدود inline آیکون در Components مالک جدا دارد و از این toggle برای تزریق markup استفاده نمی‌کند.

فیلتر metadata ابعاد مثبت و محدود width/height یا viewBox را از فایل محلی uploads ثبت می‌کند؛ بدون خواندن URL، DTD یا ساخت thumbnail raster برای SVG. PNG/JPEG/WebP/AVIF و سایر انواع را API و مجوز native وردپرس/هاست مدیریت می‌کنند؛ Theme فهرست MIME عمومی را جایگزین نمی‌کند.

## شاهد و باقی‌مانده

قرارداد کوتاه PHP 8.4: پیش‌فرض خاموش، مجوز، script/event/remote، XML/DTD/حجم نامعتبر، باقی‌ماندن شکل و CSS مجاز، hash بایت پاک‌شده و ابعاد؛ همچنین انتخاب تصویر، picture واکنش‌گرا، تصویر بدون لینک خانه و fallback رسانهٔ حذف‌شده پاس شدند. این شاهد اجرای fixtures محلی است؛ بارگذاری واقعی REST/Elementor/Multisite، شکل SVGهای مشتری، WPML واقعی، favicon مرورگر و ظاهر موبایل هنوز پذیرش نشده‌اند. منابع بررسی‌شده: WoodMart `class-logo.php` و `inc/theme-setup.php`؛ Hub `liquid-logo.php`؛ Elementor `core/utils/svg/svg-sanitizer.php` و [بستهٔ upstream](https://packagist.org/packages/enshrined/svg-sanitize).
