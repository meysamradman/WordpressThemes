# وردپرس لوکال مشترک رادمان

## فایل‌های ساخته‌شدهٔ افزونه‌ها — اصلاح ۲۰۲۶-۱۰-۳۰

فرمان‌های PHP که فایل runtime یا کش می‌سازند با کاربر www-data کانتینر اجرا شوند. اجرای اولیهٔ Rocket با root پوشه‌های cache/busting و critical-css را غیرقابل‌نوشتن برای وب کرده بود؛ مالکیت این دو و wp-rocket/min/config اصلاح و writable بودن هر چهار پوشهٔ کش با خود www-data تأیید شد. فایل سورس Rocket تغییر نکرد. پیام خطای مخزن افزونه‌ها در صفحهٔ نصب، از سیاست local/offline و بلوک HTTP بیرونی بود؛ این خطای قالب/مجوز کش نیست. پس از گزارش دوبارهٔ مالک، استثنای محدود HTTPS برای api.wordpress.org و downloads.wordpress.org در local-boundaries.php اضافه شد؛ WP_ACCESSIBLE_HOSTS نیز همین دو میزبان را برای لایهٔ بومی هسته مجاز می‌کند. query_plugins واقعی مخزن پاسخ معتبر داد و مسدودماندن میزبان نامرتبط تأیید شد. نصب خودکار، ارسال ایمیل، آپدیت خودکار و دسترسی عمومی سایر سرویس‌ها فعال نشدند. این تغییر فقط محیط لوکال است و وارد بستهٔ Theme نمی‌شود؛ نصب ZIP بومی نیز برقرار است.

## CONFIRMED — ۲۰۲۶-۱۰-۲۸

مالک یک وردپرس دائمی مشترک برای توسعه و استفادهٔ خودش خواست. محیط جاری همین پروژه `radman-local` در Docker Compose است؛ **محل اصلی کار مشترک مالک و agent، ساخت سایت و تکمیل قالب همین نصب است؛ انتقال سایت به سرور بعداً توسط مالک انجام می‌شود.** agent در کارهای معمول از همین نصب استفاده کند و وردپرس/دیتابیس موقت موازی نسازد. تست نیازمند reset، مهاجرت مخرب یا نصب کاملاً تازه نباید روی دادهٔ این سایت انجام شود؛ نیاز به محیط جدا باید در محدودهٔ همان کار مشخص باشد. محتوای کاربر، رسانه‌ها، تنظیمات و انتخاب افزونه/پوسته در Start بعدی بازنشانی نشوند. این محیط متعلق به WordPress Corporate-Catalog است؛ کانتینرهای Redis و QA پروژه‌های دیگر مستقل‌اند.

## استفادهٔ روزمره

1. در ریشهٔ پروژه روی `WordPress-Start.cmd` دوبار کلیک کنید. در صورت خاموش‌بودن Docker Desktop، اسکریپت برای روشن‌شدن آن تلاش می‌کند. بعد از آماده‌شدن سایت، مدیریت در مرورگر پیش‌فرض باز می‌شود.
2. سایت: <http://127.0.0.1:8094/>؛ مدیریت: <http://127.0.0.1:8094/wp-admin/>.
3. نام کاربری `radman` است. رمز اولیه در `artifacts/local-wordpress-access.txt` همین پروژه قرار دارد؛ این فایل و `.env.local-wordpress` حاوی اطلاعات محلی و خارج از Git هستند. اگر رمز را داخل WordPress تغییر دهید، فایل فقط رمز اولیه را نشان می‌دهد؛ Start رمز را بازنشانی نمی‌کند.
4. پایان کار روی `WordPress-Stop.cmd` دوبار کلیک کنید؛ فقط همین گروه متوقف می‌شود و اطلاعات باقی می‌مانند. روشن‌بودن Docker Desktop برای استفاده لازم است؛ تا وقتی سرویس‌ها روشن‌اند فقط بازکردن آدرس کافی است.

فرمان مشترک agent از ریشهٔ پروژه:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/local-wordpress/manage.ps1 -Action Start
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/local-wordpress/manage.ps1 -Action Status
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/local-wordpress/manage.ps1 -Action Stop
```

اسکریپت Start بدون `-OpenBrowser` مرورگر باز نمی‌کند؛ launcher ریشه این گزینه را برای استفادهٔ مالک می‌فرستد. دادهٔ سایت در volumeهای `radman-local-database` و `radman-local-wordpress` نگهداری می‌شود. این ماندگاری جای بکاپ مستقل را نمی‌گیرد؛ حذف این volumeها یا فرمان `down -v` اطلاعات را حذف می‌کند. فایل `.env.local-wordpress` برای استفادهٔ مجدد از دیتابیس موجود حفظ شود؛ اسکریپت در نبود آن با وجود volume دیتابیس رمز جدید تولید نمی‌کند.

## سورس و امکانات

Compose در `tools/local-wordpress/compose.yaml` است. PHP 8.4، MariaDB 11.4 و نسخه‌های دقیق imageهای موجود با digest ثابت استفاده می‌شوند؛ Start image جدید دریافت نمی‌کند. وردپرس و فایل‌های آپلودشده در volume ماندگارند. مسیرهای `radmanct`، `radmanct-child`، `radmanct-components`، `radmanct-content` و `radmanct-mcp` مستقیماً از همین checkout به نصب وصل‌اند؛ کپی ZIP لازم نیست. Elementor و Pro از مرجع ارسالی `themes/` فقط یک‌بار در volume وردپرس نصب می‌شوند تا هر درخواست فایل‌های زیاد آن‌ها را از Windows bind mount نخواند. مسیر مرجع فقط‌خواندنی است و تغییر نمی‌کند؛ نصب موجود در Start بعدی overwrite یا با نسخهٔ مرجع جایگزین نمی‌شود. کپی اولیه پیش از قرارگرفتن پوشه در مسیر افزونه کامل می‌شود تا فایل ناقص در دسترس نباشد. تغییر بعدی نسخهٔ Elementor/Pro یک اقدام جداگانه است.

پس از نصب اولیه، Child Theme و Components و Content و MCP و Elementor معمولی فعال‌اند؛ دو ماژول کاتالوگ/نمونه‌کار فعال‌اند. **اصلاح مالک، ۲۰۲۶-۱۰-۲۸: Elementor Pro فعلاً نصب ولی غیرفعال بماند**؛ در نصب جاری نیز با API استاندارد غیرفعال شد و Start آن را دوباره فعال نمی‌کند. کامپوننت‌ها و مسیر سفارشی رادمان به Pro نیاز ندارند؛ امکانات مخصوص Pro، مانند Theme Builder آن، تا فعال‌سازی مجدد در دسترس نیستند. طبق درخواست مالک برای آماده‌بودن افزونه‌های خود رادمان، MCP نیز فعال شد ولی گزینهٔ دسترسی MCP همچنان خاموش است و مجوز خواندن/نوشتن به ابزار بیرونی داده نشد. هیچ حساب یا لایسنس بیرونی فعال نشده و دادهٔ سرور وارد نشده است. صفحهٔ سادهٔ Home و پیش‌نویس Elementor sandbox نقطهٔ شروع هستند؛ این سایت کپی سایت مشتری نیست. زبان سایت و کاربر `fa_IR` است؛ در نصب جاری، بستهٔ فارسی هستهٔ WordPress 7.1.3 از `downloads.wordpress.org` یک‌بار دریافت و در volume سایت نصب شد. Startهای بعدی به دریافت دوبارهٔ این بسته نیاز ندارند. ترجمه‌های محصول از سورس محلی می‌آیند.

ویرایش PHP در سورس پس از Refresh دیده می‌شود. برای CSS/JS بسته‌بندی‌شده پس از ویرایش `npm run build` را در ریشه اجرا و صفحه را Refresh کنید. نسخهٔ پنج بستهٔ رادمان در دورهٔ تکمیل روی **1.1.1** ثابت است؛ [قرارداد نسخهٔ توسعه](../scenarios/local-assets.md). نصب sourceهای رادمان فقط‌خواندنی است؛ تغییر قالب/افزونهٔ متصل از ادیتور فایل WordPress یا جایگزین‌کردن آن از داخل پنل انجام نشود. افزونه‌های دیگر در volume WordPress ماندگارند و می‌توان ZIP محلی آن‌ها را نصب کرد.

ورود عادی با رمز برقرار است؛ bypass ورود محیط QA منتقل نشده است. تنها پورت `127.0.0.1:8094` باز است؛ دیتابیس پورت عمومی ندارد. MU-plugin محلی ایمیل و HTTP خارجی را متوقف می‌کند و آپدیت خودکار غیرفعال است. این محدودیت‌ها مخصوص محیط توسعه‌اند و وارد بستهٔ قالب/افزونه نمی‌شوند. برای به‌روزرسانی منبع افزونه‌های متصل از همان مسیر سورس و رویهٔ پروژه استفاده شود.

## بررسی واقعی

راه‌اندازی روی WordPress 7.1.3 و PHP 8.4.26 انجام شد؛ MariaDB 11.4.13 است. پس از Stop/Start، شناسهٔ مدیر، صفحهٔ خانه، تعداد نوشته‌ها و نشانگر نصب حفظ شدند؛ Start موجود را بدون reset تشخیص داد. احراز رمز مدیر با API وردپرس و پاسخ HTTP سایت/صفحهٔ ورود بررسی شدند؛ locale فارسی و RTL نیز از runtime تأیید شدند. خواندن افزونه‌های ثالث از bind mount ویندوز در بررسی اولیه تأخیر داشت؛ با نصب یک‌بارهٔ آن‌ها در volume، درخواست بعدی مدیریت به صفحهٔ ورود HTTP 200 رسید. هنگام جابه‌جایی اولیه، مراجعهٔ هم‌زمان مالک قبل از تکمیل کپی Elementor خطای کلاس History داد؛ پس از تکمیل کپی، درخواست جدید این خطا را نداشت و کپی نصب‌های تازه به مسیر staging تغییر کرد. این شواهد ادعای بنچمارک یا بهینه‌بودن همهٔ صفحه‌ها نیست. در log، deprecationهای PHP 8.4 از Elementor/Pro ارسالی و update-checker آن وجود دارد؛ فایل مرجع تغییر نکرد و هشدارها مخفی نشده‌اند. این بررسی جای پذیرش کامل مرورگر، سازگاری همهٔ امکانات Elementor یا آزمایش هاست را نمی‌گیرد.
