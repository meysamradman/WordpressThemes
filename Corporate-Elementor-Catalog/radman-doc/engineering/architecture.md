# معماری قطعی Radman CT

## افزونهٔ مستقل کامپوننت‌ها — CONFIRMED، ۲۰۲۶-۱۰-۲۱

مالک ساخت افزونه را صریحاً تأیید کرد. بستهٔ مستقل **Radman CT Components** با شناسه و basename ثابت `radmanct-components/radmanct-components.php` ساخته شد. طبق اصلاح مالک در ۲۰۲۶-۱۰-۲۷، این افزونه پیش‌نیاز قالب حتی برای سایت کاملاً سفارشی PHP است؛ Elementor اختیاری می‌ماند. موتورهای PHP، CSS/JS کامپوننت‌ها، کتابخانه و adapterهای Classic/Atomic در همین بسته‌اند؛ نصب Elementor برای مصرف PHP لازم نیست. طبق اصلاح ۲۰۲۶-۱۰-۲۳، آیکون‌های ضروری Theme بدون Components حاضرند؛ موتور و مجموعهٔ پایه سورس مشترک با دو خروجی نصب مستقل دارند و آیکون مشتری در Child ثبت می‌شود. [مالک آیکون‌ها](icons.md). Theme مالک هدر/فوتر، navigation، موشن عمومی، فونت و tokens است؛ Content مالک دادهٔ محصول/نمونه‌کار و MCP مالک اتصال عامل باقی می‌مانند.

helperهای `rdct_*` و شناسه‌های ذخیره‌شدهٔ ویجت‌ها حفظ شدند؛ موتور دوم در قالب باقی نمانده است. نصب/آپدیت از همان زیرساخت بومی بسته‌های محلی انجام می‌شود. تفکیک بسته به‌خودی‌خود افزایش سرعت نیست؛ معیار، enqueue شرطی، استایل منتخب و وابستگی مشترک است. جزئیات و حدود واقعی در [قرارداد کامپوننت‌ها](components.md) است.

ساختار تصویر، فونت، source/build و مالکیت فایل‌های ماژول در [قرارداد دارایی‌ها](assets.md) نهایی است؛ مسیرهای عمومی موازی برای یک نوع فایل ساخته نشوند.

هویت محصول، پیشوندها و استثناهای سازگاری در [قرارداد نام‌گذاری](naming.md) قطعی‌اند؛ Modern CSS همچنان مبنای طراحی است.


تاریخ تصمیم: ۲۰۲۶-۱۰-۱۸ — **CONFIRMED توسط مالک محصول**. این سند جایگزین تصمیم‌های متناقض قبلی درباره فرانت، هاست، مرز Core و دامنه فروشگاه است. فقط جزئیاتی که صریحاً OPEN/PROPOSED هستند نهایی نشده‌اند. معماری تأیید شده، مجوز شروع کدنویسی نیست.

## استک قطعی

### تصمیم نهایی هاست و دیتابیس — CONFIRMED، ۲۰۲۶-۱۰-۲۱

این تصمیم مالک، پیش‌نویس‌های محدود به MariaDB و استثنای قبلی React عمومی را جایگزین می‌کند. محیط پیشنهادی زیر، معیار انتخاب هاست است؛ حداقل فنی و ماتریس واقعاً بررسی‌شده با آن یکی نیستند.

| بخش | محیط پیشنهادی |
|---|---|
| PHP | 8.3 یا بالاتر؛ بررسی سازگاری 8.4 نیز حفظ شود |
| دیتابیس | MySQL 8.0 یا بالاتر **یا** MariaDB 10.11 یا بالاتر؛ فقط یکی لازم است |
| وب‌سرور | Apache یا Nginx با پیکربندی استاندارد WordPress |
| انتقال | HTTPS طبق توصیهٔ WordPress |
| Node.js روی هاست | لازم نیست؛ فقط ابزار توسعه/build است |

این پیشنهاد با [نیازمندی‌های رسمی WordPress](https://wordpress.org/about/requirements/) در تاریخ بررسی مطابق است. دیتابیس را سرویس هاست فراهم می‌کند؛ نصب استاندارد برای مشتری به معنی راه‌اندازی وردپرس، اتصال دیتابیس ارائه‌شدهٔ هاست و نصب بسته‌های رادمان است، نه نصب جداگانهٔ موتور MySQL/MariaDB توسط مشتری.

Theme و افزونه‌های محصول به یکی از دو موتور وابسته نشوند و برای نسخهٔ پایین‌تر دیتابیس که نسخهٔ هدف WordPress پشتیبانی می‌کند، بدون نیاز فنی مستند مانع نصب/اجرا نسازند. پشتیبانی هسته از نسخهٔ قدیمی، به معنی توصیهٔ آن محیط یا آزموده‌شدن همان ترکیب با رادمان نیست. عدد پیشنهادی به‌تنهایی شرط hard-fail در کد یا metadata نصب نشود؛ تغییر حداقل PHP نیز تصمیم جدا از این جدول است. metadata فعلی بسته‌ها PHP 8.0 را اعلام می‌کند؛ این یادداشت آن را به 8.3 تغییر نمی‌دهد و جای ماتریس اجرا را نمی‌گیرد.

خواندن/نوشتن داده با API رسمی WordPress باشد: WP_Query، taxonomy/metadata/options APIs؛ در نیاز واقعی به SQL مستقیم، از همان اتصال `$wpdb`، prefixهای آن و prepare استفاده شود. اتصال موازی PDO/mysqli، نام دیتابیس/جدول ثابت یا SQL اختصاصی یک vendor مبنای قابلیت عمومی نباشد. CAS ذخیرهٔ سازنده اکنون از `$wpdb->prepare()` و جدول options وردپرس استفاده می‌کند؛ این مشاهدهٔ سورس است، نه تأیید runtime هر دو موتور. رفرنس API: [wpdb](https://developer.wordpress.org/reference/classes/wpdb/).

سیاست JavaScript در [منابع محلی](../scenarios/local-assets.md) است: Vanilla JS ماژولار برای فرانت، CSS برای حرکت ساده، GSAP شرطی برای حرکت پیشرفته، React فقط رابط مدیریتی/Builder. jQuery داخلی WordPress برای افزونه‌های دیگر آزاد بماند؛ کد اختصاصی رادمان هیچ dependency مستقیم یا مصرف jQuery نداشته باشد. اجرای محصول روی هاست اشتراکی استاندارد WordPress و بدون Node runtime الزامی است.

| بخش | انتخاب |
|---|---|
| بک‌اند و رندر عمومی | WordPress + PHP Server Rendering |
| ساختار | HTML5 معنایی و HTML اولیه آماده |
| طراحی | Modern CSS: Grid، Flexbox، CSS Variables و Container Queries |
| تعامل عمومی | Vanilla JavaScript ماژولار |
| انیمیشن اختیاری | GSAP + ScrollTrigger، محلی و فقط در محل نیاز |
| توسعه و Build assets | Vite؛ Node.js فقط محیط توسعه/build |
| مدیریت و رابط پیچیده | React برای تنظیمات، Header/Footer Builder و ابزارهای مدیریت کاتالوگ/فیلد |
| محتوای استاندارد | Gutenberg |
| صفحه‌ساز ثالث | Elementor اختیاری، با سازگاری Elementor Pro طبق سناریوی مربوط |

Tailwind یا Bootstrap وابستگی استک پایه نیستند؛ CSS اختصاصی طبق تصمیم بالا استفاده می‌شود. افزودن ابزار موازی build یا framework عمومی نیازمند تصمیم جداست.

## اجرای محصول و رندر صفحات

روی هاست معمولی WordPress با PHP و دیتابیس اجرا شود؛ هیچ فرایند Node.js، Next.js، Headless WordPress یا React SPA برای محصول پایه لازم نباشد. تمام فایل‌های لازم در بسته انتشار آماده باشند.

صفحه اختصاصی مشتری با PHP/HTML، CSS، Vanilla JS، انیمیشن اختیاری و محتوای دیتابیس ساخته شود. HTML اصلی نباید منتظر hydration یا دریافت JS باشد. طراحی مشتری به template ثابت محدود نشود؛ الگوها فقط نقطه شروع‌اند.

React در کد اختصاصی رادمان برای رابط‌های مدیریت و Builderهای پیچیده از `@wordpress/element` و runtime موجود WordPress تأمین شود؛ bundle مدیریت وارد فرانت نشود و نمایش عمومی به React نیاز نداشته باشد. استثنای عمومی قبلی با تصمیم ۲۰۲۶-۱۰-۲۱ کنار گذاشته شد. پیشنهاد مشروط React مستقل `19.3.1` و مرز بررسی نیاز/سازگاری در [قرارداد React مدیریت](admin-ui.md) ثبت شده است و به معنی نصب فعلی یا runtime دوم در پنل نیست. وابستگی‌های داخلی افزونهٔ ثالث جدا از استک کد اختصاصی رادمان هستند و قالب آن‌ها را دستکاری نمی‌کند.

در صفحه منتخب Elementor مسیر استاندارد content، hookها، فایل‌ها و چرخه widget حفظ شوند؛ دیگر صفحات PHP مستقل باشند. انتخاب برگه از دو Page Template استاندارد «طراحی اختصاصی رادمان» و «رادمان — المنتور با هدر و فوتر» استفاده می‌کند و meta موازی برای renderer ندارد؛ اتصال native Atomic/V4، مرز فونت و وضعیت فعال‌سازی در [قرارداد و بررسی محدود](elementor.md) است. تبدیل محتوای روش‌ها و schema پیشرفتهٔ محتوای اختصاصی هنوز OPEN است. انتخاب طراحی اختصاصی/Elementor Pro برای آرشیو و جزئیات وبلاگ، محصول و نمونه‌کار جداگانه ساخته شده؛ [قرارداد renderer](renderers.md). Theme Builder جایگزین هدر/فوتر رادمان نیست.

## مرز Theme و Core

- **Radman CT Theme:** نمایش صفحات/آرشیو/جزئیات، طراحی و tokens، تنظیمات ظاهری و سازنده‌های هدر/فوتر با رندر PHP/HTML.
- **Radman CT Core:** ثبت CPT/Taxonomy/Metadata و منطق داده کاتالوگ، جستجو/فیلتر و استعلام؛ ابزار مدیریت کاتالوگ/فیلدهایش. UI پیچیده مدیریت می‌تواند React باشد.
- **ادغام اختیاری:** Elementor/Pro و WPML از API رسمی و فقط هنگام حضور؛ قالب بدون آن‌ها برای سایت تک‌زبانه استاندارد کار کند.
- **Radman CT MCP:** افزونهٔ اختیاری مستقل و یکپارچه با ماژول‌های داخلی Content/Theme/Elementor؛ برگه/وبلاگ آن به افزونهٔ محتوا وابسته نیست. transport به Adapter رسمی سپرده می‌شود و ابزارها validator/storage مالک خود را مصرف می‌کنند؛ [قرارداد](mcp.md). نام نهایی افزونهٔ داده Radman CT Content است؛ مسیر و namespace در [نام‌گذاری](naming.md) ثبت‌اند.
- Core برای سایت بدون کاتالوگ الزام نباشد؛ Theme نبود آن را تحمل کند، قابلیت وابسته را با وضعیت روشن غیرفعال کند و بدون fatal کار کند. داده‌ها با تعویض Theme مستقل بمانند.
- غیرفعال‌بودن ماژول باید واقعاً ثبت hook/endpoint/job و بارگذاری فایل/کوئری اختصاصی غیرلازم را حذف کند؛ روی صفحه نامرتبط نیز ماژول فعال نباید خواندن داده سنگین یا assets اضافه داشته باشد. پیکربندی/registry سبک مجاز است. قرارداد ویرایشگر، routeها، کش و داده موجود هنگام خاموشی پیش از پیاده‌سازی مشخص شود؛ خاموشی داده را حذف نکند.
- WooCommerce، سبد، پرداخت، ادغام/مهاجرت فروشگاهی و زیرساخت آینده آن در هیچ بسته Radman CT ایجاد نشود؛ فروشگاه محصول جداست.

ماژول‌ها مالک روشن برای setup، rendering، builder، settings، assets، integration و داده داشته باشند. اجزای مشترک واقعی تکرار نشوند. افزونهٔ `radmanct-content/` با ماژول‌های مستقل محصول/نمونه‌کار ساخته شده؛ [قرارداد داده و نمایش](content-modules.md) مالک جزئیات و حدود است. پایه Theme و Child در مرحله اول ساخته شده‌اند؛ وضعیت در سند پیاده‌سازی است.

سناریوی استفادهٔ مشترک از قابلیت نمایشی در PHP و ویجت اختیاری Elementor تأیید و پایهٔ اجرایی Text Reveal و آیکون در Theme ساخته شده‌اند؛ [سناریو](../scenarios/components.md) و [قرارداد فنی](components.md) مرجع آن‌اند. استقلال از Core/Elementor برای مصرف PHP حفظ شده؛ این نیاز مجوز واردکردن همهٔ ویجت‌های قالب مرجع نیست. پذیرش بصری/ویرایشگر و WPML واقعی همچنان باقی است.

## سازنده هدر/فوتر

بلوک محتوایی مشترک اولیه از دادهٔ داخلی `wp_block` استفاده می‌کند؛ renderer ظاهری در Theme و بدون وابستگی به Core است. [قرارداد بلوک مشترک](content-blocks.md) جای پیشنهاد مالکیت Core برای این بخش را گرفته؛ مرز مستقل کاتالوگ تغییری نکرده است.

انتخاب قطعی: پنل Drag & Drop با React، خروجی عمومی PHP/HTML بدون نیاز React. schema نسخهٔ ۱، optionهای بدون autoload، چیدمان نام‌دار، SQL compare-and-swap برای revision هر چیدمان، تخصیص برگه/زبان/سایت، پیش‌نمایش خصوصی PHP و پشتیبان همان سایت پیاده شده‌اند؛ مرجع دقیق و شواهد [قرارداد سازنده](builder.md) است. موارد زیر همچنان PROPOSED برای مراحل بعدند:

- ستون‌های تودرتو و overrideهای responsive بیشتر؛ بدون PHP/JS یا style آزادِ بدون کنترل.
- تخصیص مستقل بر اساس نوع محتوا، فراتر از اولویت فعلی برگه > زبان > سایت > اصلی؛ تعارض هم‌سطح رد شود.
- تراکنش مشترک تخصیص‌ها و دادهٔ چیدمان‌ها، فراتر از CAS فعلی دادهٔ هر چیدمان.
- انتقال میان سایت‌ها با remap ارجاع منو/بلوک/رسانه و preview تعاملی افزونه‌ها؛ پشتیبان فعلی فقط همان سایت است.
- migration نسخه‌دار همراه backup و حفظ داده قبلی در شکست؛ تولید/کش CSS هنگام تغییر وابستگی، نه محاسبه سنگین در هر درخواست. شکست نوشتن فایل خروجی را خالی نکند.

## Build و دارایی‌ها

Vite فایل‌های CSS/JS عمومی و مدیریت را با ورودی‌های مستقل و dependency مشترک روشن می‌سازد؛ build فقط توسعه/انتشار است و فایل نهایی روی هاست مشتری اجرا می‌شود. پنل تنظیمات و سازندهٔ اولیه از React موجود WordPress با `wp-element` استفاده می‌کنند؛ React تکراری bundle نشده است. manifest minified اتصال PHP و dependencyهای entryها را مشخص می‌کند.

CSS معمولی و minified از منبع واحد تولید شوند؛ قالب همیشه minified را مصرف کند، در مدیریت و عمومی و RTL/LTR، حتی debug. فایل تولیدی سازنده/fallback نیز قرارداد minified را رعایت کند. این build assets قالب است، نه موتور minify کل سایت.

فایل هر جزء فقط در صفحه نیازمند، CSS/JS مدیریت فقط در صفحه مدیریت مرتبط و انیمیشن فقط در محل فعال بارگذاری شود. enqueue با handle/dependency روشن؛ GSAP/ScrollTrigger محلی و بدون تکرار؛ cleanup رویداد و animation در تعویض/preview مناسب انجام شود.

منابع self-hosted و بدون CDN/API اجباری یا دانلود کتابخانه هنگام فعال‌سازی باشند؛ جزئیات منع اتصال خارجی در سناریوی منابع محلی است. عملکرد موبایل، تصاویر واکنش‌گرا، فونت/وزن محدود، جلوگیری از CLS و کاهش حرکت از ابتدا لحاظ شوند. سرعت با سنجش ثابت شود.

## داده، چندزبانه و سفارشی‌سازی

کاتالوگ با API استاندارد WordPress در Core؛ شناسه‌های نسخهٔ پایه و slugهای فعلی در [قرارداد محتوا](content-modules.md) ثبت شده‌اند. داده عمومی در post و داده ساختاریافته در meta معتبر؛ taxonomy برای فیلتر پرتکرار. schema مشخصات: کلید پایدار، نوع، واحد، مقدار و وضعیت فیلتر؛ تغییر عنوان کلید را عوض نکند. جدول اختصاصی یا meta_query سنگین بدون نیاز/اندازه‌گیری انتخاب نشود.

Gutenberg برای محتوای استاندارد؛ schema پیشرفته محتوای اختصاصی مشتری OPEN است. محدودیت template عمومی نباید طراحی را قفل کند. لایه سفارشی‌سازی با Child Theme استاندارد و نمونه `radmanct-child/` پیاده‌سازی شده است؛ مسیر استایل/صفحات و روند build در [راهنمای مشتری](client-customization.md) ثبت شده‌اند.

RTL/LTR و WPML، ترجمه متن ثابت PHP/JS و متن واردشده توسط مدیر، نگاشت شناسه ترجمه، URL زبان و کش زبان رعایت شوند. قرارداد داده Core و سازنده برای WPML قابل‌شناسایی و قواعد translate/copy/ignore پس از schema تعیین شوند. فونت و tokens از مرجع سراسری قالب؛ قرارداد جلوگیری از override/دانلود فونت Elementor در سناریوی تایپوگرافی محفوظ است.

## کیفیت و امنیت

PHP تمیز و ماژولار با WordPress Coding Standards، namespace/prefix و مسئولیت محدود؛ سازگاری خانواده PHP 8 خصوصاً 8.4، بدون syntax فراتر از حداقل منتخب یا پنهان‌کردن warning/deprecation. namespace پیشنهادی Radman CT، text domainهای مستقل بسته‌ها و prefix روشن.

مستندات توضیحی در radman-doc، نه source یا docblock/JSDoc توضیحی. شناسه/کامنت فنی/رشته مبنای رابط انگلیسی، ترجمه فارسی در منابع ترجمه؛ metadata و licenseهای الزامی حفظ شوند.

مجوز سمت سرور در هر endpoint و عملیات، nonce مناسب بدون جایگزینی capability، validation/schema/allowlist، escape متناسب زمینه، SQL آماده در کوئری مستقیم و کنترل مسیر/نوع/مجوز فایل. خواندن داده را تغییر ندهد، payload محدود و preview/private data از پاسخ/کش عمومی جدا باشند. این قرارداد شامل Theme و Core است. فعلاً endpoint ثبت‌نام/حساب عمومی جدید نداریم.

بررسی موضعی WoodMart کنترل nonce، sanitization و برخی capabilityها را نشان داده است؛ آن مشاهده ممیزی امنیتی نیست و کپی الگو مجوز حذف کنترل در handler رادمان نیست. SEO engine، firewall، cache engine یا minifier کل سایت داخل محصول ساخته نشود.

## تصمیم‌های فنی باقی‌مانده

Vite 8.3.4 و GSAP 3.15.0 در lockfile تثبیت شده‌اند؛ نسخهٔ موتور کاروسل در [قرارداد کاروسل](carousel.md) ثبت است. محیط توسعهٔ بررسی‌شده Node 24.15 و lint روی PHP 8.4.26 است. React از WordPress می‌آید و نسخهٔ جداگانه pin نشده؛ Drag & Drop بومی مرورگر است. ماتریس کامل نسخه‌های WordPress/PHP و افزونه‌های هدف هنوز تست نشده است. Core مستقل، کتابخانهٔ چیدمان/CAS و فیلتر پایه ساخته شده‌اند. فیلد/فیلتر پیشرفته، طرح نهایی مشتری، ماتریس افزونه‌ها و بودجهٔ عملکرد پس از baseline همچنان OPEN هستند؛ فرم و پردازش درخواست با اصلاح مالک طبق [سناریوی محتوا](../scenarios/content.md) فعلاً DEFERRED است. اصل استک، PHP SSR، نقش React، Vite، Core مستقل و خارج‌بودن WooCommerce دیگر OPEN نیستند.
