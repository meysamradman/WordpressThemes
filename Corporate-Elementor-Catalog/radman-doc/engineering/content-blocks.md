# بلوک مشترک — قرارداد اولیه

وضعیت: پیاده‌سازی اولیه با دادهٔ استاندارد WordPress؛ نصب واقعی وردپرس، ویرایشگر الگو و WPML هنوز تست نشده‌اند. نیاز محصول در [سناریوی بلوک‌ها](../scenarios/reusable-blocks.md) است.

## مالکیت و مدیریت

از نوع محتوای داخلی `wp_block` استفاده می‌شود؛ CPT یا جدول اختصاصی و افزونهٔ جدید ایجاد نشده است. الگوی وردپرس در هدر/فوتر با ID ارجاع داده می‌شود؛ محتوا کپی نمی‌شود و ویرایش منبع، همهٔ محل‌های مصرف را تغییر می‌دهد. داده با تغییر قالب باقی می‌ماند. این تصمیم جای پیشنهاد قبلی «ماژول بلوک در Core» را برای نسخهٔ پایه می‌گیرد؛ دادهٔ کاتالوگ همچنان متعلق به Core مستقل است.

اصلاح مالک ۲۰۲۶-۱۱-۰۱: ورودی «بلوک‌های محتوایی مشترک» از منوی رادمان و افزودن/انتخاب آن از سازنده حذف شد؛ صفحه یا ویرایشگر موازی لازم نیست. قابلیت اصلی الگوها و دادهٔ `wp_block` وردپرس باقی می‌مانند. طراحی سفارشی از قطعهٔ PHP ثبت‌شدهٔ Child و کار المنتوری از Template خود Elementor استفاده می‌کند. schema و renderer ارجاع‌های قدیمی فقط برای سازگاری باقی می‌مانند؛ دادهٔ کاربر حذف یا مهاجرت خودکار نمی‌شود.

سازنده دیگر فهرست الگوها را query یا در config ارسال نمی‌کند؛ گزینهٔ بلوک در عناصر، منبع پنل و انتخاب‌گرهای مربوط نمایش ندارد. در frontend نیز فهرست الگوها query نمی‌شود؛ برای ارجاع قدیمی فقط IDهای مصرف‌شده با object cache عادی وردپرس خوانده می‌شوند.

## دامنهٔ رندر

عنصر `block` در schema سازنده، `blockId` عددی مثبت دارد. نسخهٔ اولیه برای محتوای پایه است: paragraph، heading، image، list/list-item، quote، group، columns/column، buttons/button، separator، spacer، table و gallery. `core/block` برای ارجاع تو‌در‌تو پذیرفته می‌شود. HTML آزاد، shortcode، فرم، query loop، embed و blockهای افزونه‌ها در renderer فعلی پذیرفته نمی‌شوند؛ مدیریت native الگوهای نامرتبط سایت محدود نمی‌شود.

پیش از رندر، کل درخت بررسی می‌شود: نوع `wp_block`، وضعیت publish و نبود password در تمام ارجاع‌ها الزامی است. محتوای هر منبع حداکثر ۱۲۸ KiB، مجموع حداکثر ۲۵۶ node، عمق ساختار ۱۶ و زنجیرهٔ حداکثر ۸ منبع است. حلقه، منبع مفقود/غیرعمومی، نوع نامجاز یا تجاوز از حد، خروجی همان عنصر را خالی می‌کند؛ داده پاک نمی‌شود و قسمت‌های دیگر layout باقی می‌مانند.

رندر از `render_block` وردپرس استفاده می‌کند، نه اجرای `the_content`، PHP یا shortcode دلخواه. guard موقت `pre_render_block` فقط در همین رندر نصب و با `finally` حذف می‌شود؛ حفاظت ارجاع‌ها به بخش‌های دیگر سایت تحمیل نمی‌شود. خروجی با KSES استاندارد وردپرس محدود می‌شود. IDهای HTML و لینک‌های fragment/ارجاع‌های ARIA در هر محل مصرف prefix می‌گیرند تا استفادهٔ یک الگو در هدر و فوتر ID یکسان تولید نکند؛ anchorهای بیرونی الگو در این مرحله قرارداد عمومی ندارند.

برای مسیر استاندارد قالب، fragment هر محل مصرف در `wp_enqueue_scripts` آماده می‌شود تا enqueueهای native آن پیش از چاپ دارایی‌ها شروع شوند؛ همان HTML در template مصرف می‌شود و دوباره رندر نمی‌شود. cache فقط در حافظهٔ همان درخواست و برای همان kind/item است، نه HTML مشترک همهٔ زبان‌ها/محل‌ها. تولید و جای‌گذاری styleهای block support همچنان با WordPress است و باید در نصب واقعی بررسی شود. اگر چیدمان هیچ عنصر بلوک نداشته باشد، ماژول `content-blocks.php` در frontend بارگذاری نمی‌شود.

## زبان و باقی‌مانده

هر ID، از جمله ارجاع‌های داخلی، با `wpml_object_id` برای نوع `wp_block` و بدون fallback خودکار به زبان اصلی نگاشت می‌شود. نبود WPML همان ID را نگه می‌دارد؛ با حضور WPML، نبود ترجمه یا ترجمهٔ draft/protected خروجی ندارد. وجود hook به معنی تأیید ترجمهٔ الگوها در نسخهٔ خاص WPML نیست.

ادغام فرم/Elementor/ویجت ثالث در بلوک، selector با جستجوی بزرگ، کنترل خطای داخل ویرایشگر native و تست واقعی assetهای Gutenberg/WPML مراحل بعدند. این renderer اولیه جای پشتیبانی کامل HTML Blocks وودمارت را نمی‌گیرد و سورس آن کپی نشده است.
