# اتصال اختیاری MCP رادمان

مالک رفتار محصول [سناریوی MCP](../scenarios/ai-mcp.md) است. درخواست ۲۰۲۶-۱۰-۲۱ شروع پیاده‌سازی را مجاز کرد؛ این سند جای تأیید اتصال واقعی کلاینت را نمی‌گیرد.

## مرجع و معماری

بررسی تازهٔ مستندات رسمی در ۲۰۲۶-۱۰-۲۱: [راهنمای نصب Adapter](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/getting-started/installation.md) نصب به‌صورت وابستگی افزونه را توصیه می‌کند و bundle کردن به شکل کتابخانهٔ Composer را به‌دلیل تداخل نسخه‌ها توصیه نمی‌کند؛ [مهاجرت 0.7.0](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/migration/v0.7.0.md) نیز خروج از vendor به افزونهٔ canonical را شرح می‌دهد. بنابراین پیشنهاد قبلی گفتگو مبنی بر اینکه برای نصب واحد «باید» Adapter را داخل رادمان گذاشت، تصمیم فنی تأییدشده نیست و اصلاح می‌شود. ساختار جاری یک افزونهٔ اختصاصی رادمان با ماژول‌های داخلی و یک Adapter رسمی مشترک است؛ بسته‌بندی یکپارچه انجام نشده و صرف تعداد کمتر افزونه شاهد سرعت بیشتر نیست.

در Elementor 4.3.5 ارسالی، `modules/mcp/module.php` ابزارهای native نظیر get-structure، build-composition، manage-elements و update-settings را ثبت می‌کند. فعال‌شدن exposure و شرط V4 متعلق به خود Elementor است؛ وجود فایل به معنی آماده‌بودن همهٔ ابزارها روی هر سایت یا سند کلاسیک نیست. مستند رسمی [MCP overview](https://github.com/elementor/elementor/blob/main/docs/atomic-builder/mcp/overview.md) و [manage-elements](https://github.com/elementor/elementor/blob/main/docs/atomic-builder/mcp/abilities/manage-elements.md) با Context7 بررسی شدند. رادمان JSON خصوصی Elementor یا renderer آن را بازنویسی نمی‌کند.

موجودی دوباره در ۲۰۲۶-۱۰-۲۱ بررسی شد: `themes/woodmart-mcp/` نسخهٔ 1.0.2، `themes/ai/` نسخهٔ 1.4.0 و `themes/mcp-adapter/` نسخهٔ 0.7.1 موجودند. گزارش قبلیِ نبود سورس WoodMart MCP دیگر مبنای کار نیست. bootstrap، مجوزها، پنل اتصال، ابزارهای محتوا/تنظیمات/لوگو/چیدمان و بخش صف Gutenberg خود افزونه بررسی شدند. افزونهٔ ثالث EMCP با MCP رسمی Elementor یا این سه بسته یکی نیست و به رادمان اضافه نشده است.

### ساختار واقعی مرجع WoodMart

| لایه | نقش بررسی‌شده |
|---|---|
| WoodMart MCP 1.0.2 | عملیات قالب را با namespace `woodmart/` در Abilities API ثبت می‌کند؛ جستجو/ایجاد/ویرایش محتوا، خواندن/تغییر تنظیمات، لوگوی هدر، چیدمان و شرط نمایش، ابزارهای درخت Gutenberg و صف تغییر |
| AI 1.4.0 | افزونهٔ رسمی WordPress برای AI experiments، مرور abilities، تولید/ترجمه/ویرایش محتوا و اتصال provider؛ ابزارهای اختصاصی WoodMart در خود WoodMart MCP ثبت می‌شوند |
| MCP Adapter 0.7.1 | Abilities را به ابزارهای MCP ارائه می‌کند؛ سرور پیش‌فرض ابزارهای discover/get-info/execute دارد و permission هر Ability را رعایت می‌کند |
| Remote bridge روی کامپیوتر عامل | پنل WoodMart تنظیمات `npx -y @automattic/mcp-wordpress-remote@latest` را برای STDIO کلاینت می‌سازد؛ پل به endpoint سایت با نام کاربر و Application Password متصل می‌شود |
| Skill کلاینت | دستورالعمل استفاده از ابزارها؛ سرور MCP یا مجوز وردپرس نیست و خودش endpoint نمی‌سازد |

`inc/class-plugin.php` ادغام را پس از `after_setup_theme` و فقط با API فعال WoodMart راه می‌اندازد. `inc/class-main.php` handlerهای کوچک و مشترک می‌سازد؛ `class-permission.php` علاوه بر edit_posts، مجوز رکورد، ایجاد و انتشار را جدا بررسی می‌کند. پنل `inc/admin/class-agents.php` برای Claude Desktop/CLI، Codex Desktop/CLI و Cursor خروجی JSON/TOML یا فیلدهای جدا تولید می‌کند. `assets/js/mcp.js` با REST بومی `wp/v2/users/me/application-passwords` و nonce رمز برنامه می‌سازد؛ رمز تازه در همان رابط به config تزریق می‌شود، رمز قبلی از hash وردپرس بازیابی نمی‌شود.

`inc/admin/class-dependencies.php` افزونه‌های AI و Adapter را وابستگی اعلام و مسیر نصب/فعال‌سازی دارد. این انتخاب WoodMart به معنی نیاز ذاتی Abilities رادمان به افزونهٔ AI نیست: ثبت/اجرای ابزارهای فعلی رادمان بر Abilities داخلی WordPress متکی است. AI ارسالی حداقل WordPress 7.0.3 و Adapter ارسالی حداقل 6.9 را اعلام می‌کنند؛ حداقل Theme/Core پایه تغییر نمی‌کند. تولید محتوا داخل افزونهٔ AI به connector/provider پیکربندی‌شده مربوط است؛ اتصال عامل موجود به MCP به‌خودی‌خود کلید provider جدید در قالب نمی‌خواهد.

در Gutenberg، فایل‌های `class-pending-changes.php` و `queue/class-finalization.php` تغییر درخت بلوک را با محتوای پایه/hash صف می‌کنند؛ برخی تغییرات تا بازشدن صفحهٔ AI Block Queue و پایان finalization زنده نمی‌شوند. pre-flight مجوز/تعارض، آماده‌سازی و سپس نوشتن وجود دارند؛ مراحل localization تصاویر می‌توانند دریافت منبع خارجی داشته باشند. این الگو هنوز در رادمان کپی یا اجرا نشده است؛ ابزارهای فعلی رادمان ذخیرهٔ native دارند و queued گزارش نمی‌شوند. ابزارهای این مرجع عمدتاً Gutenberg و API خود WoodMart هستند؛ از آن‌ها سازگاری native Atomic رادمان نتیجه گرفته نمی‌شود.

بخش‌هایی که برای رادمان مفیدند: تفکیک عملیات از transport، تشخیص وابستگی، راهنمای تنظیم کلاینت، مجوزهای رکورد، کنترل تعارض، schema معتبر و راهنمای عامل. دانلود خودکار وابستگی/skill، کتابخانهٔ دموی خارجی، `@latest` اجباری، غیرفعال‌کردن TLS برای میزبان local و موتورهای عمومی مرجع به رادمان منتقل نمی‌شوند. پنل تشخیص وابستگی/نشانی و راهنمای اتصال در ۲۰۲۶-۱۰-۲۹ تکمیل شد؛ تولید config مخصوص هر کلاینت و skill اختصاصی مشتری هنوز ساخته نشده‌اند؛ skillهای فعلی `.agents/` برای توسعهٔ مخزن هستند.

یک اصلاح محدود از مرجع اعمال شد: schema شیء بدون فیلد اجباری در رادمان `default={}` دارد تا ورودی null در API بومی نیز معتبر بماند. در Adapter ارسالی، متاتول execute-ability خودِ کلید `parameters` را الزامی می‌داند و ابزار بدون آرگومان با `parameters={}` فراخوانی می‌شود؛ نبود این کلید را نباید با آرگومان تهی ابزار یکی دانست. اصلاح محدود به schema رادمان است و filter عمومی روی توانایی‌های افزونه‌های دیگر نصب نمی‌کند.

افزونهٔ مستقل `radmanct-mcp/` از Abilities API وردپرس استفاده می‌کند؛ transport/protocol، credential store یا سرور Node اختصاصی ندارد. [Adapter رسمی](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/guides/default-server.md) ابزارهای دارای `meta.mcp.public=true` را در سرور پیش‌فرض کشف می‌کند؛ endpoint معمول آن `mcp/mcp-adapter-default-server` زیر REST URL همان سایت است. نام MCP و URL واقعی از نسخه/پیکربندی Adapter نصب‌شده گرفته شوند؛ تشخیص class به‌تنهایی اثبات endpoint یا اتصال موفق نیست. dispatcher نسخهٔ 0.7.1 ارسالی بررسی شد؛ هم‌زیستی واقعی Elementor و اتصال کلاینت هنوز پذیرش جدا می‌خواهند.

Abilities به WordPress 6.9+ یا پیاده‌سازی سازگار نیاز دارند؛ حداقل Theme/Core بدون MCP همان 6.6 باقی است. Adapter جدا نصب و پیکربندی می‌شود؛ رادمان دانلود/فعال‌سازی خودکار یا اتصال خارجی ایجاد نمی‌کند. native application passwords و HTTPS مسیر اتصال کاربر به سایت‌اند؛ رمز در option قالب یا پاسخ ابزار ذخیره/برگردانده نمی‌شود. هیچ دارایی frontend اضافه نشده است.

## CONFIRMED و پیاده‌شده — بستهٔ مستقل و مرز ماژول‌ها، ۲۰۲۶-۱۰-۲۱

مالک یک افزونهٔ یکپارچهٔ MCP با ماژول‌های داخلی خواست. `radmanct-mcp/radmanct-mcp.php` ساخته و کد MCP از افزونهٔ محتوا خارج شد؛ دادهٔ محصول/نمونه‌کار و تنظیمات ظاهری قالب جابه‌جا نشدند. افزونهٔ محتوا با نام، پوشه و text domain نهایی `radmanct-content` و namespace برابر `RadmanCTContent` یکدست شد. با دستور مالک، سازگاری با بستهٔ آزمایشی قبلی پیاده نمی‌شود؛ [قرارداد نام‌گذاری و آپدیت آینده](naming.md). وابستگی‌های رسمی در محصول کپی یا ادغام نشدند؛ بستهٔ AI برای ابزارهای فعلی اجباری نیست.

دلیل تفکیک، امکان استفاده از ابزارهای برگه/وبلاگ بدون نصب Core کاتالوگ، غیرفعال‌سازی و آپدیت مستقل، و مالکیت روشن اتصال است. تعداد افزونه یا پوشه به‌تنهایی سرعت را تعیین نمی‌کند و افزایش سرعت اندازه‌گیری‌شده از این پیشنهاد نتیجه نمی‌شود. bootstrap سبک، ثبت شرطی ابزارها، query محدود و نبود فایل عمومی غیرلازم معیار اجرا هستند.

| مالک | مسئولیت پیشنهادی |
|---|---|
| Theme | نمایش، سازنده و validator/storage هدر/فوتر؛ رابط MCP منطق آن‌ها را دوباره نسازد |
| Core | داده و validator محصول/نمونه‌کار؛ نبودش ابزارهای برگه/وبلاگ MCP را متوقف نکند |
| Radman CT MCP | ابزارها، مجوز اتصال و نوشتن، تشخیص وابستگی، تنظیمات/راهنمای اتصال و ادغام‌های کوچک با مالک‌های بالا |
| Adapter رسمی | transport، پروتکل و احراز هویت استاندارد؛ کپی vendor یا سرور موازی ایجاد نشود |
| Elementor | طراحی و ذخیرهٔ سندهای خودش با ابزار رسمی؛ ادغام رادمان فقط قابلیت موجود را تشخیص و مرز مالکیت را رعایت کند |

فایل ورودی افزونه bootstrap و ترجمه را راه‌اندازی می‌کند. `inc/bootstrap.php` بارگذاری سبک و شرطی، `inc/abilities/` ابزار/schema، `inc/admin/` تنظیمات و `inc/integrations/` اتصال‌های مستقل Content/Theme/Elementor را مالک‌اند. فایل‌های اجرایی ابزارها فقط هنگام راه‌اندازی Abilities registry خوانده می‌شوند؛ تنظیمات مدیریت فقط در درخواست مدیریت وارد می‌شوند. در صفحهٔ عمومی CSS/JS اختصاصی MCP نداریم. فقط فایل و زیرگروه لازم ساخته شود؛ CSS/JS احتمالی مدیریت آینده طبق قرارداد دارایی‌ها در `src/css/admin/` و `src/js/admin/` می‌مانند. validator و storage مالک محتوا/سازنده کپی نشده‌اند.

تنظیمات MCP همان دو option مستقیم `radmanct_mcp_enabled` و `radmanct_mcp_write` هستند؛ bootstrap سازگاری، alias و مهاجرت با دستور مالک حذف شدند. کد و پنل MCP در سورس Content وجود ندارند. صفحهٔ مستقل «تنظیمات ← Radman CT MCP» settings group خودش را دارد؛ خاموش/غیرفعال‌کردن افزونه داده را حذف نمی‌کند. توزیع مستقل در `artifacts/radmanct-mcp-0.1.0.zip` است و به ZIP قالب یا Content وابسته نیست. کارت‌های MCP/Adapter در فهرست افزونه‌های قالب وضعیت و مسیر نصب native نشان می‌دهند؛ نصب خودکار نداریم.

## تنظیمات و اختیار

پنل مستقل MCP دو کنترل دارد: فعال‌سازی ابزارها و اجازهٔ تغییر محتوا/چیدمان؛ هر دو پیش‌فرض خاموش‌اند. حالت فقط‌خواندنی ابزار نوشتن را ثبت نمی‌کند. در حالت خاموش فایل‌های اجرایی ابزارها خوانده و توانایی‌های رادمان ثبت نمی‌شوند. در هر اجرای ابزار، وضعیت تنظیم و `manage_options` دوباره بررسی می‌شوند؛ قابلیت‌های edit/publish/assign_terms و edit_theme_options هم در مالک native رعایت می‌شوند. نسخهٔ فعلی مخصوص مدیر است؛ دسترسی نقش‌های دیگر هنوز ارائه نشده است.

`meta.public=false` و `show_in_rest=false` مانع معرفی یک API عمومی موازی برای توانایی‌ها هستند؛ exposure برای MCP صریح است و permission callback همچنان لازم است. این کلید، حالت ناشناس نیست. فعال‌کردن رادمان، MCP خود Elementor را روشن نمی‌کند؛ مدیر آن را مستقل تنظیم می‌کند. ثبت قابلیت یا annotation مجوز خواندن/نوشتن را جایگزین نمی‌کند.

## ابزارهای ساخته‌شده

| توانایی | رفتار |
|---|---|
| `radmanct/site-context` | هویت سایت/محیط/locale، انواع فعال، وضعیت نوشتن، چیدمان‌های نام‌دار و ابزارهای رسمی Elementor که واقعاً ثبت شده‌اند |
| `radmanct/list-content` | فهرست برگه/نوشته/محصول/نمونه‌کار، حداکثر ۲۰ نتیجه در هر صفحه؛ بدون بدنهٔ کامل |
| `radmanct/list-media` | جست‌وجوی تصاویر موجود رسانه با شناسه، نشانی، متن جایگزین، ابعاد و thumbnail؛ حداکثر ۲۰ نتیجه و بدون دریافت/آپلود/تغییر فایل |
| `radmanct/read-content` | فیلدها، term ID، دادهٔ Core، مالک محتوا و hash نسخه؛ با مجوز ویرایش همان رکورد |
| `radmanct/list-terms` | یافتن دسته/برند/ویژگی/tag موجود، حداکثر ۴۰ نتیجه؛ ایجاد taxonomy تازه ندارد |
| `radmanct/create-content` | ایجاد محتوا از REST بومی همان نوع، پیش‌فرض draft؛ انتشار فقط با status صریح و مجوز native |
| `radmanct/update-content` | تغییر فقط فیلدهای ارسال‌شده، با نسخهٔ قبلی اجباری؛ بدنهٔ Elementor به ابزار رسمی خودش ارجاع داده می‌شود |
| `radmanct/read-layout` | schema و revision چیدمان موجود هدر/فوتر PHP؛ فقط با حضور Theme/API و مجوز مناسب |
| `radmanct/save-layout` | dry_run یا ذخیره با validator سازنده و compare-exchange اتمیک موجود؛ تخصیص سایت/زبان/برگه را تغییر نمی‌دهد |

نوع محصول/نمونه‌کار فقط با فعال‌بودن همان ماژول مجاز است. فیلدهای title/content/excerpt/slug/status/featured_media/template و شناسهٔ taxonomyهای همان نوع allowlist دارند؛ ورودی دلخواه به meta/author/options منتقل نمی‌شود. HTML متن از KSES عبور می‌کند. مشخصات/قیمت/کد/گالری، schema کامل همان مدل Core و کنترل تصویر قابل‌خواندن را مصرف می‌کنند. schema اطلاعات محصول در بدنهٔ Elementor یا ابزار فروشگاهی کپی نشده است. نتیجهٔ ذخیره وضعیت، نسخه و لینک همان رکورد را دارد.

ویرایش PHP سفارشی یعنی محتوای وردپرس و کنترل‌هایی که Template واقعاً مصرف می‌کند؛ فایل PHP/CSS مشتری با این ابزار تغییر نمی‌کند. هدر/فوتر از همان renderer عمومی استفاده می‌کنند. shell، اجرای کد دلخواه، حذف محتوا، نصب افزونه و دست‌کاری credential ارائه نشده‌اند.

## تعارض، ذخیره و محدودیت واقعی

hash محتوا شامل وضعیت/متن/Template/تصویر/termها و دادهٔ Core است؛ ورودی قدیمی و قفل ویرایش کاربر دیگر رد می‌شوند. این بررسی، تراکنش اتمیک مشترک با همهٔ ویرایشگرهای وردپرس نیست؛ فاصلهٔ زمانی بررسی و ذخیرهٔ native باقی است. چیدمان‌ها از CAS اتمیک موجود خود سازنده استفاده می‌کنند. revisionهای native محتوا و متای Core حفظ می‌شوند. اگر متن ذخیره شود ولی ذخیرهٔ details شکست بخورد، خطای partial با ID برمی‌گردد و موفقیت کامل ادعا نمی‌شود؛ ابزار عملیات چندبخشی را تراکنش سراسری معرفی نمی‌کند.

اتصال واقعی Codex/Claude، transport/auth/session در Adapter نصب‌شده، ویرایش Atomic واقعی، WPML و قفل‌های هم‌زمان مرورگر هنوز پذیرش جدا می‌خواهند. تغییر زبان/رابطهٔ ترجمه، تنظیمات ظاهری، اختصاص چیدمان به برگه/زبان، ایجاد چیدمان نام‌دار، بلوک مشترک و ساخت term تازه هنوز ابزار MCP ندارند؛ امکان موجود پنل با ابزار ساخته‌شده یکی نیست. سناریوی کامل این بخش‌ها باقی است و بسته به نسخهٔ پایه نباید آماده گزارش شود.

بررسی هدفمند در `tools/qa-core.ps1 -McpOnly` از WordPress/DB موقت با شبکهٔ داخلی استفاده می‌کند؛ پروتکل یا کلاینت MCP را شبیه‌سازی نمی‌کند. شواهد اجرا در [پایه](../implementation/foundation.md) ثبت می‌شوند.

## بازبینی WoodMart و اصلاح محدود — ۲۰۲۶-۱۰-۲۹

با درخواست مالک، مسیرهای اتصال/مجوز WoodMart MCP و API عمومی Adapter ارسالی دوباره بررسی شدند. مستند رسمی [نصب](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/getting-started/installation.md)، [سرور پیش‌فرض](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/guides/default-server.md) و [اتصال مالک سایت](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/getting-started/site-owners.md) با جست‌وجوی وب و Context7 تطبیق داده شدند. Adapter همچنان مالک transport است؛ ثبت توانایی/وجود کلاس جای اثبات اتصال واقعی نیست.

- `inc/admin/connection.php` فقط هنگام رندر صفحهٔ تنظیمات MCP خوانده می‌شود. وضعیت Abilities، Adapter، route دارای POST و دسترسی همان کاربر به Application Password جدا نمایش داده می‌شوند. URL از serverهای ثبت‌شده و `rest_url` می‌آید؛ route سفارشی، plain permalinks و سرور خاموش/بدون HTTP با URL ثابت جایگزین نمی‌شوند. این بررسی درخواست HTTP یا handshake اجرا نمی‌کند و سرور سفارشی ممکن است همهٔ ابزارهای رادمان را expose نکند.
- راهنمای فارسی اتصال به صفحهٔ native رمز برنامه و مستند رسمی لینک می‌دهد. credential در رادمان تولید/ذخیره نمی‌شود؛ نصب، روشن‌کردن دسترسی سایت، دانلود bridge یا خاموش‌کردن TLS خودکار نداریم. پنل CSS/JS جدید ندارد.
- جست‌وجوی رسانه از REST بومی با `context=edit` و مجوزهای خودش استفاده می‌کند؛ فقط projection تصویر و thumbnail لازم برمی‌گردد. سه فهرست محتوا/term/رسانه همان کلید `items` را حفظ کرده و `page`، `total` و `total_pages` اضافه می‌کنند. سقف schema و pagination حفظ شده است.
- `site-context` محدودیت ویرایش سورس سفارشی، تنظیمات، تخصیص چیدمان، ترجمه و بلوک مشترک را صریح می‌گوید. نام ability المنتور فقط ثبت آن را نشان می‌دهد و تأیید exposure یا پشتیبانی همهٔ اسناد نیست.

بررسی کوتاه روی نصب مشترک محلی با `tests/runtime/mcp-discovery.php`، بدون تغییر option یا محتوا، مسیر فقط‌خواندنی رسانه/برگه، pagination، حد ۲۰، projection و رد ناشناس/خاموشی را تأیید کرد. `tests/mcp-connection-contract.php` با doubleهای کوچک route سفارشی، سرور بدون HTTP، ساخت URL بومی و unavailable بودن رمز برنامه را بررسی کرد؛ این تست transport واقعی نیست. lint چهار PHP تغییرکرده و بازتولید ترجمه انجام شد. هیچ محیط موقت یا بستهٔ ZIP ساخته نشد؛ دسترسی MCP سایت همچنان خاموش ماند.

**باقی‌مانده:** ابزار تنظیمات ظاهری، ایجاد/تخصیص چیدمان، بلوک مشترک و WPML همچنان ساخته نشده‌اند؛ ویرایش سند Elementor به قابلیت رسمی و نسخهٔ واقعی آن وابسته است. wizard/config اختصاصی کلاینت و پذیرش end-to-end اتصال/auth/session هم باقی‌اند. این بازبینی تکمیل همهٔ سناریوها یا برابری ابزارها با WoodMart نیست؛ صف Gutenberg، فروشگاه و کتابخانهٔ دموی خارجی آن جزو انتقال فعلی نیستند.
