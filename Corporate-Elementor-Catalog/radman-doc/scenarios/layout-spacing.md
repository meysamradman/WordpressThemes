# عرض، تراز و فاصله‌های سایت

## CONFIRMED — ۲۰۲۶-۱۰-۱۹

مالک کنترل روشن و هماهنگ عرض و فاصله برای هدر، فوتر، محتوای عمومی/سفارشی، وبلاگ، محصول و نمونه‌کار را می‌خواهد. تنظیمات باید حرفه‌ای، واکنش‌گرا، ماژولار و بدون تداخل با Elementor باشند. این سند مالک واحد رفتار است؛ پایهٔ اجرایی ساخته شده و حدود بررسی در انتهای سند آمده است. تنظیم عرض، کتابخانهٔ چندطرحی یا محدودکردن طراحی اختصاصی مشتری نیست.

## محل کنترل‌ها

اصلاح مالک، ۲۰۲۶-۱۰-۳۰: تمام‌عرض بودن صفحهٔ سفارشی به معنی حذف سقف عددی width است، نه حذف gutter. تنظیم صریح همان صفحه از حالت عمومی اولویت دارد و فیلدهای فاصلهٔ خالی همچنان از تنظیمات عمومی دستگاه می‌آیند. برای صفحهٔ اول سفارشی فعلی فقط override استاندارد full انتخاب شد؛ عرض/فاصلهٔ دیگر صفحات عوض نشد. در محتوای Elementor/طرح Pro، خود Elementor مالک width، gap و padding است و wrapper محدودکنندهٔ قالب اعمال نمی‌شود؛ هدر/فوتر همچنان تنظیم مستقل دارند. منبع رسمی: [Full Width](https://elementor.com/help/using-elementors-full-width-page-template/) و [عرض و padding کانتینر](https://elementor.com/help/container-layout-tab-settings/).

| هدر | تنظیمات رادمان ← هدر و فوتر ← چیدمان منتخب؛ فاصلهٔ داخلی کانتینر در سازنده | هدر منتخب، مستقل از روش طراحی محتوای صفحه |

| وبلاگ، محصول، نمونه‌کار | تنظیمات طراحی محتوا برای هر نوع، با ارث‌بری پیش‌فرض | آرشیو و جزئیات مستقل، فقط هنگام رندر اختصاصی رادمان |

| محتوای Elementor و طرح منتخب Pro | تنظیمات خود Elementor | عرض، gap و padding اجزای المنتوری توسط رادمان بازنویسی نشوند |

## معنای انتخاب عرض

تأکید مالک، ۲۰۲۶-۱۰-۲۷: برای هر هدر و فوتر انتخاب «تمام‌عرض» و «ارث‌بری از عرض تنظیمات قالب» واضح و مستقل باشد؛ محل هر دو همچنان تنظیمات رادمان ← هدر و فوتر است. مقدار دوم از token زندهٔ عرض سایت می‌آید و snapshot عددی در سازنده ذخیره نمی‌کند. گزینهٔ عرض سفارشی قبلی و داده‌های آن حفظ می‌شوند.

- «عرض سایت/ارث‌بری»: محتوای داخل container، سقف عرض مشترک سایت را می‌گیرد و با `margin-inline:auto` در وسط قرار می‌گیرد.
- «تمام‌عرض»: سقف ثابت container برداشته می‌شود؛ این انتخاب به‌خودی‌خود به معنی صفرشدن حاشیهٔ امن کنار صفحه نیست. فاصلهٔ کناری انتخاب مستقل دارد و صفر صریح نیز در محل مجاز ممکن است.
- «عرض سفارشی»: سقف عرض دلخواه معتبر انتخاب می‌شود، نه عرض ثابت اجباری بزرگ‌تر از viewport؛ در موبایل همچنان به فضای موجود محدود و وسط‌چین باشد.
- عرض لایهٔ پس‌زمینه از عرض محتوای داخلی جداست؛ مثلاً زمینهٔ هدر می‌تواند سراسر صفحه و لوگو/منو داخل container محدود و وسط باشند. انتخاب تمام‌عرض پس‌زمینه نباید منو را ناخواسته جابه‌جا کند.
- عرض خواندن متن با عرض کلی container یکی نیست. متن طولانی نوشته می‌تواند محدودتر از شبکهٔ کارت‌ها، گالری یا سکشن تصویری باشد؛ alignwide/alignfull استاندارد Gutenberg و سکشن سفارشی باید مسیر روشن داشته باشند.
- Boxed کردن کل بدنه، ایجاد قاب/سایهٔ سایت و همهٔ حالت‌های WoodMart جزو این تصمیم نیستند؛ قابلیت‌های مرجع بدون نیاز وارد قالب نشوند.

## فاصله و تراز

کنترل فاصلهٔ کناری container، فضای بالا/پایین ناحیهٔ محتوا، padding داخل ردیف هدر/فوتر و gap بین عناصر مفهوم جدا داشته باشند. عنوان، واحد و محل هر کنترل همین تفاوت را نشان دهند. مرکزشدن container با تراز متن یا توزیع عناصر منو یکی نیست؛ برای ردیف همچنان تراز/justify مناسب وجود داشته باشد.

فاصلهٔ هدر تا شروع محتوا و پایان محتوا تا فوتر هر کدام فقط یک مالک مشخص داشته باشند. padding ناحیهٔ محتوا، margin فوتر و padding اولین/آخرین سکشن نباید ناآگاهانه یک فاصله را دو بار بسازند. فاصلهٔ عمدی داخل طراحی مشتری حفظ شود؛ نرمال‌سازی wrapper قالب به معنی حذف فاصلهٔ عناصر مشتری نیست.

پیش‌فرض سراسری با ارث‌بری باشد؛ override دسکتاپ/موبایل در جای لازم روشن باشد. «ارث‌بری» مقدار مستقل از صفر است؛ صفر فاصلهٔ معتبر است و نباید به پیش‌فرض تبدیل شود. inline/block و start/end به جای چپ/راست فیزیکی مصرف شوند. container در RTL/LTR، عرض کم، محتوای بلند و منوی فارسی/انگلیسی overflow افقی ناخواسته ایجاد نکند. خود محتوای بلند مثل جدول باید راهکار مخصوص خود را داشته باشد، نه پنهان‌کردن overflow کل سایت.

## ترتیب اولویت و سفارشی‌سازی

برای خروجی‌های متعلق به رادمان، پیش‌فرض قالب ← تنظیم سراسری ذخیره‌شده ← override معتبر همان ناحیه/نوع محتوا ← override اختیاری همان برگه/طراحی سفارشی است. صفحهٔ سفارشی به‌صورت پیش‌فرض هدر/فوتر منتخب و عرض/فاصلهٔ عمومی قالب را مصرف می‌کند؛ تنظیم دوباره برای هر صفحه لازم نیست. هدر و فوتر تنظیم چیدمان خودشان را دارند؛ مقدار «عرض سایت» از تنظیم سراسری مصرف می‌کند و مقدار سفارشی همان چیدمان مستقل است. ردیف/عنصر فقط فاصله و چیدمان داخلی خودش را تغییر دهد؛ تغییر یک ردیف نباید عرض همهٔ صفحات را عوض کند.

وبلاگ، محصول و نمونه‌کار بتوانند در آرشیو/جزئیات از پیش‌فرض مشترک استفاده کنند یا override آگاهانه بگیرند. تنظیم module خاموش، آن را فعال نکند؛ کنترل مربوط فقط هنگام کاربرد نشان داده شود و هیچ query برای محصولات/نمونه‌کار جهت محاسبهٔ عرض اجرا نشود.

برای PHP سفارشی، قرارداد توسعه‌دهنده باید راه کوتاه مصرف عرض/فاصلهٔ مشترک داشته باشد؛ برای هر پروژه CSS و wrapper موازی از ابتدا ساخته نشود. خروج صریح سکشن به تمام‌عرض یا طراحی اختصاصی مجاز بماند. انتخاب‌گر مستقل override برای تک‌تک برگه‌ها هنوز قطعی نیست؛ ابتدا تنظیم سراسری، ناحیه و نوع محتوا کافی‌اند و جزئیات این سطح در بخش باز آمده است.

## مرز Elementor و Gutenberg

در Template المنتوری و در آرشیو/جزئیات واگذارشده به Pro، محتوای ساخته‌شده با Elementor داخل container محدودکننده یا padding پیش‌فرض محتوای PHP دوباره پیچیده نشود. selector عمومی روی `.elementor`، `.e-con` یا همهٔ فرزندان صفحه، یا `!important` برای تحمیل عرض/فاصله ساخته نشود. renderer منتخب تعیین کند چه لایه‌ای مالک چیدمان است؛ کلاس روش نمایش باید scope روشن بدهد. نبود Elementor/طرح منطبق و بازگشت به PHP، تنظیمات خروجی PHP را دوباره اعمال کند.

هدر/فوتر رادمان در صفحهٔ المنتوری همچنان از تنظیم خودشان پیروی کنند. Template تمام‌عرض با هدر/فوتر و Elementor Canvas با حذف آن‌ها یکسان نیستند؛ انتخاب عرض نباید Canvas را به‌جای برگهٔ تمام‌عرض جا بزند. هنگام طراحی صفحهٔ المنتوری، gutter و فضای ابتدا/انتهای wrapper قالب پیش‌فرض اضافی نسازند؛ فاصلهٔ خود containerهای المنتور باقی بماند.

همگام‌سازی خودکار تنظیمات عرض رادمان با Elementor Site Settings نداریم؛ این کار نباید تنظیمات ذخیره‌شدهٔ افزونه را بی‌صدا تغییر دهد. اگر بعداً هماهنگ‌سازی لازم شد، قرارداد جدا و انتخاب صریح داشته باشد. مالکیت فونت طبق [تایپوگرافی](typography.md) مستقل از مالکیت عرض است.

برای Gutenberg، عرض خواندن/گستردهٔ ویرایشگر و خروجی PHP باید هماهنگ باشند؛ `theme.json` و متغیرهای CSS نباید دو پیش‌فرض متعارض پس از تغییر تنظیم بسازند. alignwide/alignfull و stylesheet صفحهٔ سفارشی باید در بررسی پوشش داده شوند.

## قاعدهٔ فنی و پذیرش

- دادهٔ تنظیمات و resolver مشترک، validation محدود، CSS Variables و قواعد scope‌شده استفاده شوند؛ منطق عرض/فاصله برای هر template دوباره نوشته نشود. نام کلیدها، حدود عددی و واحدهای دقیق پیش از اجرا در قرارداد فنی نهایی شوند؛ ورودی CSS آزاد و JavaScript برای محاسبهٔ عرض پایه لازم نیست.
- کنترل‌ها از اجزای مشترک پنل/سازنده مصرف شوند. صفحهٔ بدون ماژول یا Elementor فایل/پردازش آن ادغام را نگیرد؛ محاسبهٔ چیدمان نباید باعث query محتوا یا اسکن plugin در هر درخواست شود.
- دادهٔ فعلی هدر/فوتر و عرض سراسری حذف یا بی‌صدا تغییر معنا ندهند. پیش‌فرض‌های فعلی و تغییر احتمالی فاصله‌های قبلی باید هنگام migration روشن ثبت شوند.
- بررسی کوتاه آینده: ارث‌بری/صفر/مقدار نامعتبر، سقف viewport، مرکزشدن container، عرض مستقل هدر/فوتر، فاصلهٔ یک‌بارهٔ ابتدا/انتها، آرشیو و جزئیات سه نوع محتوا، Gutenberg و صفحهٔ PHP سفارشی، Elementor/Pro و fallback. تأیید بصری RTL/LTR و موبایل جدا از تست استاتیک است؛ تست طولانی خودکار لازم نیست.

## وضعیت واقعی و کار باقی‌مانده

پایهٔ اجرایی ۲۰۲۶-۱۰-۱۹ شامل resolver مشترک، کنترل سراسری عرض/فاصله و override مستقل آرشیو/جزئیات وبلاگ، کاتالوگ و نمونه‌کار است. هدر/فوترساز انتخاب full/contained/custom و gutter دسکتاپ/موبایل دارند. عرض خواندن و عرض گستردهٔ Gutenberg از تنظیمات رادمان به دادهٔ theme متصل‌اند؛ دادهٔ Global Styles کاربر بازنویسی نمی‌شود. [قرارداد فنی و حدود ورودی](../engineering/layout.md).

wrapper محتوای PHP مدیریت‌شده، padding ابتدا/انتها را یک بار می‌سازد؛ margin اضافی فوتر در این مسیر حذف شده است. صفحات Elementor و طرح Pro از محدودیت wrapper رادمان خارج‌اند. Template سفارشی رادمان و نمونهٔ ثبت‌شدهٔ Child همان تنظیمات مشترک را خودکار مصرف می‌کنند. فقط template ناشناختهٔ توسعه‌دهنده از مدیریت خودکار خارج است و ابزار PHP برای ورود صریح به قرارداد مشترک دارد.

قراردادهای کوتاه ارث‌بری، صفر، ورودی نامعتبر، schema سازنده، مسیر سفارشی و مرز Elementor پاس شده‌اند. باقی‌مانده: بازبینی بصری روی سرور تست برای RTL/LTR، موبایل، alignwide/alignfull، محتوای واقعی مشتری و Elementor/Pro؛ این موارد از آزمون stub و Build نتیجه‌گیری نشده‌اند.

## کنترل برگه و حدود فعلی

فاصلهٔ عمومی محتوا برای دسکتاپ، تبلت و موبایل ورودی مستقل دارد؛ خالی از پایه ارث می‌برد و صفر معتبر است. ویرایش برگه بخش اختیاری «چیدمان محتوای رادمان» دارد؛ پیش‌فرض آن ارث‌بری کامل از قالب است. انتخاب contained/full/custom فقط برای استثنای همان برگه است و مقادیرش جایگزین مقدار حل‌شده می‌شوند، نه padding اضافه. بازگشت به حالت سراسری overrideها را غیرفعال می‌کند؛ هدر/فوتر و Elementor تغییر نمی‌کنند. چهار دستگاه هدر/فوتر طبق [قرارداد سازنده](../engineering/builder.md) مستقل‌اند. ورودی px صحیح است؛ واحدهای دلخواه/عبارت CSS آزاد تأیید نشده‌اند. حدود و breakpointها در [قرارداد چیدمان](../engineering/layout.md) ثبت شده‌اند.

## مرجع بررسی‌شده

`themes/woodmart/inc/admin/settings/general-layout.php` گزینه‌های عرض/عرض سفارشی؛ `themes/woodmart/inc/configs/header-builder-settings.php` تنظیم مستقل عرض header؛ و `themes/hub/theme/theme-options/liquid-layout.php` عرض سایت و فاصله‌های ردیف. فایل Hub در حضور Elementor Addons شرط خروج دارد؛ این جزئیات فقط شاهد تفکیک مالکیت در مرجع است، نه API یا رفتار قابل کپی برای رادمان. framework، حالت‌های اضافی، منابع hint خارجی و CSS کامل آن‌ها منتقل نشوند. مستندات [صفحهٔ محتوای Hello Elementor](https://developers.elementor.com/docs/hello-elementor-theme/hello_elementor_content_width/) نیز با Context7 برای تفکیک قرارداد عرض Theme بررسی شد؛ API مختص Hello نباید در رادمان استفاده شود.
