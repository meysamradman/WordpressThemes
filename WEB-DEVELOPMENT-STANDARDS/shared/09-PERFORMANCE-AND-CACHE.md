# عملکرد، کش و آزمون شبکه

## تشخیص و اندازه‌گیری

- URL، viewport، موقعیت، دستگاه، مهمان/مدیر و کش سرد/گرم را ثبت کنید. اول waterfall و عنصر LCP را پیدا کنید. TTFB شامل مسیر اتصال و انتظار پاسخ است. `load`، LCP و پایان آخرین درخواست متفاوت‌اند. درخواست دیرهنگام را با زمان شروع، نوع و Initiator بررسی کنید.
- تصویر LCP با اندازه و نسبت واقعی در HTML قابل کشف باشد. فقط دارایی واقعاً مهم را preload یا high priority کنید. کاورهای بعدی و رسانهٔ پخش با قرارداد همان پروژه مؤخر شوند. JS/CSS و فونت بی‌مصرف از Network و manifest مصرف‌کننده تأیید شوند. خود اندازهٔ ZIP شاخص حجم بازدید نیست.
- دادهٔ میدانی CWV در صدک ۷۵ برای موبایل و دسکتاپ جدا سنجیده شود. حدود خوب LCP تا ۲٫۵ ثانیه، INP تا ۲۰۰ms و CLS تا ۰٫۱ هستند. Lighthouse و GTmetrix تست آزمایشگاهی‌اند. نتیجهٔ مقایسه را در شرایط یکسان گزارش کنید.

## سیاست کش

| لایه | قرارداد |
|---|---|
| CSS/JS هش‌دار | TTL بلند و `immutable` در صورتی که تغییر محتوا حتماً URL را عوض کند. manifest و HTML باید به نسخهٔ جدید برسند. فایل‌های هنوز referenced تا قطع مصرف نسخهٔ قبلی در دسترس بمانند. |
| تصاویر/فونت با URL ثابت | TTL متناسب با امکان تغییر فایل، با سازوکار purge یا validatorهایی مانند `ETag` و `Last-Modified`. هدر واقعی پاسخ CDN/وب‌سرور سنجیده شود. |
| HTML عمومی | فقط GET/HEAD عمومیِ واجد شرایط. ورود، پیشخوان، preview، درخواست دارای نشست، محتوای رمزدار/خصوصی و خروجی وابسته به کاربر bypass شوند. زبان، کوئری و دستگاه فقط وقتی در cache key لحاظ شوند که به خروجی اثر دارند. |
| Elementor | کش HTML عمومی، کش خروجی ویجت و CSS تولیدی ادیتور مالک‌های متمایزند. محتوای پویا طبق API و نسخهٔ نصب‌شده بررسی شود. صحت ادیتور/پیش‌نمایش و پس از ویرایش نیز تست شود. |

در میزبان، کش سرد/گرم را با GET مهمان و هدرهای پاسخ مقایسه کنید. نبود هدر HIT اثبات نبود کش نیست. تغییر انتشار/محتوا purge متناسب می‌خواهد. روش تنظیم، TTL واقعی، سازگاری CDN و rollback فقط در Runbook همان سایت ثبت شوند.
