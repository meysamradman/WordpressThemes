# استاندارد عمومی HTML، سئو، موبایل و انیمیشن — v1.2

> بازبینی بسته 1.3 — 2026-11-19؛ نام مسیر برای سازگاری ارجاع‌های موجود حفظ شده است. تاریخچه در CHANGELOG-v1.3.md.

**تاریخ بازبینی منابع: ۱۶ نوامبر ۲۰۲۶**  
**کاربرد:** همه وب‌سایت‌های مشتریان؛ مستقل از برند، وردپرس یا فریم‌ورک. قابل تحویل به Codex.  
**تصمیم اجرایی:** **یک URL + یک HTML/DOM اصلی + Responsive CSS**؛ نسخه مجزای موبایل ساخته نمی‌شود.

> **مرز واقعیت و قرارداد:** گوگل تعداد الزامی H1/H2/H3، تعداد `div`/`span`، چگالی کلمه کلیدی، تعداد کلمات صفحه یا مدت انیمیشن تعیین نکرده است. «یک H1»، محدوده حرکت‌ها و سیاست حذف افکت موبایل، **استاندارد پیشنهادی تیم** هستند؛ نه قانون قطعی رتبه‌بندی گوگل.

## ۱. ساختار و محتوای هر صفحه

| جزء | استاندارد اجرایی |
|---|---|
| `<title>` | برای هر URL یکتا، دقیق و هماهنگ با موضوع/H1؛ بدون تکرار بی‌مورد کلیدواژه. |
| `<meta name="description">` | توضیح مفید و مختص همان صفحه؛ حد کاراکتر ثابت/تضمین نمایش در گوگل ندارد. |
| `h1` | **ترجیحاً یک H1 ثابت**، توصیفی و مخصوص همان صفحه؛ لوگو یا عبارت متحرک به‌جای آن قرار نگیرد. |
| `h2`, `h3` | H2 برای بخش‌های اصلی و H3 برای زیرموضوع‌ها؛ تعداد متناسب با محتوای واقعی، نه سهمیه سئو. `h4`–`h6` فقط در صورت نیاز. |
| `p` | متن مفید، قابل‌خواندن و بدون کپی؛ هیچ حداقل تعداد واژه‌ای برای گوگل وجود ندارد. |
| `span`, `div` | `span` برای تأکید درون متن، `div` برای layout/افکت؛ جایگزین heading یا عنصر معنایی نشوند. |
| `header`, `nav`, `main`, `section`, `article`, `footer` | ساختار معنایی؛ معمولاً یک `main` اصلی. هر `section` محتوایی یک عنوان مناسب داشته باشد. |
| `a`, `button` | مسیر صفحات با `<a href>` واقعی؛ کنترل منو، اسلاید و عملیات درون صفحه با `<button>`. |
| `img` | `alt` توصیفی برای تصویر محتوایی، `alt=""` برای تزئینی، ابعاد/نسبت تصویر مشخص. |

**صفحه اصلی:** هدر/ناوبری → هیرو با H1 و معرفی کوتاه → بخش‌های اصلی با H2 → نمونه‌کار/خدمات/محصولات/محتوای مرتبط (براساس ماهیت پروژه) → دعوت به اقدام → فوتر. متن هر بخش به‌اندازه پاسخ به نیاز کاربر باشد، نه صرفاً برای پرکردن صفحه. **فوتر:** لینک‌های واقعی و مهم، اطلاعات تماس معتبر، بدون انباشت کلیدواژه و لینک تکراری.

**متادیتا و فنی:** Canonical درست و سازگار با Sitemap/ریدایرکت؛ robots/noindex برحسب سیاست انتشار؛ Sitemap فقط برای URLهای نهایی قابل ایندکس؛ JSON-LD مطابق محتوای واقعی؛ بدون `meta keywords`، قیمت/امتیاز/موجودی ساختگی. متاتگ تکراری از قالب و افزونه چاپ نشود. تست HTTP، لینک داخلی، نمایش موبایل، محتوای رندرشده و گزارش ایندکس پیش از انتشار لازم است.

**مرجع تخصصی:** تصمیم منبع، نقش، responsive image و مدیا در [17](17-IMAGES-AND-MEDIA-v1.0.md)؛ قرارداد دقیق metadata، index، schema و مهاجرت در [20](20-TECHNICAL-SEO-SCHEMA-v1.0.md). تصویر شاخص اجباری برای همه برگه‌ها یا Hero نیست؛ بر اساس نقش و قرارداد رندر استفاده شود. قواعد حرکت این سند صرفاً اهداف UX هستند؛ 05 و مالک چرخه پروژه مرجع پیاده‌سازی‌اند.

## ۲. موبایل و ریسپانسیو (تصمیم قطعی)

1. `<meta name="viewport" content="width=device-width, initial-scale=1">`؛ بزرگ‌نمایی کاربر را مسدود نکن.
2. **یک HTML و محتوای اصلی یکسان** روی دسکتاپ/موبایل؛ با Media Query، Flex/Grid و Container Query فقط چینش، اندازه، ترتیب بصری و تصویر را تغییر بده. دو کپی از کل سکشن‌ها نساز.
3. H1، توضیح اصلی، لینک‌های مهم، robots و داده‌های ساختاریافته در موبایل حذف نشوند؛ آکاردئون برای جمع‌کردن بصری مجاز است، اما محتوای کلیدی فقط پس از درخواست/کلیک از سرور ساخته نشود.
4. Breakpoint بر اساس شکستن طرح؛ آزمون عملی در عرض‌های نمونه 320، 360، 390، 768 و 1024 پیکسل و روی دستگاه واقعی؛ بدون اسکرول افقی ناخواسته.
5. فونت بدنه معمولاً نزدیک 16px، کنتراست و فاصله خط مناسب؛ اهداف لمسی راحت (ترجیح عملی نزدیک 44×44px؛ این عدد الزام رتبه‌بندی نیست)؛ منو/کاروسل با لمس و کیبورد قابل استفاده.
6. تصاویر با `srcset`/`sizes`، در صورت نیاز `<picture>`؛ برای تصویر **LCP/هیرو** معمولاً `loading="eager"` و فقط در صورت مناسب‌بودن `fetchpriority="high"`. تصاویر پایین صفحه می‌توانند `loading="lazy"` باشند؛ ابعاد همه تصاویر مشخص شود.
7. تصویر/محتوای حیاتی در HTML قابل کشف باشد. منابعی که فقط با کلیک/Swipe درخواست می‌شوند، برای محتوای اصلی انتخاب خوبی نیستند.

**پاسخ فنی به نگرانی حجم:** Responsive با CSS دو HTML تولید نمی‌کند. اما **کد GSAP و افکت‌های دسکتاپ اگر بی‌قیدوشرط import/enqueue شوند، ممکن است در موبایل هم دانلود شوند حتی اگر انیمیشن اجرا نشود**. برای ویژوال واقعاً سنگین، JS را شرطی و جداگانه بارگذاری کن؛ تست Network ضروری است.

## ۳. سیاست GSAP و ScrollTrigger

| افکت | دسکتاپ | موبایل |
|---|---|---|
| ورود ملایم عنوان/کارت (Reveal) | بله | بله، کوتاه‌تر و کمتر |
| تغییر کلمات هیرو | بله | بله، اگر خوانایی و ارتفاع ثابت بماند |
| Hover/Mouse-follow | در صورت کاربرد | حذف یا تبدیل به لمس/حالت ثابت |
| ScrollTrigger ساده | بله | فقط در صورت روان بودن |
| Sticky/Pin طولانی و اسکرول افقی اجباری | محدود و تست‌شده | ترجیحاً حذف و چیدمان عمودی |
| Parallax عمیق، Blur زیاد، انیمیشن بی‌وقفه | پرهیز از افراط | حذف/کاهش شدید |
| WebGL/مدل سه‌بعدی سنگین | فقط با اندازه‌گیری | تصویر یا نسخه بسیار سبک به‌عنوان جایگزین |

- انیمیشن‌های DOM را **تا حد ممکن با `transform` و `opacity`** بساز؛ از تغییر پی‌درپی `top/left/width/height` و محاسبات سنگین layout اجتناب کن. `will-change` را همه‌جا دائمی فعال نکن.
- برای تفاوت موبایل/دسکتاپ و پاکسازی افکت‌ها از `gsap.matchMedia()` استفاده کن؛ هنگام تغییر Breakpoint، انیمیشن و ScrollTrigger قبلی باید revert/cleanup شود. برای `prefers-reduced-motion: reduce` انیمیشن غیرضروری حذف یا به Fade بسیار کوتاه تبدیل شود.
- H1، متن، لینک‌ها و تصاویر معنادار باید **قبل از اجرای JS در HTML باشند**؛ GSAP صرفاً آن‌ها را انیمیت کند. `opacity:0` دائمی در CSS پایه برای محتوای حیاتی نگذار؛ بدون JS باید متن دیده شود.
- از Reveal طولانی هیرو که نمایش محتوای اصلی را به تأخیر می‌اندازد خودداری کن؛ برای ScrollTrigger می‌توان از `once: true` در Revealها استفاده کرد. عنصر `pin`‌شده را مستقیماً transform نکن؛ اگر لازم است عناصر داخلی آن را حرکت بده.
- انیمیشن‌ها نباید اسکرول را قفل کنند، برای رسیدن به محتوا کاربر را مجبور به دیدن صحنه کنند یا حالت Focus را مخفی کنند.

**الگوی کوتاه GSAP — بدون HTML مجزا برای موبایل:**

```js
const mm = gsap.matchMedia();
mm.add({
  desktop: '(min-width: 768px)',
  mobile: '(max-width: 767px)',
  reduceMotion: '(prefers-reduced-motion: reduce)'
}, (ctx) => {
  const { desktop, mobile, reduceMotion } = ctx.conditions;
  if (reduceMotion) return; // محتوا در HTML/CSS پایه قابل مشاهده است.
  gsap.from('.hero-copy', {
    opacity: 0, y: mobile ? 8 : 20, duration: mobile ? 0.3 : 0.55,
    ease: 'power2.out', clearProps: 'all'
  });
  // ScrollTriggerهای pin فقط در صورت نیاز و بعد از تست موبایل:
  if (desktop) { /* desktop-only ScrollTrigger setup */ }
});
```

> اگر فایل پلاگین یا Three.js سنگین است، `matchMedia` به‌تنهایی مانع دانلود باندل نمی‌شود؛ برای کاهش بایت‌های دانلود از **code splitting / import شرطی واقعی** یا enqueue فقط روی صفحات نیازمند استفاده کن.

## ۴. کاروسل/اسلایدر (نمونه‌کار، محصول، نظرات)

- برای محتوای مهم **پیش‌فرض: کاروسل دستی**؛ کنترل «قبل/بعد»، Swipe لمسی و کیبورد. حتی‌المقدور روی موبایل از اسکرول افقی استاندارد/CSS Scroll Snap استفاده کن؛ به کتابخانه سنگین نیاز نیست.
- در صورت چرخش خودکار، کنترل **توقف/شروع** لازم است؛ هنگام فوکوس کیبورد و Hover توقف کند؛ با `prefers-reduced-motion` خودکار شروع نشود. مدت اسلاید باید فرصت خواندن بدهد (عدد اجباری گوگل وجود ندارد).
- اسلایدها و لینک‌ها با HTML معنایی و قابل دسترس باشند؛ محتوای اصلی/لینک صفحات را فقط پس از Swipe/Click از سرور درخواست نکن. تصویر اسلاید اول اگر در نمای اولیه است با اولویت مناسب؛ تصاویر پایین/غیرفعال Lazy با تست واقعی مرورگر.
- روی کاروسل از نشانگرهای موقعیت، برچسب دکمه (`aria-label`) و وضعیت فوکوس قابل مشاهده استفاده کن. انیمیشن slide را روی `transform` پیاده کن و اندازه ظرف را تثبیت کن تا CLS ایجاد نشود.

## ۵. ورود صفحه، Preloader و Loading

- **پیش‌فرض: بدون Preloader تمام‌صفحه، تایمر اجباری یا انیمیشن ۲–۳ ثانیه‌ای قبل از نمایش محتوا.** کاربر باید سریع H1 و محتوای اصلی را ببیند؛ لودینگ ظاهری جای LCP واقعی را نمی‌گیرد.
- فقط برای **درخواست واقعاً درحال پردازش** (ارسال فرم، دریافت داده، عملیات زمان‌بر) از loading یا skeleton استفاده کن؛ فضایش را رزرو کن تا CLS نشود، وضعیت را برای فناوری کمکی اعلام کن و خطا/زمان‌بر شدن را مدیریت کن.
- Splash/لوگوی متحرک را در صورت نیاز **غیرمسدودکننده** و بعد از نمایش محتوای اصلی اجرا کن؛ با reduced motion غیرفعال.
- عکس/ویدئو/مدل سه‌بعدی Hero نباید مانع نمایش متن و CTA شود: ابتدا پوستر/تصویر سبک و محتوای HTML، سپس منبع سنگین در صورت نیاز. ویدئوها در موبایل بهتر است دستی با `poster` شروع شوند؛ منابع پایین صفحه lazy.
- برای اسکریپت‌های ضروری `defer`/`type="module"` و بارگذاری صفحه‌ای؛ از کار طولانی JS روی Main Thread در شروع و هنگام لمس پرهیز کن.

## ۶. معیار پذیرش و تست Codex

- [ ] یک URL/HTML اصلی برای موبایل و دسکتاپ؛ محتوای مهم و لینک‌های واقعی در هر دو یکسان و قابل استفاده.
- [ ] H1 ثابت، عنوان/متادیتا/Canonical درست، heading سلسله‌مراتبی، فوتر و لینک‌ها قابل خزیدن.
- [ ] بدون JS یا با reduced motion، متن، لینک و تصویر اصلی قابل مشاهده‌اند.
- [ ] منو، کاروسل و فرم با لمس/کیبورد؛ بدون اسلاید خودکار کنترل‌ناپذیر.
- [ ] Mobile: بدون Pin آزاردهنده، اسکرول افقی ناخواسته، Hover-only یا لودینگ تمام‌صفحه غیرضروری.
- [ ] فیلم/Three.js/GSAP فقط در صفحات لازم؛ بررسی **واقعی Network و Performance** برای بایت‌های دانلود و Long Taskها.
- [ ] اهداف **Core Web Vitals** در صدک ۷۵ داده واقعی کاربران، جداگانه برای موبایل و دسکتاپ: `LCP ≤ 2.5s`، `INP ≤ 200ms`، `CLS ≤ 0.1`. از Lighthouse/PageSpeed/DevTools و داده واقعی استفاده شود.
- [ ] تصاویر/فونت‌ها ابعاد و بارگذاری صحیح؛ Hero/LCP بدون lazy بی‌دلیل؛ بقیه lazy و قابل کشف.

**اگر پروژه با وردپرس اختصاصی است:** محتوای اصلی از PHP رندر شود؛ اسکریپت‌ها از `wp_enqueue_script`/`wp_enqueue_style` فقط در صفحات لازم بارگذاری شوند؛ برای موبایل نسخه قالب PHP جدا با `wp_is_mobile()` نساز، مگر نیاز مشخص و مدیریت کش/SEO آن اثبات شده باشد.
