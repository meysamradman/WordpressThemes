# نسخه‌ها، CSS/JS و ساخت بسته

> بازبینی بسته 1.3 — 2026-11-19؛ نام مسیر برای سازگاری ارجاع‌های موجود حفظ شده است. تاریخچه در CHANGELOG-v1.3.md.

- حداقل اعلام‌شدهٔ قالب، نسخهٔ هدف، نسخهٔ نصب‌شده و نسخه‌ای که واقعاً تست شده چهار دادهٔ جدا هستند. نسخه و منبع واقعی در Profile همان پروژه ثبت شود. runtime را از PHP وب/CLI و محیط نصب‌شده بررسی کنید و ابزار ساخت را از manifest و lockfile بخوانید. مقدار تأییدنشده را مشخص کنید. تغییر نسخه، مهاجرت یا تولید بسته بخشی از یک ویرایش عادی نیست.
- CSS یک پایهٔ سبک و مالک token دارد. استایل هر کامپوننت و صفحه کنار همان ماژول بماند. JS سراسری فقط زیرساختی را داشته باشد که مصرف سراسری دارد. import ثابت برای وابستگی لازم همان entry، import پویا برای قابلیت شرطی و cleanup با مالک فعلی. تعداد فایل به‌تنهایی معیار معماری نیست.
- انتخاب entry و ثبت وابستگی‌ها با مسیر [قالب سفارشی](../wordpress-custom/07-WORDPRESS-CUSTOM-DEVELOPMENT-v1.0.md) یا [Elementor](../wordpress-elementor/15-WORDPRESS-ELEMENTOR-DEVELOPMENT-v1.0.md) انجام شود. CSS لازم برای HTML اولیه به‌موقع برسد و نبود مصرف‌کننده به معنی نبود درخواست کد اختیاری باشد.
- در صورت Vite، manifest و فایل‌های هش‌دار همان build با هم بررسی و تحویل شوند. CSS و زنجیرهٔ importهای ثابت/پویا باید در بسته موجود باشند. dist خروجی ساخت است. Node ابزار توسعه و build است. فایل‌های runtime را از روش رسمی WordPress enqueue کنید.
- ZIP به‌روزرسانی فقط فایل‌های لازم را دارد. اطلاعات اتصال، `wp-config.php`، فایل نمونهٔ آن، محیط توسعه، بکاپ و SQL در ZIP عمومی قرار نگیرند. SQL فقط برای مهاجرت دادهٔ درخواست‌شده و جداگانه تحویل شود. برای هاست یونیکس، مجوز معمول ZIP پوشه `0755` و فایل `0644` است. مجوز واقعی و مالکیت پس از استخراج بررسی شود.

## تحویل وردپرس بر اساس دامنه

این روال برای سایت‌های مشتری با قالب سفارشی و Elementor یکسان است. پوشهٔ تحویل خصوصی با دامنهٔ مقصد نام‌گذاری شود و راهنمای آن مشخص کند هر فایل برای کدام عملیات است.

| وضعیت مقصد | بستهٔ تحویل |
|---|---|
| نصب تازه روی دیتابیس خالی | `01-database/database-ready.sql` آمادهٔ ایمپورت با دامنهٔ واقعی مشتری و `02-public_html/public_html.zip` شامل فایل‌های لازم سایت. `index.php` و `wp-content/` باید مستقیماً در ریشهٔ ZIP باشند. |
| سایت فعال، تغییر فایل‌ها | ZIP فقط با فایل‌های تغییرکرده و وابستگی‌های لازم شامل manifest و دارایی‌های همان build. در صورت تحویل بستهٔ کامل برای نصب تازه، صریحاً مشخص کنید روی سایت فعال فقط مسیرهای مربوط به به‌روزرسانی استخراج می‌شوند. |
| سایت فعال، تغییر داده | یک فایل اصلاحی با نام روشن مانند `01-database/fix-track-order.sql` یا مهاجرت محدود از طریق API وردپرس. روی دیتابیس فعال ایمپورت کامل انجام نشود. اگر داده تغییر نکرده باشد، فایل اصلاحی لازم نیست. |

- برای ساخت SQL نصب تازه، نشانی‌های محلی با ابزار سازگار با دادهٔ سریال‌شده به URL واقعی مقصد تبدیل شوند. دامنه، پیشوند جدول و خالی بودن مقصد پیش از ایمپورت بررسی شوند. `wp-config.php`، اطلاعات اتصال، کلیدهای محیط و فایل‌های بازیابی خارج از ZIP و مسیر وب بمانند.
- برای سایت فعال از وضعیت فعلی هاست مبنا بگیرید. اصلاح فقط جدول، ستون و رکوردهای لازم را هدف بگیرد و با شناسه، نوع محتوا، مقدار قبلی یا کلید پایدار کنترل شود. فایل را روی کپی یا جدول آزمایشی تست کنید و در صورت امکان اجرای دوباره بی‌اثر باشد. اگر پیش‌شرط‌های اصلاح گروهی تطبیق ندارند، هیچ بخشی از گروه نوشته نشود. تعداد مورد انتظار و روش کنترل نتیجه را بنویسید.
- قبل از اجرای اصلاح، بکاپ بازیابی هاست را جدا و خصوصی نگه دارید. محتوا و تنظیمات جاری، کاربران، رسانه، افزونه‌ها و قواعد هاست از جمله AIOS و `.htaccess` باید در محدودهٔ به‌روزرسانی حفظ شوند. پس از اعمال، اثر تغییر را در مسیر مربوط بررسی کنید و در صورت نیاز کش همان بخش را پاک کنید.
- بعد از صحت‌سنجی ZIP و SQL جدید، نسخه‌های قدیمی همان خروجی را از **پوشهٔ تحویل همان دامنه** پاک کنید. در پوشهٔ تحویل فقط بستهٔ جاری و فایل‌های اصلاحی لازم همان تحویل بمانند. بکاپ بازیابی یا منبع مشتری در مسیر جدا نگه داشته شود.
