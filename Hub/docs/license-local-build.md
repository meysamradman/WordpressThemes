# نگهداری نسخه محلی Hub

تاریخ: ۲۰۲۶-۱۱-۱۰. مبنا: فایل‌های تحویل‌شده Hub 6.0.3، Hub Core 6.0.3 و Hub
Elementor Addons 6.0.3؛ این مبنا لزوماً نسخه رسمی دست‌نخورده نیست، زیرا functions.php
از ابتدا سه خط فعال‌سازی ساختگی داشت.

نسخه خروجی قالب: **6.0.3.2**. افزونه Hub Elementor Addons همان **6.0.3** است و
بسته اصلاح‌شده‌اش پسوند `local1` دارد. ثابت نسخه آن تغییر نکرده چون در درخواست API
کتابخانه استفاده می‌شود. Hub Core و Elementor دست‌نخورده‌اند.

## محدوده نهایی مورد تأیید کاربر

فقط وابستگی به لایسنس حذف می‌شود. کتابخانه Hub Collections باید با منبع و رفتار
اصلی خودش باقی بماند. تغییرات آزمایشی محدودکردن شبکه، فونت، دمو، Mailchimp و Twitter
به‌طور کامل برگشت داده شدند و داخل خروجی نهایی نیستند. این بسته کاملاً آفلاین نیست.
ملاحظات اتصال خارجی جداگانه در `external-connections.md` آمده‌اند.

طبق تأکید بعدی کاربر، حذف لایسنس نباید اعلان یا نصب آپدیت قالب/افزونه‌ها را ببندد.
اعلان آپدیت قالب از API اصلی فروشنده برگشته و از لایسنس مستقل است. کاربر می‌پذیرد
که نصب ZIP اصلی اصلاحات را حذف می‌کند؛ بعد نسخه جدید را در `update/` قرار می‌دهد
تا بررسی و اصلاح مجدد انجام شود. این قواعد در Skill محلی
`../.agents/skills/hub-maintenance/SKILL.md` هم ثبت شده‌اند.

## علت پیام و اصلاح دقیق

سه خط functions.php فقط purchase code، وضعیت valid و ایمیل را هر بار می‌نوشتند.
manager اصلی جداگانه دامنه قبلی، domain key و revoke را بررسی می‌کرد؛ بنابراین
هنوز امکان نمایش پیام مهاجرت دامنه و خطای ۵۰۳ برای بازدیدکننده وجود داشت.

| فایل | اصلاح نهایی |
| --- | --- |
| `hub/functions.php` | حذف سه update_option مربوط به کد، valid و ایمیل ساختگی؛ راه‌اندازی مستقل Liquid_Updater بدون الزام لایسنس |
| `hub/liquid/admin/updater/liquid-register-admin.php` | حذف manager فعال‌سازی، بررسی دامنه و لغو، پردازش callback، پیام خطا و قفل template_redirect؛ حفظ کلاس کوچک Liquid_Register با messages/form برای سازگاری قالب‌های موجود |
| `hub/liquid/admin/updater/liquid-updater-class.php` | دریافت نسخه از همان API اصلی؛ اتصال به اعلان استاندارد وردپرس؛ بررسی دوره‌ای و کش؛ بدون popup و اتصال admin_head قدیمی |
| `hub/liquid/admin/liquid-admin-dashboard.php` | عنوان صفحه Hub Local |
| `hub/liquid/admin/views/liquid-plugins.php` | برداشتن شرط وضعیت لایسنس؛ محتوای اصلی نصب افزونه باقی است |
| `hub/liquid/admin/views/liquid-demos.php` | برداشتن شرط وضعیت لایسنس؛ کنترل Hub Core و محتوای اصلی دمو باقی است |
| `hub/liquid/libs/merlin/merlin-config.php` | غیرفعال‌شدن مرحله و الزام فعال‌سازی |
| `hub/liquid/libs/merlin/class-merlin.php` | عدم ثبت AJAX فعال‌سازی و خروج فوری از handler قدیمی؛ سایر مراحل دست‌نخورده |
| `hub-elementor-addons/elementor/template-library/template-library.php` | فقط حذف شرط hub_purchase_code_status در get_template_content؛ بقیه فایل از نظر محتوای کد برابر ورودی است |
| `hub/style.css` | نسخه 6.0.3.2 و Update URI با آدرس API فروشنده؛ دیگر false نیست و updater مستقل فعال است |

کد updater قدیمی و بخش‌های غیرفعال vendor ممکن است هنوز به‌عنوان فایل/متد داخل
درخت کد باشند؛ مسیر بارگذاری و اجرای فعال لایسنس حذف شده است. اعلان GPL، نام
نویسنده و مجوز فایل‌های ثالث حذف نشده‌اند.

گزینه‌های قدیمی لایسنس در دیتابیس سایت واقعی پاک نشده‌اند و اکنون برای اجرای قالب
و کتابخانه مصرف نمی‌شوند. هیچ مهاجرت یا حذف اطلاعات سایت واقعی اجرا نشده است.
کد حفظ تنظیمات در Reset قدیمی دست‌نخورده است؛ از Reset برای این اصلاح استفاده نکن.

## فایل‌های مرجع و خروجی

- `change-manifest.json`: فهرست تغییرات با hash نسخه اولیه و نهایی.
- `license-changes.patch`: اختلاف با فایل‌های تحویل‌شده، برای مرور و تطبیق معنایی.
- `../backups/hub-6.0.3-before-local.zip`: فایل‌های اصلی پیش از تغییر؛ شامل چند فایل
  بررسی‌شده‌ای هم هست که نهایتاً به نسخه اولیه برگشتند.
- `../releases/`: ZIP قالب و افزونه اصلاح‌شده، به‌اضافه Hub Core اصلی برای نصب محلی.
- `../update/README.md`: مسیر تحویل و مقایسه نسخه‌های بعدی.

اعلان و مسیر نصب آپدیت قالب در وردپرس فعال است. در نسخه 6.0.3.1 این مسیر اشتباهاً
حذف شده بود؛ نسخه 6.0.3.2 آن را مستقل از لایسنس برگرداند. فعال‌کردن نصب خودکار
زمان‌بندی‌شده جدا از «اعلان آپدیت» است؛ انتخاب auto-update کاربر دست‌کاری نشده است.
جایگزینی با ZIP اصلی فروشنده اصلاحات را حذف می‌کند؛ این پیامد مورد قبول کاربر است
و نسخه اصلی جدید برای اصلاح مجدد به `update/` تحویل داده خواهد شد.

## رفتار نهایی بررسی آپدیت

- منبع نسخه: `https://api.liquid-themes.com/hub`، همان action=get_version و slug=hub
  و author اصلی؛ بدون ارسال ایمیل یا purchase code ساختگی. دانلود package برگشتی
  در پیشنهاد استاندارد وردپرس حفظ می‌شود. نصب واقعی بسته فروشنده در این نوبت انجام نشد.
- WP-Cron با hook `hub_check_theme_updates` هر ۱۲ ساعت؛ بررسی موفق ۱۲ ساعت کش
  می‌شود. پس از خطا ۳۰ دقیقه backoff داریم و آخرین پاسخ سالم تا ۷ روز حفظ می‌شود.
- صفحه اختصاصی «پیشخوان > به‌روزرسانی‌ها» در صورت نیاز بررسی می‌کند. «بررسی دوباره»
  با nonce و مجوز استاندارد می‌تواند کشِ زمان بررسی را نادیده بگیرد. timeout درخواست
  ۵ ثانیه است. صفحات معمولی مدیریت و بازدیدکننده فقط داده کش‌شده را می‌خوانند.
- خواندن `site_transient_update_themes`، badge و ساخت updater هیچ HTTP انجام نمی‌دهد.
  این تضمین مربوط به updater جدید است؛ قطع همه اتصال‌های سایر قابلیت‌ها نیست.
- نسخه مقایسه بالادستی `6.0.3` از پسوند بسته محلی `6.0.3.2` جداست. در نسخه جدید
  فروشنده، UPSTREAM_VERSION باید مطابق مبنای جدید اصلاح شود.
- مسیر آپدیت افزونه‌های مخزن مانند Elementor تغییری نکرده است. افزونه‌های همراه
  Hub طبق منطق اصلی TGMPA و versionهای تعریف‌شده در فایل liquid-register-plugins.php
  بررسی می‌شوند؛ این نسخه‌ها همراه آپدیت قالب تازه می‌شوند. API مستقلِ تازه‌ای برای
  تک‌تک افزونه‌ها ساخته نشده و نسخه آن‌ها از نسخه قالب حدس زده نمی‌شود.

تأیید کوتاه نسخه 6.0.3.2: ۱۵ بررسی آفلاین updater گذشت؛ سرور واقعی اطلاعات 6.0.3
را با HTTP 200 برگرداند. در runtime وردپرس، پاسخ آزمایشی نسخه 6.0.4 به پیشنهاد
استاندارد آپدیت تبدیل و سپس پاک‌سازی شد؛ پاسخ واقعی دوباره در کش قرار گرفت. پنج بار
خواندن وضعیت آپدیت هیچ HTTP نداشت و refresh بعد از بررسی موفق دوباره درخواست نزد.
hook زمان‌بندی نیز ثبت شد. gateهای لایسنس همچنان حذف‌اند. Skill با quick_validate
اعتبارسنجی شد. تست طولانی یا نصب نسخه جدید فروشنده انجام نشد.

## بررسی محدود انجام‌شده

- lint تمام فایل‌های PHP تغییرکرده با PHP 8.5.12 روی میزبان.
- smoke کلاس سازگاری: نمایش وضعیت محلی، نبود فرم فعال‌سازی و نبود متدهای قفل/دامنه/updater.
- Docker: WordPress 7.1.3، PHP 8.4.26، Elementor 4.3.5، Hub Core 6.0.3، Hub Elementor Addons 6.0.3.
- ۹ بررسی runtime: بارگذاری افزونه‌ها، ۱۵۳ ویجت ثبت‌شده، منبع اصلی Hub Collections،
  ذخیره و خواندن قالب محلی Elementor، فهرست و درج محتوای طرح Hub با وضعیت لایسنس invalid.
- درخواست کتابخانه در smoke با پاسخ کنترل‌شده شبیه‌سازی شد؛ URL، API version 6.0.3
  و مسیر import اصلی بررسی شدند. دسترسی زنده به کاتالوگ فروشنده تأیید نشده است.
- درخواست HTTP ناشناس صفحه نخست: ۲۰۰، بدون پیام لایسنس یا Fatal؛ حتی با گزینه‌های
  invalid و revoke قدیمی در همین دیتابیس آزمایشی. دریافت دوم حدود ۱۳٫۸ ثانیه طول کشید؛
  این اندازه‌گیری محیط Docker/Windows است و نشانه بهبود سرعت سایت واقعی نیست.
- فایل‌های Hub Core بررسی‌شده با بکاپ byte-for-byte برابرند. تغییر کتابخانه فقط همان
  guard است؛ فایل‌های UI/JS کتابخانه و پوشه ویجت‌ها و کنترل‌ها اصلاح نشده‌اند.

در بررسی اولیه، مرورگر و اجرای JS ویرایشگر بررسی نشده بود؛ نتیجه تلاش کوتاه بعدی
در بخش زیر آمده است. آزمون طولانی، تمام قالب‌های فروشنده و سایت واقعی بررسی نشده‌اند.
هشدارهای deprecated موجود در Redux و Elementor روی PHP 8.4 مشاهده
شدند؛ vendorها برای رفع آن دست‌کاری نشدند. نمایش خطا در Docker خاموش و ثبت log روشن است.

## تلاش کوتاه برای بررسی پنجره کتابخانه در مرورگر — ۲۰۲۶-۱۱-۱۰

ورود به مدیریت Docker موفق شد و صفحه ویرایش Elementor برای پیش‌نویس آزمایشی شماره ۱۰
باز شد. با این حال ویرایشگر روی Loading ماند و پیشنهاد Enable Safe Mode ظاهر شد؛
Safe Mode فعال نشد و تنظیمات قالب یا Elementor تغییر نکردند.

در Network، فایل محلی `hub-templates-lib.js?ver=6.0.3` پاسخ ۲۰۰ گرفت. هم‌زمان
درخواست `https://cdn.jsdelivr.net/npm/ace-builds@1.43.2/src-min-noconflict/ace.min.js?ver=1.43.2`
هنوز پاسخ نداشت. این منبع در فایل دست‌نخورده
`elementor/core/editor/loader/editor-loader.php:272` ثبت شده است. فایل دیگر ACE با نام
`ext-language_tools.js` پاسخ ۲۰۰ گرفت. در بررسی DOM، `window.elementor` هنوز تعریف
نشده و document در وضعیت loading بود؛ بنابراین اجرای کامل ویرایشگر و بازشدن مودال
انتخاب طرح تأیید نشد. این مشاهده به‌تنهایی اثبات علت قطعی همه مشکلات ویرایشگر نیست.

برای کوتاه‌ماندن آزمون، تست طولانی، تغییر کتابخانه، فعال‌کردن Safe Mode یا جایگزینی
CDN انجام نشد. تأییدهای PHP و API شبیه‌سازی‌شده قبلی معتبرند، اما نباید آن‌ها را با
تأیید بصری پنجره انتخاب طرح یا دسترسی زنده به طرح‌های فروشنده یکسان دانست.
در این نوبت فقط مستندات تکمیل شدند؛ فایل‌های خروجی نصب تغییری نکردند.

## محیط Docker

### نتیجه بعد از انتقال به volume و اصلاح دسترسی‌ها

در ادامه همین روز، صفحه Theme Options با ورود واقعی دوباره دریافت شد: HTTP 200،
زمان پاسخ حدود ۲٫۲۷ ثانیه و صفر پیام File Permission Issues.

ویرایشگر Elementor پیش‌نویس شماره ۱۰ در مرورگر به وضعیت complete رسید و
`window.elementor` بارگذاری شد. این بار هر دو فایل ACE از CDN پاسخ ۲۰۰ گرفتند.
دکمه اصلی Hub Collections داخل iframe ویرایشگر کلیک شد؛ مودال اصلی کتابخانه باز
شد و ۱۰۶۰ کارت طرح در DOM ثبت شدند. نمونه‌ها شامل Header 80، Footer 82 و
Call to Action 47 بودند. در مشاهده محدود، ۲۳ تصویر thumbnail بارگذاری شده بودند
(بقیه می‌توانند lazy-load شوند). Console در این اجرا خطای JavaScript نداشت.
این تأیید واقعی بازشدن و نمایش فهرست کتابخانه است؛ تلاش قبلی Loading را توصیف می‌کند
و دیگر وضعیت آخر محیط نیست. درج و ذخیره همه طرح‌ها یا سازگاری کامل کل کاتالوگ
آزموده نشده است. نسخه افزونه‌ها برای این بررسی تغییر نکرد.
تب Pages نیز انتخاب شد و ۱۸۷ کارت صفحه نمایش داده شد؛ نمونه اول
`Starhub Fourteen - Home` بود. پنجره کتابخانه برای بازبینی کاربر باز ماند.

پروژه Compose: `hub`؛ سایت `http://localhost:8096/` و مدیریت `/wp-admin/`.
کاربر آزمایشی: `hubadmin`؛ رمز در `.env` با کلید `HUB_ADMIN_PASSWORD` قرار دارد.
پورت فقط روی 127.0.0.1 منتشر شده؛ دیتابیس و volumeها مستقل‌اند. شبکه عادی bridge
است تا کتابخانه اصلی مسدود نشود. هیچ پروژه یا دیتابیس Docker دیگر تغییر نکرد.

در تنظیم اولیه فایل‌های پروژه به‌صورت read-only از ویندوز mount شده بودند. به درخواست
بعدی کاربر برای نصب/آپدیت و تست، هر چهار پوشه قالب/افزونه در volume داخلی
`hub_hub_wordpress` کپی شدند و bind mountهای ویندوز برداشته شدند. فایل‌های مرجع
میزبان و دیتابیس حفظ شدند. کپی اجرایی اکنون قابل‌نوشتن است؛ تغییر فایل میزبان دیگر
خودکار به محیط اجرا منتقل نمی‌شود. آپدیت از پیشخوان فقط کپی اجرایی را تغییر می‌دهد.
نسخه افزونه‌ها در جریان این انتقال ارتقا داده نشد.

خطای File Permission Issues بعد از انتقال بررسی شد: uploads مالک root داشت و
پوشه `uploads/redux` مجوز 000 داشت. مالکیت uploads به www-data و مجوز پوشه‌ها به
755 و فایل‌ها به 644 اصلاح شد. نوشتن واقعی با کاربر www-data در مسیرهای وردپرس،
wp-content، uploads، upgrade، plugins و themes و دسترسی همه ۱۹ ورودی موجود uploads
بررسی شد. برای اجرای PHP وردپرس در تست‌های بعدی از `--user www-data` استفاده شود.
این اصلاح فقط مربوط به محیط Docker است و فایل‌های قالب/افزونه را تغییر نمی‌دهد.

پوشه `update/` و مستندات نگهداری خارج از قالب‌اند. محتوای ZIPهای خروجی نیز بررسی شد؛
هیچ پوشه نگهداری update/docs یا فایل manifest/patch خودمان داخل بسته نصب قالب نیست.

راه‌اندازی: `docker compose up -d --pull never`.
توقف بدون حذف داده: `docker compose stop`.
برای این کار از `down -v` استفاده نکن؛ آن فرمان داده‌های محیط را حذف می‌کند.

ابزار شبکه smoke موقت بود و از mu-plugins محیط حذف شد؛ محدودکننده دائمی شبکه وجود ندارد.
رمزها، تست‌ها، وردپرس و دیتابیس داخل ZIP قالب/افزونه بسته‌بندی نمی‌شوند.
